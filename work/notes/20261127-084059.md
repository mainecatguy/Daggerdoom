# Talking to generic outdoor NPCs (townspeople) — 2026-11-27 08:40

## Problem found

Doom already treated townspeople (`DFTownsperson`) as NPCs for Use: `dd_info.cpp` `Pick` counts `IsTownsperson`, and
`DD_InfoUseNpc` sends `DFB_KIND_NPC_USE` with the townsperson's id (tag 7). The break was on Daggerfall's side:
`DoomerfallTalk.OnUse` only looked the id up with `DoomerfallNpcs.FindNpc`, which knows only `StaticNPC`s (tag 6). A
townsperson id found nothing, so Daggerfall answered `NPC_USE_GONE` and nothing opened. (The `+NOINTERACTION` lead in
`20261124-004803.md` was not the cause: Doom's NPC pick is a ray test of its own and ignores that flag.)

Merchants are interior `StaticNPC`s, which is why they worked.

## Fix (Daggerfall Unity only; no UZDoom, bridge, or mod change)

- `DoomerfallTalk.cs`: a townsperson id is looked up in `DoomerfallTownspeople.FindPerson` (living people of the
  current town only). Daggerfall then runs its own mobile-NPC activation on a stand-in `MobilePersonNPC` that carries
  the person's race, gender, outfit, guard flag, name (the same name the look label shows) and portrait record
  (`MobilePersonNPC.SetPerson`'s formula: the race/gender/outfit face record plus the person's face variant).
  - The stand-in's GameObject is made inactive before the component is added, so `MobilePersonNPC.Awake` never runs:
    it never registers in `ActiveGameObjectDatabase` as a civilian and has no billboard, motor, or collider.
  - One stand-in per person (up to 64, then the cache is cleared), so Daggerfall's "same talk partner" rules and its
    per-NPC rolls (`DFRandom.Seed = lastTargetMobileNPC.GetHashCode()`) stay with that person while a game runs.
  - The stand-ins are destroyed whenever a game starts (`StartGameBehaviour.OnStartGame`) and when a load begins
    (`SaveLoadManager.OnStartLoad`), so no talk partner carries over a load or into a new character (verifier fix 2).
- `PlayerActivate.DoomerfallTalkToMobileNpc`: a 9-line hook beside the existing `DoomerfallUseNpc`, calling
  Daggerfall's own `ActivateMobileNPC` in Grab mode at Doom's distance. It opens `TalkManager.TalkToMobileNPC` (the
  region's "People of" faction, commoners social group, as in Daggerfall Unity), and beyond reach gives "You are too
  far away". Talk carries Daggerfall's usual reaction roll and Etiquette/Streetwise tallies.
- Crouch + Use (which Doom sends as Steal) on a townsperson also just talks. The first version ran Daggerfall's
  pickpocket here, which adds gold, tallies Pickpocket, and on failure records a crime and spawns city guards; that was
  not asked for, so it is off (verifier fix 1). Townsperson pickpocketing belongs to its own item (for example the
  Pickpocket part of `skillbasics` in `work/todo.md`).
- `DoomerfallBridge.cs`: hands the townspeople component to the talk component.

Ownership: Daggerfall owns dialogue and rules; Doom only reports which person the player used and from how far.
Behaviour changed: Use on a townsperson (crouching or not) opens Daggerfall's talk, with its reaction roll and skill
tallies, or "too far away". No combat, movement, AI, crime, or economy path is reached from it.

# Look labels show the item name, not the pickup message (run 20261127-084059)

Goal: looking at a stimpack said "Picked up a stimpack." instead of "Stimpack", and the owner's save "YouGotAPickup"
showed a "You got a pickup" label while looking at nothing.

## Plan

1. Find where the label's item name comes from. Fix the name for stock and DRLA pickups.
2. Load the owner's save, find what the label pointed at, fix it.
3. Prove both in a real paired run (old build against new), plus a sweep of every pickup class, plus the E1M1 checks.

## Findings

- **Names.** `dd_items.cpp ItemName` used the item's Tag, else its pickup message. Stock Doom items have Tags. DRLA's
  mostly do not: `RLStimpack : CustomInventory replaces Stimpack` has only `Inventory.PickupMessage "Picked up a
  stimpack."` (`GameMods/ExtractedData/DoomRL_Arsenal_1.1.5/actors/misc/HealthItems.txt`). Same for medikits, keys,
  armor bonuses and many more. The same name also went into the art slot header, so Daggerfall's inventory name for a
  Doom item taken with Use could get the message too.
- **The empty-spot label.** The save is `D:\dev\DoomDaggerfall-loop\play\run\saves\save08.zds` (title "YouGotAPickup",
  map DDS5LK5G). In its level snapshot the player stands at (-87, -15, 0), ceiling 96, sector 58. A `DFAmmo_Clip_0`
  lies at (-102, -6, **96**) in the same sector, on top of the 3D floor of the storey above: 17 units away
  horizontally. Doom's `P_CheckSight` lets it through (it tests 3D floors only roughly inside one sector, and the item
  rests exactly on the plane), and `AimScore`'s "item on the floor near your feet" rule ignores which way the player
  faces. So the label named a clip no one could see, wherever the player looked. In the owner's build the DFAmmo
  classes had no Tag yet (added 03:31 on 2026-11-27, `bb699f46`) and override `PickupMessage()` instead of setting
  `PickupMsg`, so the fallback read Inventory's default "You got a pickup". On today's build the same spot said
  "Bullets". Use would also have taken that clip through the floor.

## What changed

1. **`mods/doomerfall/src/zscript/DoomerfallLook.zs` `DoomerfallItemName.Of(Actor)`**: the name rule, in order:
   - the item's Tag (a Tag that is an untranslated string id such as DRLA's `TAG_MEGASPHERE` counts as none; a
     trailing "Pickup"/"Pickups" word is dropped, so DRLA's "Clip Pickup" is "Clip");
   - the Tag of the stock item the class replaces (`RLStimpack` -> Stimpack's "Stimpack");
   - the pickup message cut to its noun and title-cased ("Picked up a small health canister." -> "Small Health
     Canister"); Inventory's default message and messages with format codes never count;
   - the class name split into words ("RLMarathonStimpack" -> "Marathon Stimpack").
   In ZScript, `GetTag("")` answers the class name for an untagged actor, so the rule passes a marker instead.
2. **`UZDoom/src/dd_items.cpp`**: `ItemName` calls that rule (found once with `PClass::FindFunction`, like
   `WeaponText`). Without the mod it keeps the old rule. `ItemInView` takes a `look` flag, set only by `DD_LookItem`
   (the label). With it, an item is skipped when a solid 3D floor lies between the player's eye height and the item
   both in the item's sector and in the player's own sector (`OtherStorey`), so an item on a ledge seen from an open
   room still gets a label. Use and Info choose exactly as before. Both changes are reached only with a bridge session
   and Use rules on a generated map.
3. **Floor guns**: unchanged. `dd_look.cpp AskGun` still shows Doom's name until Daggerfall's material name arrives.
4. **Sentence messages**: a pickup message holding a pronoun or verb word (you, your, this, there, it, is, are, has,
   have, been, will, now, activated, ...) does not name the item and falls back to the class name. DRLA's Duke Nukem 2
   items: "This is the most powerful weapon of all!" -> "Duke2 Rocket", "Cloaking device activated!" -> "Duke2 Cloaking
   Device". The sweep now fails on any sentence-like name.

Verifier round 1 (fixed): the first version put the storey filter on Use and Info too, and Duke 2 items kept sentence
messages as names. Whether Use should also refuse items through a floor is a question for the owner.

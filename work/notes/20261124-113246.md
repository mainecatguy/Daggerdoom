# Agent test runs must never take the owner's mouse, focus, screen, or sound

Branch `agent/quiet-20261124-113246`. Follows `work/notes/20261123-215225.md` (the first quiet launch run).

## Result in one paragraph

A program on a private desktop cannot show the owner a window, take focus, flash the taskbar, or move the pointer
(`SetCursorPos` fails with error 5, measured). It **can** still confine the pointer: `ClipCursor` from a private desktop
succeeded and the owner's desktop saw the clip (measured; an earlier attempt failed only while another clip was
active). A game whose window is the only one on its private desktop counts as focused there, so a Unity cursor lock
or a UZDoom mouse grab would pin the owner's pointer. So the fix has two parts: (1) `quiet_run.py` puts every program,
and everything it starts, on a private desktop by default; (2) in their quiet modes neither game confines the cursor
any more: Daggerfall Unity with `-dfmute` never locks it (`DoomerfallQuiet.cs`), and UZDoom with `-noactivate` never
grabs the mouse (`i_mouse.cpp`, one line). Both flags are added by the launcher's `--minimized` and by the new
`quiet_run.py`. UZDoom renders the same on a private desktop, and paired tests, smoke loads, and Unity builds pass
with the same output. All 90+ test scripts
already call the main checkout's `quiet_run.py`, so the change reaches them without editing each one. **The
permission settings refused my edits to `scripts/overnight/quiet_run.py` and `AGENTS.md`** (the goal authorized them,
but the tool denied the folder), so the new `quiet_run.py` is ready, tested, and waiting in
`work/notes/20261124-113246-quiet_run.py`. See "To apply" below.

## New probe checks (`tools/quiet_probe/quiet_probe.py`)

The cursor belongs to the whole desktop, so these watch globally. Each event is tagged `tree` when it can be tied to
the command's own windows (foreground window, window under the cursor, or clip rectangle matching a window of the
tree), otherwise `other`.

- **clip**: `GetClipCursor` smaller than the virtual screen, polled every 4 ms.
- **move**: the cursor changed with no low-level mouse event (`WH_MOUSE_LL`) since the previous sample and none in
  the last 50 ms. `SetCursorPos` makes no low-level mouse event; real and injected mouse input do.
- **hidden**: `GetCursorInfo` reports no cursor shown, or no cursor.
- **capture**: `GetGUIThreadInfo` capture window on a thread that owns a tree window, or on the foreground thread.
- **injected**: low-level mouse events flagged `LLMHF_INJECTED` (`SendInput`, `mouse_event`).

`self_test.py` now also clips the cursor to one pixel less than the screen for 0.2 s, moves it one pixel and back,
hides it over a 3x3 window at the pointer, captures the mouse with that window, and sends two one-pixel injected
nudges, which must count as injected input and not as program moves. Result: `PASS` (run while the owner was
moving the mouse).

### Failed approaches for the probe

- `GetMouseMovePointsEx` (the mouse's movement history) to tell program moves from mouse moves. `SetCursorPos` adds
  its points to that history too, with the same zero `dwExtraInfo`, so nothing tells them apart.
- Only "a hook event since the previous sample": while the owner used the mouse, about one cursor step a second
  (1 to 3 pixels) arrived with no hook event, which counted as a false program move. The 50 ms window removes these.
  The cost: a program move made while the mouse itself is moving is missed.
- Python's `INPUT` structure with extra padding (48 bytes) makes `SendInput` fail silently; it must be 40 bytes on x64.

## Findings

1. **A private desktop blocks cursor moves but not cursor clips.** `tools/quiet_probe/desktop_mouse_check.py` runs a
   helper through `quiet_run.py --desktop`. `SetCursorPos` returns FALSE with error 5 and the owner's cursor did not
   move, and `GetCursorPos` fails there. `ClipCursor` succeeded, and the owner's desktop saw the clip
   `(0,0,3839,2160)` for the second it lasted. The first time I ran it, `ClipCursor` failed with error 5, while a
   one-point clip from another program was active; I first wrote down "blocks the mouse completely" from that run,
   which was wrong. Since a one-point clip also drags the pointer to that point, a game confining the cursor from a
   private desktop takes the owner's pointer. Hence the two game-side changes.
2. **The owner's cursor was clipped to a single point** at the start of this run: `(1920,1080,1920,1080)`, the centre
   of the 3840x2160 screen, with no game running. That is how a Unity game locks the cursor (a one-point clip at its
   window's centre, cursor moved there), and a 640x360 Daggerfall Unity window centred on the screen has its centre
   there. A clip outlives the program that set it until a desktop switch clears it, so the pointer stays stuck after
   the test ends. Later in the run, more one-point clips appeared at `(1426,770)` and `(1920,1080)`, each with the
   cursor jumped to that point, while no process of mine was on the owner's desktop. `tools/quiet_probe/who_clips.py`
   names the foreground window and every window centred on the clip point at that moment. It found only the Claude
   desktop app in front and explorer and the NVIDIA overlay centred there, because windows on private desktops cannot
   be queried from the owner's desktop (their handles return pid 0 and error 1400). **The program that set them was
   not identified with certainty.** What the timing shows:
   - In each of four paired runs inside the new `quiet_run.py` (all games on private desktops), a one-point clip at
     `(1426,770)` began 8 to 11 s in, while both games were running, and the owner's pointer was dragged there
     (from `(1465,2071)`, `(949,946)`, and so on). In the run that recorded process lifetimes it ended at 16.552 s:
     UZDoom exited at 16.551 s, and Daggerfall Unity (crash handler gone at 16.486 s) at about the same moment.
     `(1426,770)` is the centre of a 2852x1540 rectangle at the screen's origin.
   - The same `(1426,770)` clip also appeared between my runs, while none of my programs were running, so at least
     one other lane makes it too. Two Unity editors (another lane's builds) and other `quiet-run-*` desktops existed at
     the time.
   - Daggerfall Unity alone at its title screen on a private desktop made no clip in one run; in an earlier run a
     `(1920,1080)` clip appeared at 22 s and ended when the game was killed at 25 s.
   UZDoom's grab (`FRawMouse::Grab`) calls `ClipCursor` with its client rectangle and Unity's cursor lock clips to its
   window's centre, so both games can do this on a private desktop, where their window counts as focused. The two
   game-side changes stop both. The play-test list asks the owner to confirm.
3. **Daggerfall Unity on the owner's desktop takes focus twice per start** (about 3 s and 6 s in), shown once. This is
   every direct launch, and every paired test whose harness folder holds a launcher older than the launcher's
   private desktop.
4. **UZDoom without `-noactivate` takes focus once** at startup. With `-noactivate` it never did. UZDoom grabs the
   mouse only while its window is the foreground window (`I_CheckNativeMouse`). On a private desktop it can be, so
   `-noactivate` now also means "never grab the mouse" (`UZDoom/src/common/platform/win32/i_mouse.cpp`, marked
   `// Doomerfall`). Tests drive Doom through the bridge and console, not the real mouse, so they lose nothing.
5. UZDoom's raw keyboard input (`RIDEV_INPUTSINK`) reaches a background test game, but `PostKeyEvent` drops key-down
   events when it is not the foreground window, so the owner's typing does not drive tests.
6. A **visible "Windows PowerShell 5.1" console window** (pid 60264) was open on the owner's desktop during this run.
   It may be the owner's own; if a lane opened it, a script started PowerShell without `-WindowStyle Hidden` or
   `-NoNewWindow`. Not investigated.
7. `loud_launch_lint.py tools scripts` lists 10 older tools that start UZDoom or Unity directly instead of through
   `quiet_run.py` (for example `dungeon_converter/smoke_load.py`, `texture_shot.py`, `dungeon_compare/*.py`,
   `hp_sync/build_unity.py`). They start UZDoom minimized with `-noactivate`, and `smoke_load.py` measured all 0. Left
   unchanged: converting ten tools I cannot all test would risk their results. With `--base` the check reports only
   files a branch changes.

## What the probe cannot see

- Sounds in Windows' shared "system sounds" session, such as a message box chime (no process session).
- Raw-input registrations of other processes (`RIDEV_NOLEGACY`, `RIDEV_CAPTUREMOUSE`); their effect needs focus,
  which is checked.
- A program cursor move made while the mouse itself is moving (see above), and which program made a clip or move
  that cannot be tied to a window (reported as "other").
- Keyboard focus taken without becoming the foreground window, and global keyboard hooks.

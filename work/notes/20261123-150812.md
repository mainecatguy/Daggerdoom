# Connected building and dungeon transitions

Branch `agent/engine_r3-20261123-150812`. Demo: `D:\dev\DoomDaggerfall-loop\review\connected-transitions\play.bat`. It starts in Gothway Garden, which has houses and the Privateer's Hold entrance.

## Result

When the Doom player uses a building or dungeon door, the hidden Daggerfall player now goes through the same door with Daggerfall's own transition code. Daggerfall then holds the real interior or dungeon in memory. Leaving returns it to Doom's outdoor position.

## How it works

1. `NotifyTransition` in `dd_treadmill.cpp` sends a new ordered bridge event, `DFB_KIND_TRANSITION`, with the action and the outside door's world position. It is additive, so the protocol stays at 4.
2. `DoomerfallTransition.cs` waits for the world to settle, finds the nearest real Daggerfall door of the right type, and refuses a match over 128 units.
3. Buildings use `TransitionInterior` with the same discovery data as a real door click. Exits use `TransitionExterior` and `TransitionDungeonExterior`.
4. The dungeon uses `StartDungeonInterior` with enemy import off, because Doom owns monsters. **Daggerfall quest foes are therefore not placed by this path.** Quests are out of scope.
5. A save waits for any pending transition. Because events are ordered, the door event always arrives before the save request.
6. After a load, Doom re-sends which side of which door it restored, before the load finishes. Daggerfall reconciles to that.
7. If Daggerfall cannot follow, it logs an error and waits outside the door, which was the earlier behavior. Doom keeps playing.

## Known gaps

- Only Privateer's Hold can be entered as a dungeon, because Doom has only that one converted.
- Interior position is not synced. Daggerfall stands at its landing spot while Doom walks around, so room-level logic such as quest markers or NPC proximity will not follow the player yet.
- After loading inside a dungeon, Daggerfall's stored position is the map pixel's origin rather than the entrance. This is Daggerfall's normal respawn. The map pixel is right and leaving worked.
- A startup `-loadgame` races the private test start and leaves Daggerfall at its start pixel. Test runs load after both games are playing instead. The real startup flow does not exist yet.
- Not run: death inside a building, loading a save made before this change, and every door of every building.
- Doors between rooms, locks, shop hours, NPCs, and interior enemies remain out of scope.

## Failed approaches and bugs found

- The first entry into a neighboring location failed. Daggerfall's location object lags the map pixel by some frames, so the door search looked in the previous town. It now waits for the location and GPS to match the door's pixel.
- The first exit-accuracy log reported up to 3,164 units. A position check left over from before the door compared against an old target. Clearing it on each door gave 0.0.
- My first exception count used a pattern that missed `System.` exceptions. The stricter count found a startup exception that also appears in earlier builds' logs, and the terrain exception below.
- Loading at the very first ready moment threw a `NullReferenceException` in `DaggerfallTerrain.CompleteMapPixelDataUpdate`. It did not appear in 6 of 6 load runs after waiting 3 seconds for streaming to finish. I did not fix it, because it is in the general load path. It is reported as an oversight.

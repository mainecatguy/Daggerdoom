## Findings

- **The join commit (6b3623ed) left git conflict markers in six files**: `dd_bridge.cpp`, `vmthunks_actors.cpp`,
  `actor.zs`, `CVARINFO.txt`, `MAPINFO.txt` and `manual.md`. UZDoom and the mod could not have compiled. Resolved by
  keeping both sides everywhere (`DD_SheetSkillBase` and `DD_SheetValue`; both handlers `DoomerfallJump` and
  `DoomerfallAutomatics` in MAPINFO; both CVARs; the manual's Automatics section, then Falling and jumping). Commit
  bfc0ffeb.
- Daggerfall's exemptions (`AcrobatMotor`): Slowfall sets the fall start to the current height every frame while
  falling (`ApplyGravity`), so the fall counts only from where Slowfall ended; a landing with
  `StreamingWorld.PlayerTileMapIndex == 0` (water tile) does no damage (`CheckFallingDamage`).
- `IsSlowFalling` is a *constant effect*: the effect manager clears it and the Slowfall effect sets it again every
  frame. Setting it directly from a test component races with that (the first test run saw it on for ~1 s only), so
  the test casts a real Slowfall spell instead.
- Daggerfall's streaming world keeps updating `PlayerTileMapIndex` from the position Doom sends, so the water tile is
  the one under Doom's player. Town DDT07154 and the overworld start have no water tile in the player's own map pixel;
  the nearest is about 460 m from the overworld start (found by the test component, across the 9 loaded terrains).
- In the sync test, casting a spell throws a NullReferenceException in `HUDActiveSpells.UpdateIcons` after the bundle
  is assigned (Daggerfall's HUD is not set up there), and the spell then ends after ~2 s. The test recasts each second
  while Slowfall should be on. I did not check whether a real Slowfall cast in a normal paired game hits the same
  exception. Worth a look during play-testing (see the list).

## What was built

- **Bridge:** `dfb_df_state.player_flags` (the old `pad0`, so the layout is unchanged) with `DFB_PLF_SLOWFALL` (1) and
  `DFB_PLF_OUTDOOR_WATER` (2). Bindings regenerated (`generate_bindings.py`; schema hash changed, so both games must
  be rebuilt together, as they were). I used the per-frame state, not the character sheet, because the water flag
  follows the player's position and the sheet logs every change.
- **Daggerfall:** `DoomerfallFallState.cs` fills the flags every frame (Slowfall from `PlayerEntity.IsSlowFalling`;
  water only outdoors, `!IsPlayerInside && PlayerTileMapIndex == 0`) and logs changes to the bridge log. Called next
  to the damage bonus in both publish paths of `DoomerfallBridge.cs`.
- **UZDoom:** `DD_BridgePlayerFlags()` (dd_bridge.cpp), thunk `Actor.DD_PlayerFlags` (vmthunks_actors.cpp),
  declaration in actor.zs. Returns 0 with no bridge session, so Doom-only games are unchanged.
- **Mod:** `DoomerfallJump.zs`: while Slowfall is reported the fall start follows the player every tic; a landing
  with the water flag does no damage (logged with `DDLog.Debug`).
- **Tests (outside game source except one hook):**
  - `tools/jumping/jumpz_saveload.py` + `.zs`: Doom-only real save/load. The probe turns the handler on as a
    Daggerfall map would (`rules`, `testSkill`), saves at Jumping 50, then new launches load that save at 100, 0, 50
    and 75.
  - `tools/jumping/run_fall_exempt_test.py` + `fall_exempt_probe.zs`: paired run with Daggerfall's `-dffalltest`.
  - `DoomerfallFallStateTest.cs` (Daggerfall, `-dffalltest`): casts Slowfall for 20 s, clears spells for 20 s; logs
    the nearest water tile as a Doom-unit offset. Hook: two lines in `DoomerfallBridge.cs`.
- `manual.md` Falling and jumping: water and Slowfall now protect; Slowfall does not slow the fall yet.
- Demo notes (`tools/jumping/make_demo.py`) mention both exemptions.

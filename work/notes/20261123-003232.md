# Show Daggerfall's fast travel menu in Doom

Branch `agent/engine-20261123-003232`. Demo: `D:\dev\DoomDaggerfall-loop\review\fast-travel-menu\play.bat`. Press K to open the map. Esc or K closes it.

## Result

The Open Fast Travel control pauses Doom and shows Daggerfall's real travel map inside the Doom window. Doom's mouse and keyboard drive it. Closing it resumes Doom. Picking a destination logs it and closes the menu without moving the player, advancing time, or charging gold.

## How it works

**Frames.** While a menu is open, Daggerfall draws its normal UI into a private render texture through its existing `CustomRenderTarget` hook. `AsyncGPUReadback` copies it without stalling the GPU, and the BGRA frame goes into a new shared surface: a separate mapping with its own triple buffer (up to 1920x1200). Doom takes the newest frame, uploads it as a texture, and draws it letterboxed over a black screen.

**Input.** While a menu is open, Doom's GUI capture is on and `DD_BridgeUiWndProc` forwards raw window messages as bridge events. `DoomerfallInput` applies them before any other Daggerfall script runs, at most one change per key per frame so a fast click is never lost. `InputManager`, hotkeys, scroll, typed characters, and the windows' direct key reads all use it. With no menu open, every call goes to Unity as before.

**Lifecycle.** `netevent df_fast_travel` is intercepted natively only in a bridge session. Doom sends `UI_OPEN`, Daggerfall opens the window and answers `UI_STATE`, and returning to the HUD closes it. Doom gives up after 5 seconds with no answer, or if Daggerfall's heartbeat goes stale, and resumes play.

**Adding the next menu.** Add a `DFB_UI_*` id and open that window in `DoomerfallUi.OnOpen`. The surface, input, pause, and close paths are shared. The bridge protocol is now version 3.

## Measured (`tools/fast_travel_menu/run_menu.py`, run `final`)

Both games were minimized, so treat these as relative. Daggerfall's surface was 960x540.

| Measure | p50 | p99 | max |
|---|---|---|---|
| Input sent to frame received by Doom (first menu, 13 samples) | 8.30 ms | 10.22 ms | 10.22 ms |
| Input sent to frame received by Doom (second menu, 14 samples) | 7.86 ms | 24.57 ms | 24.57 ms |
| Capture to received by Doom (613 frames) | 2.10 ms | 4.56 ms | 7.81 ms |
| Doom's CPU copy of a frame (613 frames) | 0.09 ms | 0.17 ms | 0.27 ms |

These stop when Doom receives the frame. They do not include Doom's draw and display time. Opening took 5 to 13 ms in the final run. On other runs with the machine busy, input latency reached about 410 ms, with few frames delivered, and I did not determine what else was running.

## Proven with the real games

- Open, Esc close, and reopen. Doom's `maptime` stayed frozen while open (207 and 278) and advanced between opens.
- A full route through real UI: I'm At, Enter, L for the list, double click a location, Y, then B for Begin. Daggerfall logged `Agakawan at map pixel 840,456 (not applied)`. Pixel stayed 862,442, gold stayed 5000, and game time stayed 523531.
- Screenshots from Doom show the map with correct orientation and the location list (`review\fast-travel-menu\run\shots`).
- `bridge_stress` passes on protocol 3.
- No bridge: `DOOM.WAD` E1M1 runs clean. With the DRLA set it reports the same 3 script errors and 763 unknown-class lines as the previous build, so those are not from this work.
- A plain launch of the private Daggerfall copy logs no bridge activity and no exceptions.

## Known gaps

- **Doom's real window-to-surface mouse mapping is untested.** Minimized windows have no usable client area, so the test sends surface pixels directly. This is the first thing to check by hand.
- **The owner's registry key was not compared before and after.** Isolation rests on the portable install and patched product name, as in earlier runs.
- The Daggerfall window stays open behind Doom, and its size comes from its private settings (960x540). The `-screen-width` and `-screen-height` arguments had no effect, so the menu is upscaled in a larger Doom window.
- Doom's sound is not paused while a menu is open.
- `Input.anyKey` in the setup wizard and direct reads outside the window classes are not forwarded. This matters for the startup menu work.
- A `NullReferenceException` in `DaggerfallUI.SetupSingleton` appears in bridge test launches and not in the plain launch. The menu works despite it. Not investigated.

## Failed approaches

- A shadow `Input` class in the windows' namespace failed to compile, with ambiguous references. Replaced by direct calls in the 11 window files that read keys.
- The first frames were upside down on Direct3D. Fixed with `SystemInfo.graphicsUVStartsAtTop`.
- The test driver first matched any `uzdoom.exe`, so **early runs may have posted mouse moves and Esc to another UZDoom window** if a parallel lane had one open. It now targets only the PID from its own launcher log.
- Scripted clicks landed in the wrong place because Windows rescaled posted coordinates by the display's 2.25 DPI factor. The driver is now DPI aware.
- Early test screenshots used UZDoom's default folder, so a few may be in the owner's Documents `My Games` folder. Later runs use the private `run\shots` folder.

## Play-test list

1. Run `play.bat`, press K, and check that the cursor is visible and lines up with the map, including in a resized and a fullscreen Doom window.
2. Click a region, pick a location, and press Begin. Confirm Doom resumes with nothing changed.
3. Close with Esc, with K, and with the Exit button. Confirm Doom doesn't fire or move from the closing input.
4. Alt-Tab while the map is open and come back.
5. Type in the Find box.
6. Judge the menu's sharpness and how responsive it feels.

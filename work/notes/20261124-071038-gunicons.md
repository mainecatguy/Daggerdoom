# Fix: Doom guns show the wrong picture in Daggerfall's inventory (20261124-071038)

## Cause

`dd_items.cpp` `ArtFor` picks the picture Doom sends for a Doom item class. It uses the sprite Doom saw when the
player took that item (`seenArt`). If Doom never saw one, it walks the class's states and takes the first drawn frame,
trying the `Spawn` label first and `SpawnFrame` second.

Every DRLA weapon pickup inherits `Spawn` from `RLBaseWeaponPickup` (`DoomRL_Arsenal/actors/ArsenalRLWeaponPickup.txt`):

```
Spawn:      TNT1 A 0 ... Goto SpecialStartsStuff -> NoSpecialStartsStuff -> Goto SpawnFrame
SpawnFrame: PISG X 4      <- the pistol pickup sprite
```

A DECORATE `Goto` is resolved in the class that writes it, so in the static state chain that `Goto SpawnFrame` points to
the base class's own `PISG X`. A real actor reaches the gun's own frame (for example `PKCG X` for `RLChaingunPickup`)
only through the runtime `A_Jump(256, "SpawnFrame")`, which looks the label up on the actor's class. So the static
walk returned the pistol sprite for every DRLA gun pickup that Doom had not seen.

That explains why some guns were right and others wrong:

- A gun taken off the floor with Use was seen by Doom, so `seenArt` held its real sprite (the owner's combat shotgun).
- A gun Daggerfall got any other way showed the pistol: the starting gun Daggerfall adopts, and a gun put away by a
  hotkey (both stored as `RL<Gun>Pickup`, `DoomerfallGuns.zs` `PickupFor`). Every gun after a load or a restart also
  showed the pistol, because `seenArt` lives only in the running Doom.

## Fix

`ArtFor` now tries DRLA's `SpawnFrame` label first, then `Spawn`. `FindState` looks a label up on the most derived
class, so this finds the gun's own frame. Stock Doom classes have no `SpawnFrame` and behave as before.
`SpawnFrame` is DRLA's display-frame label on all its weapon pickups (hundreds of definitions), so the rule is general.

## Verification

Builds from this worktree: bridge (`bridge-doomitems`), launcher (`launcher-doomitems`), UZDoom (`uzdoom-doomitems`), and
the Daggerfall Unity CliBuild (`CliBuild result: Succeeded`). The "before" pictures used the UZDoom built at integration
`2ca87c1`. The "after" pictures used the same review folder with only `uzdoom.exe` rebuilt with the fix.

New test tool `tools/gun_icons/gun_icons.py` (based on `tools/hotkeys`), review folder
`D:\dev\DoomDaggerfall-loop\review\gun-icons`:

- `take LABEL`: Use takes six DRLA guns off the floor in Privateer's Hold (chaingun, combat shotgun, shotgun, plasma
  rifle, rocket launcher, modded pistol), then makes a synchronized autosave.
- `load LABEL`: loads that save in fresh copies of both games, so Doom has seen no gun. Daggerfall's `-dfdoomitemstest`
  writes each inventory picture to `review\gun-icons\<LABEL>\<take|load>\<class>.png`.
- `sheet` writes `review\gun-icons\compare.html` (all four rows side by side). `check` runs DOOM.WAD E1M1.

Results (logs in `review\gun-icons\run`):

23x15 is the pistol pickup sprite. I viewed `before\load\RLChaingunPickup.png` (a pistol) and
`after\load\RLChaingunPickup.png` (the chaingun). In the first "before" take run, DRLA X started the player with a
chaingun, which Daggerfall adopted as `RLChaingunPickup`. That is likely how the owner got a pistol-pictured chaingun.

Regression (`gun_icons.py check`, fixed UZDoom): DOOM.WAD E1M1 stock exit 0, 0 script errors, not fatal. With DRLA
exit 0, 3 script errors (the same three from the DRLA mods' own `translation` and `menudef` lumps seen in every
earlier run), not fatal. `-norun` exit 1337. The paired runs logged no fatal errors.

Not covered: Daggerfall Unity code is unchanged. Armor and other non-gun DRLA items were not re-pictured. They get
the same rule, and any that define `SpawnFrame` now use it.

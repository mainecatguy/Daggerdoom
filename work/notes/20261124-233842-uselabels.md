# NPCs say why they will not talk (run 20261124-233842)

Goal: when the player uses an NPC that will not open a dialogue, show the message Daggerfall shows, with Daggerfall
Unity's own text and rules. Done when a paired run shows an NPC refusing with Daggerfall's message on Doom's screen,
and a willing NPC still opens the dialogue.

## What Daggerfall Unity does when a static NPC will not talk

Read from `PlayerActivate.StaticNPCClick` / `ActivateStaticNPC` and `TalkManager.TalkToStaticNPC` / `TalkToNpc`:

| Case | Daggerfall Unity's response |
|---|---|
| Reaction to the player below -20 (faction rep + social group rep + biography + reaction mod), or the NPC already rejected the player once this session | Message box, text record 7205, "You get no response." (`TalkToNpc`) |
| First rejection: the greeting roll fails (`GetNPCGreetingRecord` sets `alreadyRejectedOnce`) | Message box with the NPC's rejection greeting (a random text from the greeting record) |
| Racial override suppresses talk (werewolf/wereboar beast form) | Message box with the override's text (`LycanthropyEffect.GetSuppressTalk`) |
| Too far away | Mid-screen "You are too far away." (already routed to Doom before this run) |
| A quest is listening on the NPC's faction (`QuestMachine.HasFactionListener`) | Nothing at all (silent return, with a TODO in DFU) |
| NPC carries a ShowText / ShowTextWithInput action (castle gate guard, Mantellan Crux) | Not talk: the action shows its text through the action system. Separate backlog item "Dungeon actions: dialogue". |
| Fade in progress | Nothing |

So every real refusal in Daggerfall Unity is a Daggerfall message box pushed by the activation itself.

## Plan

1. Check whether Doom's Use route already carries these message boxes to Doom's screen. `DoomerfallTalk` answers
   `NPC_USE_WINDOW` for any NPC in reach; Doom opens `DFB_UI_TALK`; `DoomerfallTalk.OpenWindow` runs Daggerfall's own
   activation, and `DoomerfallUi` keeps the menu open while any Daggerfall window is on top. A message box should
   therefore show inside Doom like the talk window does. No earlier run ever tested it (no `talk: top window after
   activation is DaggerfallMessageBox` line in any review log).
2. Build a paired test with a refusing NPC: `-dftalkrefuse` (test only, in `DoomerfallTalkTest.cs`) drops the player's
   social group reputations to -100 after the first talk window closes, so Daggerfall's own reaction check refuses
   from then on. The talk test also logs the text of any message box it closes.
3. Fix whatever the test shows is missing.

## Findings

**The refusal already works on current integration. No game code change was needed.** Daggerfall's own activation
pushes its message box, and the existing talk route (`DFB_UI_TALK`) shows any Daggerfall window inside Doom, not only
the talk window. Nobody had tested a refusal before, so the owner had no evidence of it. The test also proves that
Doom draws the box: uz.log `ui: Daggerfall opened menu 6 ... 127 frames shown`.

Paired run (`python tools/npc_refusal/refusal.py run final`, DRLA set, town start, Gothway Garden tavern, 4 NPCs pressed
twice each). From `review\npc-refusal\run\final\df.log`:

- Press 1, willing NPC: `talk: top window after activation is DaggerfallTalkWindow`,
  `talktest: talking to "Uthore Hearthsly" ... greeting "Hello."`
- `talktest: social group reputations set to -100, later NPCs should refuse`
- Presses 2-8: `talk: top window after activation is DaggerfallMessageBox`, `ui: menu 6 opened`,
  `talktest: message box "You get no response."`, `ui: menu 6 closed, reason 1`
- `RESULT talk windows 1, refusal message boxes 7: PASS`. The same result came from an earlier run (r4) on the first test build.
- Player.log has one exception, the known start-up `NullReferenceException` in `DaggerfallUI.SetupSingleton` (already reported).

E1M1 with no bridge (`refusal.py check`): stock exit 0, E1M1 entered, no script errors. With DRLA: exit 0, E1M1 entered.
The 3 script errors are DRLA's own lumps loaded against DOOM.WAD (`translation`, `menudef.monster`,
`menudef.skillmenu`). This branch makes no engine change.

### What changed

- `DoomerfallTalkTest.cs` (test only): logs the text of any message box it closes. New `-dftalkrefuse` flag: after the
  first talk window closes, social group reputations go to -100, so Daggerfall's own reaction rule refuses from then
  on. It works without `-dftalktest`, so the demo keeps windows open.
- `DoomerfallBridge.cs`: the existing one-line test hook also starts the component for `-dftalkrefuse`.
- `tools/npc_refusal/`: `refusal.py assemble|run|check` and `harness.zs`. It walks into the tavern and presses Use on
  each NPC twice.

### Test-data trouble (worked around, not fixed)

The review folders' bundled converter writes interiors without Daggerfall place keys. Current UZDoom treats those as
unreadable and rebuilds them with that same old converter, so building doors stall at "Opening..." (runs r2 and r3).
`assemble` now swaps in `D:\dev\DoomDaggerfall-build\housepickups-converter` (built from integration) and drops cached
interiors. This is the stale-cache problem the earlier oversights already describe.

### Gaps (Daggerfall itself is silent here, or this is outside the goal)

- **Walking townspeople:** Use on one sends `NPC_USE`, but Daggerfall finds no static NPC with that id and answers
  `NPC_USE_GONE`, so nothing shows. In Daggerfall they talk (`TalkToMobileNPC`), and the same refusal rule applies to
  them. Talking to them is unbuilt work, not a refusal, so it is raised as a question.
- **Faction listener NPCs** (`QuestMachine.HasFactionListener`, some named NPCs during the main quest): Daggerfall
  Unity returns silently, so Doomerfall stays silent too, following Daggerfall's rule.
- **ShowText action NPCs** (castle gate guards, Mantellan Crux): these belong to the backlog item "Dungeon actions:
  dialogue".
- **`NPC_USE_REFUSED`** (a load is running, or a Daggerfall window is already open): nothing shows. The player cannot
  reach this in Daggerfall itself.
- The first-rejection greeting and the werewolf beast-form text use the same message box route, but were not run.

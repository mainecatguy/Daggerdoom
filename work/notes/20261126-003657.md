# Level-up flow in Doom (20261126-003657)

Goal: Daggerfall's level-up message and window show in Doom, the player can finish them, and the new level and
attributes reach both games.

## What Daggerfall Unity does on a level-up (findings)

- In stock Daggerfall Unity skill use is tallied during play. **In a Doomerfall session most of that is gone**
  (verifier's finding, checked in code): Daggerfall's `WeaponManager` is disabled in a paired session
  (`DoomerfallPositionSync.cs`), and Doomerfall reports only Climbing uses from Doom (`DoomerfallClimb.cs`). So
  weapon skills, Hand-to-Hand, Critical Strike, Dodging (`EnemyAttack`), Running/Jumping/Swimming (`PlayerEntity`
  motor checks) and magic schools get no uses from Doom play. Uses made inside Daggerfall's own windows still count,
  by code: Etiquette/Streetwise in `TalkManager`, Mercantile in `DaggerfallTradeWindow`, guild training. The talk and
  trade tallies are not run-tested here. The manual says only this. Combat skill tallying is not part of this card;
  raised as a question.
- Skills only rise, and the level is only checked, in
  `PlayerEntity.RaiseSkills()`. It runs at most once per 6 game hours and is called from exactly two places:
  `DaggerfallRestWindow` (each rest/loiter tick) and `DaggerfallTravelPopUp` (end of a fast travel).
- When the level formula (`FormulaHelper.CalculatePlayerLevel`) is above the current level, `CheckForLevelUp` sets
  `ReadyToLevelUp` and posts `dfuiOpenCharacterSheetWindow`. The Oghma Infinium does the same with a 30 point pool.
- The character sheet then plays the level-up sound, raises `Level` by one and max HP by the per-level formula, and
  adds the **stats rollout**: a bonus pool (`FormulaHelper.BonusPool`, 4 to 6) spent with a stat button and the small
  up/down spinner beside it. Exit is refused with Daggerfall's "distribute your bonus points" message box until the
  pool is empty (or every stat is at max). On Exit the working stats become the player's stats.
- There is **no separate text message** in Daggerfall Unity for a level-up. The "message" is the sound plus the sheet
  opening by itself. Skill rises show Daggerfall's popup text ("Your X skill has improved") and a primary skill reaching
  100 shows the "master" message box; those come from the same `RaiseSkills` call.

## How this already maps onto Doomerfall

- `DoomerfallUi.AskForOwnWindow` already shows **any** window Daggerfall opens by itself (`DFB_UI_DAGGERFALL`, menu 7),
  forwarding Doom's mouse and keyboard. So the level-up sheet, the "distribute points" box and the skill/master
  messages need no new engine or bridge code.
- `DoomerfallSheet` republishes the sheet slot whenever a value changes, so the new level and stats reach Doom with no
  hook (Doom logs `sheet: read ... level N`).
- For a `DFB_UI_DAGGERFALL` menu, Doom never sends a close for the player's keys (`IsOpenMenuKey` returns false), so
  Doom cannot pop the sheet past Daggerfall's "spend your points" rule. Only Doom's error paths (no answer, peer
  stale) can close it; those already pop to the HUD for every Daggerfall window.

## Gaps found (not fixed; need the owner)

1. **Resting does not exist in Doom yet.** In play, the only thing that runs Daggerfall's skill and level check is a
   fast travel. A character that never fast travels never levels up (and its skills never rise). Rest is in the
   design (`gamedesign.md`, Resting & Loitering: Daggerfall owns it, blocked by nearby Doom monsters, interrupted by
   Doom ambushes) but has no card. Question raised.
2. **The level-up sound is silent.** Daggerfall's audio is muted for the whole bridge session (Doom owns sound;
   `DoomerfallNewGame` sets `AudioListener.volume = 0` except during character creation), so the fanfare that comes
   with the sheet is never heard. Same for every Daggerfall window's clicks. Question raised.

## Results

Natives were built from this worktree (`tools/levelup/build_native.py`, into `bridge-location`, `launcher-location`,
`uzdoom-location`) because the shared `D:\dev\DoomDaggerfall-build\bridge` DLL had another schema
(`923d08aa…` vs this branch's `d11fd6dd…`; the first run failed with "bridge DLL does not match this build").
No native source changed.

**Correction (after the verifier's review).** The first version of the test hook did not earn exactly one level: the
blank test character's starting skill sum is 0, so the formula already said level 3 or 4 (`earned level 1 -> formula
4 after 1 skill points`), which would have left further level-ups pending. The hook now recomputes the skill sum and
sets `StartingLevelUpSkillSum` so the formula equals the current level, then raises primary skills until it is
exactly level + 1 (`baseline level 1 formula 1`, then `earned level 1 -> formula 2 after 15 skill points`). My
earlier fast travel claims were also wrong and are replaced below; see "Withdrawn".

All runs below use the committed harness and DFU build with the fixed hook; logs are in `review/levelup/run`,
`run-travel` and `run-control` (each start: `+map DDT07154`, outside Privateer's Hold, DRLA, paired, minimized).

**Direct (`levelup.py run`): 5 passed, 0 failed.**

1. Daggerfall opened `DaggerfallCharacterSheetWindow` by itself (df.log "opened ... by itself, asking Doom"), Doom
   opened menu 7 (uz.log "Daggerfall opened menu 7 at 640x400"); sheet levelling, level 1 -> 2, pool 4.
2. Exit with points left: Daggerfall's message box, a click dismisses it, sheet still open with the same pool.
3. Clicking Strength then its up arrow 4 times through Doom's window: pool 0, working Strength 54.
4. Exit: menu closed, Daggerfall level 2, stats 54,50,...
5. Doom's copy of the sheet: `sheet: read ... level 2 str 54/54`.

**Fast travel (`levelup.py run travel`): 6 passed, 0 failed.** The level is earned, but only a real fast travel
through Doom's travel map runs Daggerfall's skill check (I'm At, region, location list row 3 = Aldcart, Yes, Begin).
uz.log: `travel: Daggerfall placed the player` at 119540.515, `Daggerfall asked to show a window it opened by itself`
at 119541.156, `Daggerfall opened menu 7` at 119541.296, so the sheet was in Doom 0.8 s after the arrival. Then the
same five checks as above passed (pool 5, Strength 55 in Daggerfall and in Doom's sheet).

**Control (`levelup.py run control`, same trip, no level earned, no test hook): 2 passed.** Doom kept running
after the arrival. In this run Doom's main thread was busy for about 40 s after the arrival (`travel: Daggerfall
placed` at 119393.900, next heartbeat at 119434.112), then carried on normally. A first control run that waited only
20 s took this for a freeze; the harness now waits 90 s.

Regression (`levelup.py check`, no bridge): DOOM.WAD E1M1 stock exit 0, entered, 0 errors; with the DRLA set exit 0,
entered, 3 script errors (DRLA's own `translation` and `menudef` messages, also in every paired run); `-norun` 1337.

Harness lessons: without Doom's `-dfuitest`, Windows' real-cursor moves on the private desktop overwrite the
driver's posted mouse position, so no click lands; `-dfuitest 0` filters them and opens nothing. Doom with DRLA can take
over 30 s to start cold.

### Withdrawn

Earlier versions of these notes, the harness docstring and commit 112e2453 said Doom froze leaving DDT07154 with or
without a level-up, and that this was pre-existing. That was not supported: the travel runs were cut off by a 20 s
wait (and a 90 s harness timeout in the first travel run), the "same trip" control log I kept was a later run that
started on DDOVER01 and never travelled, and the `DDSTITCH leave DDT07154` line I quoted came from a log I later
overwrote. With the committed harness, fast travel works and the level-up sheet shows after it. The 40 s busy arrival
seen in the control run is the only observation left; I did not investigate it (it fits the existing todo item about
long operations blocking the main thread).

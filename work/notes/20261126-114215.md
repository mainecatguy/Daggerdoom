## 1. Action records on doors

Daggerfall's rules (`DaggerfallAction.cs`): LockDoor (16) sets `CurrentLockValue = 16` if the door is not locked;
UnlockDoor (17) sets 0; OpenDoor (18) sets 0 and opens it if closed; CloseDoor (20) closes it if open and sets
`CurrentLockValue = StartingLockValue` (so a closed door relocks to its starting lock). Before this run, Doom moved the
door for 18 and 20 but never told Daggerfall, and 16 and 17 did nothing but count a diagnostic.

New bridge kind `DFB_KIND_DOOR_ACTION` (195, UZ to DF, `dfb_door.state` = the action type).

- `door_objects.zs`: `DFDoor.ActionSet` now returns whether the door started moving. New `DFDoor.TellLockAction(type)`
  sends `dfdoor_action:<LoadID>:<type>` (only when the map has LoadIDs).
- `action_objects.zs`: 16 and 17 on a record with a door call `TellLockAction`; 18 and 20 call it only when the door
  really moved. That stands in for Daggerfall's `IsOpen` check, because Daggerfall's own door model is hidden and never
  moves, so its `IsOpen` is always false. A record without a door keeps the old `DFActionRules.Request`.
- `dd_doors.cpp` relays the event as `DOOR_ACTION`.
- `DoomerfallDoors.OnAction` applies DaggerfallAction's rule to the live `DaggerfallActionDoor` and resends the locked
  list at once. Doom's lock state changes only from that list.

Without a bridge session the event reaches ZScript, which ignores it, so plain Doom and stock WADs are unchanged.

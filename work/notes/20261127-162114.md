# Skill point sound and message (skillmenu 02, run 20261127-162114)

Goal: when the player gains a skill point, Daggerfall's sound plays and Daggerfall's message shows, on Doom's screen.

## Findings

- **Daggerfall Unity's message:** `PlayerEntity.RaiseSkills` (the skill check that rest and fast travel run) shows
  `skillImprove`, "Your %s skill has improved.", through `DaggerfallUI.PopupMessage`. It already reaches Doom's HUD:
  `DoomerfallHudMessages` forwards every `PopupMessage` as `DFB_KIND_HUD_TEXT`, and Doom holds a line sent while a
  Daggerfall window is open until it closes (`dd_info.cpp`, `hudHeld`). No new message code was needed.
- **Daggerfall Unity's sound:** there is **none for an ordinary skill point**. The only sound in `RaiseSkills` is
  `SoundClips.ArenaFanfareLevelUp` (clip 32, 2.3 s), played with the "master" message box when a primary skill reaches
  100. The level-up sheet has its own `SoundClips.LevelUp` (clip 96, 3.8 s). Engineering call: use clip 32, the sound
  Daggerfall's own skill-increase code plays, so a skill point and a level-up stay distinguishable. It is one constant
  (`DoomerfallPerks.SkillPointClip`); question for the owner below.
- Daggerfall's audio is muted for the whole bridge session (`DoomerfallNewGame`), so Daggerfall cannot play it itself.
  Doom already loads Daggerfall's clips from `DAGGER.SND` for ambient one-shots (`dd_weather.cpp`, `ClipSound`).
- **Card 01 (Skill XP, the Skills menu) is not in this branch.** It is on `agent/skillmenu-20261127-140808`, not
  merged into this branch's base (`e56e5dcc`). This card does not depend on it: the sound comes from a watcher that
  sees every rise of a permanent skill value, whatever caused it, so bought points will get the sound once both are
  merged. A bought point does not show "Your X skill has improved." today (card 01's Buy shows only the master
  message at 100); see "Merge note".

## Plan (as run)

1. Daggerfall: `DoomerfallPerks` already watches permanent skill values every frame during play (no hooks in game
   classes; loads and new characters reset its baseline, so they never fire). Any frame where at least one skill rose
   sends the bridge text `uisnd 32` once, and logs `skill point: sound 32 sent to Doom` in the bridge log.
2. Doom: `dd_weather.cpp` parses `uisnd <clip>` next to `amb <clip>` and plays the clip as a UI sound (`CHANF_UI |
   CHANF_NOPAUSE`, no attenuation, full volume), logging `ui sound <clip> from Daggerfall` to the bridge log. The text
   only arrives over the bridge, so a plain Doom run never reaches it.
3. Test hook `DoomerfallSkillPointTest.cs` (`-dfskillpointtest <file>`, self-starting, own file): at the HUD, gives
   Climbing 20000 uses and runs `RaiseSkills` (round 1), then six seconds later Climbing and Running together (round 2).
4. Harness `tools/skillpoint/skillpoint.py` (assemble, run, run rest, run travel, check); natives from
   `tools/skillpoint/build_native.py`.
5. Manual: a paragraph in "Levelling up". Demo `review/skill-point/play.bat`.

### After the verifier's second review: fast travel

The verifier found (by code) that fast travel calls `RaiseSkills` before Doom loads the arrival map, and a map load
stops every channel (`S_StopAllChannels`, `S_Start`), UI sounds too, so the fanfare would be cut off. Fixes:

6. **Sound waits for the arrival.** `DoomerfallPerks` now marks the sound pending and sends it only when
   `DoomerfallPositionSync.TravelHolding` is false (new one-line read-only property). That hold is set by
   `OnPostFastTravel`, which `performFastTravel` raises in the same call right after `RaiseSkills`, and ends when Doom
   reports the arrival map pixel ("travel: Doom reached pixel"). A rest's check runs at the HUD, so its sound is not held.
7. **The message survives the arrival load.** Doom gets the HUD line when the travel menu closes, ~7 s before the
   blocking map load ends. The mod's HUD timer measured wall time between draws, so the first draw after the load
   stepped ~7 s and expired the line at once. Daggerfall's own `PopupText` counts down with `Time.deltaTime`, which
   Unity caps at the project's maximum timestep (1/3 s, `ProjectSettings/TimeManager.asset`). `Doomerfall.zs` now caps
   its step the same way, so lines are not eaten by a load (for every HUD line, as in Daggerfall).
8. Test hook mode `-dfskillpointtest <file> prime`: gives Climbing its uses, clears the six-hour wait and lowers health,
   without running a check, so a real Rest Until Healed or a real fast travel (driven through Doom's window as
   `tools/levelup` and `tools/rest` do) runs Daggerfall's own skill check.

## Failed approaches

- First test run: the hook raised Climbing 3 s after the HUD appeared, before the watcher had armed (Daggerfall's
  play phase), so no sound was sent; and the blank test character's skill sum turned that one point into a level-up,
  whose sheet stayed open and blocked round 2. The hook now waits for the play phase and lines the level formula up
  with the current level first (as `DoomerfallLevelUpTest`). In real play, points come only from rest and travel,
  long after the watcher arms.
- The first version sent the sound as soon as a skill rose. On fast travel that is before the arrival load, which
  stops it (verifier, by code). Replaced by the travel hold above.
- My first rest check required Doom's `ui: closed` line before the `ui sound` line; Doom handles both in the same pump,
  sound first, in the same millisecond. The check now tests the real claim (Daggerfall sends it after the message
  closed and the HUD is back; Doom plays it within 0.1 s of the close).
- A screenshot after arrival by posting F12 to Doom's window: no screenshot was taken (Doom's in-game keyboard reads raw
  input). Dropped.

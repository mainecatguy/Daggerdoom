# Bridge version check fix (Q&A item 64)

## What was broken
`bridge/test/check_bindings_drift.py` had a hard-coded case that looked for `DFB_PROTOCOL_VERSION 4u`. The header is
at 7, so the case found nothing and the whole drift check always reported FAILED.

The runtime checks were not affected: `dfb_attach` and Daggerfall's `DefinitionMismatch()` already compare against the
header's value (C# through the generated bindings).

## Change
- `check_bindings_drift.py`: the version case now reads the current version from the header and bumps it by one, so it
  cannot drift again. It also requires the log line to name both versions. The unchanged-copy line now says PASS/FAIL.
- `generate_bindings.py --check` (runs in every bridge, UZDoom and launcher CMake build): when the versions differ, the
  STALE line now says so. Pass/fail behavior is unchanged.

## Verification
- `python bridge/test/check_bindings_drift.py`: unchanged copy and all 10 cases PASS, exit 0.
- `python bridge/generate_bindings.py --check`: up to date, exit 0.
- Scratch copy of `bridge/`, built with CMake (VS 18 2026, Release):
  - matching: build exit 0; `bridge_stress.exe` exit 0, including "wrong protocol version is refused".
  - header bumped to 8 without regenerating: build exit 1 with
    `bridge bindings are STALE (protocol version mismatch: header 8, generated bindings 7): ...`

UZDoom, Unity and the games were not rebuilt or launched: no game source changed. Nothing visible to play, so no demo
and no play-test list.

## Result

`python tools/visual_parity/menus.py [--seed N]` opens the same five windows (inventory, travel map, map, quest
journal, rest), in a seeded order, with the same place, facing and game time on both sides, and writes matched

## What changed

- `menus.py` reads the paired session's place and time from its `df.log` after the windows have been shot: `gps` and
  `pixel` from the last sync line, and the game minutes from the first "ui: world before" line, which Daggerfall
  Unity writes only when a window opens. It also gets the Doom facing from the QA bot, and passes all of them to the
  capture job. It warns if any of them is missing. (The first version of this run read `df.log` right after sync,
  before any window had logged the minutes. So no `time` line reached the job, and the earlier "time matched" claim
  was wrong. The verifier caught this.)
- The visual-parity Doom harness (`tools/visual_parity/doom`, test-only, loaded only by these scripts) has a new
  CVar `vp_noguns`, which `menus.py` sets. In the first second of the map it takes the player's ammo and pistol, so
  Daggerfall's inventory gets no Doom bullets (verified: `VPTAKE Clip x60` and others; "inventory before: Iron
  Longsword, Steel Dagger, Steel RLPistolPickup"). The pistol still gets adopted. Taking it for 15 seconds (224
  removals) did not stop that, because Doom gives the starting pistol back. No game code changed.
- `--user-desktop` (added by the first run as a diagnosis switch) is removed from `menus.py` and `common.py`. The
  menu capture works on the private desktop, so nothing needs the owner's desktop. Before this, the capture player
  stood in Daggerfall city (207,213), while the paired session was in the town outside Privateer's Hold (109,158).
  Verified: `MENUSTART pixel 109 158 location Privateer's Hold`.
- Capture player (`DungeonCaptureMenus.cs`, test-only, `-dfcapture`): new `world`, `yaw` and `time` job lines; VSync
  off with a 60 fps cap (as `DoomerfallSyncTest` does); the UI read after the end of a frame (bounded wait);
  OnGUI event counts and a step trace (`df_steps.txt`) for diagnosis; a fallback that draws the top window itself if
  the GUI pass left the texture empty (never needed, so untested).
- `common.py` copies the play folder's Expanded Inventory art into the capture install, so Daggerfall Unity uses the
  same inventory window as Doomerfall. Doomerfall has the mod built in, and it is active only where its art is
  installed (`ExpandedInventory.cs`).

## Failed approaches and what is still unexplained

- `hidden_desktop.py`: ran the capture player unminimized on a further unseen desktop. It did not help. With the old
  build the UI stayed empty; with the next build the player hung. Removed (commit 6d977cf7).
- A middle build reported `gui none` (no IMGUI events at all) and hung in its first shot, minimized or not. The next
  build added only the step trace and fixed a compile error, and it got Repaint events and worked in three runs.
  So I can't say which change fixed the empty UI layer. The likely candidates are VSync off plus the frame cap, or
  reading after the end of the frame. The hang may have been a stale build (one of the builds failed to compile, and
  the run could have used an older player). Not proven.
- Doomerfall's black menu shots from the first run did not come back. The paired game, the play folder and the
  Doom commands were unchanged, so the cause is unknown. The first run's guess (the screenshot misses the bridge's 2D
  layer) is wrong: the shots now include it. If they turn black again, compare the paired Daggerfall Unity's frames.

# Door locks in the location record (run 20261126-150155)

Goal: keep every door lock change (picks, lever unlocks, relocks) in the location record's door fact instead of the
separate `DoomerfallDoors.json` ledger, and fix card 04's reviewer flag (a loaded save whose doors were never armed).
Review: `20261126-lockpick-review.md`. The rejected separate store of `agent/lockpick-20261126-135825` is not reused;
only its paired harness cases (pick / lever / relock, per-case log names) were ported.

## Plan

1. Door fact: write the live locks beside the open bits in `DFDoorHandler.Distill`, read them in `Restore`.
2. Remove the ledger and the `DFB_DOOR_FACT` path; Daggerfall still arms a freshly built map (`DFB_DOOR_ARM`).
3. The arrival autosave must also wait for the place record, since it now carries the locks.
4. Loaded save with unarmed doors: ask for the arm again; the arm never touches armed doors.
5. Doom-only harness (record round trip, save/load arm check), paired pick/lever/relock take+load, entry, New Game,
   stock check.

## Design

### The door fact (door_objects.zs)

Before: `"<stamp> <hex open bits>"`. Now, once the doors are armed: `"<stamp> <hex> L<i>.<lock>,<i>.<lock>"`, listing
only doors whose live lock differs from their starting lock (index in the same order as the open bits). `L` alone means
"armed, every door at its starting lock". No third field means the locks were never armed (no Daggerfall answer yet);
old records also look like that, so they still read.

- Why a sparse list instead of one "unlocked" bit (the review's wording): a lever can also *lock* a door that starts
  unlocked (action 16 gives 16), and action 20 restores the starting lock, so a door has three possible states, and the
  Lock spell will later add arbitrary values. A sparse list stores all of them and is empty in the usual case.
- `Restore` with a lock field arms every lockable door at its starting lock, then sets the listed ones. The record is
  newer than the starting lock, so it wins whether Daggerfall's arm arrived before it or after it (the arm only sets
  doors not yet armed).
- A record made before the arm leaves the live locks alone.

Picks, lever unlocks and relocks need no per-change message: they change Doom's live lock, and the record is distilled
on leaving and with every save, like the open state.

### Daggerfall (DoomerfallDoors.cs, DoomerfallSave.cs)

The ledger (`LedgerData`, `DoomerfallDoors.json`, `WriteLedger`/`ReadLedger`, the picked list in `OnLockpick`) is gone.
On Doom's request Daggerfall sends only `DFB_DOOR_ARM`. The location record (DoomerfallLocations) keeps the door fact as
opaque text, so it needed no change. `DFB_DOOR_FACT` was removed from the bridge header and bindings regenerated.

Old saves with a `DoomerfallDoors.json`: the file is ignored, so doors picked under card 02 come back locked. Card 02 was
never on `main`, so I did not write a migration.

### Setup gate (dd_locations.cpp)

`DD_LocationsEntered` registers `place` with the gate, and it is done when the record is applied (or Daggerfall has none,
or the 5 s wait runs out). Without this, the dungeon-entry autosave could land between the arm and the record and save the
picked door locked; a load never re-applies the record (the snapshot stands).

### Card 04's reviewer flag (door_objects.zs WorldLoaded)

On a loaded save, if any lockable door is not armed, the door handler sends `dfdoor_facts` again. Daggerfall answers
with the arm, which sets only unarmed doors, so a save's live locks are never overwritten. Without a bridge session
nobody answers. Known gap: if that save was also made before the place record arrived (both Daggerfall answers missed
for 5 s), lock changes from earlier visits to that dungeon are not recovered, because the save's own report already
replaced Daggerfall's record with the unarmed one.

### Card 04's flag: how it is detected (a failed approach first)

First try: set a flag in `WorldLoaded` when `e.IsSaveGame`, and send `dfdoor_facts` from there or on the next tic. The
Doom-only save/load check showed no request: on a save load the handler that receives `WorldLoaded` is replaced by the
copy deserialized from the save, so neither the event nor a transient flag survives (the harness's own handler showed
the same: its timer was never reset). Working version: a transient `ticked` field, false again on any loaded copy; the
first `WorldTick` with `level.maptime > 1` (not a fresh map, which already asked in `WorldLoaded`) sends `dfdoor_facts`
if any lockable door is unarmed.

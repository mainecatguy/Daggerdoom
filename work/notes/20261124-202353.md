# No debug messages on screen in normal play (run 20261124-202353)

## Problem

UZDoom's plain `Printf` (PRINT_HIGH) goes to stdout, the `+logfile` log, the console, *and* the notify lines at the top
of the screen. Doomerfall's diagnostics (DDTM, DDENC, DDMON, DDTOWN, DDSTITCH, DFMesh, `[bridge]`, ...) and the mod's
`Console.Printf` lines (`Doomerfall: loaded ammo ...` on every weapon switch, `DFCLIMB ...`, `DDWAR ...`,
`Doomerfall: action fired ...`) all used it, so they showed on screen in normal play.

## Approach

UZDoom already has the flags needed: `PRINT_NONOTIFY | PRINT_NOCONSOLE` still writes to stdout (`-stdout`) and the
`+logfile` log, but not to the console buffer or the notify lines (`c_console.cpp` PrintString). Tests read stdout or
the log file, so they keep working.

- New CVar `dd_debugmessages` (bool, default off, `CVAR_NOSAVE` so it never sticks in an ini). Turn it on with
  `+dd_debugmessages 1` on the command line (or `--uzdoom-arg +dd_debugmessages --uzdoom-arg 1` through the launcher), or
  type it in the console.
- Engine: `UZDoom/src/playsim/dd_log.{h,cpp}`: `DD_DebugPrintf(...)` and `DD_DebugLevel()`. Every Doomerfall diagnostic
  `Printf("DD...")`/`Printf("DF...")` in the dd_* files and `hw_dfmesh.cpp` ("DFMesh: ...") now goes through it
  (76 calls), and the bridge's `Log()` (`[bridge] ...`) uses `DD_DebugLevel()` for its console copy (its own
  `-dfbridgelog` file is unchanged).
- Mod: `mods/doomerfall/src/zscript/DoomerfallLog.zs`: `DDLog.Debug(String)` with the same rule (via
  `Console.PrintfEx`). Converted: `Doomerfall: mod loaded`, `action fired`, `unknown action`, `loaded ammo`, `DFAMMO`,
  `DFCLIMB`, `DDWAR`.
- Converter: `CityExport.cs`'s generated runtime script (`ddruntime.pk3`) printed `DFGATES spawned N leaves` on every
  town load and `DFCITY: N billboards`; both now use the same CVar check inline (the runtime pk3 loads before
  doomerfall.pk3, so it cannot call `DDLog`).

Left alone on purpose:
- Player messages (`You take ...`, `Save failed ...`, `Opening...`, `Climbing`, `Daggerfall cannot open that menu here.`,
  `A save is already in progress.` ...).
- `PRINT_LOG` lines (`doomitems: ...`, dd_info's HUD text copy): already log only.
- Output of console commands the player types (`dfmesh_status`, `dfmesh_bench`, the mesh view toggle).
- Test-only code that runs only behind a test flag (`dd_encounter_test.cpp`, `dd_facetest.cpp`, `dd_qa.cpp`, the
  `*Test.zs` handlers, the item gallery map's `DFITEMS`, smoke-src, tools/ harnesses). The rule allows output behind a
  special flag, and those flags are that.
- Daggerfall Unity side: its HUD messages sent to Doom (`DoomerfallAmmo.Hud`, hotkey messages) are player messages.

- Converter's dungeon runtime (`action_objects.zs`, `door_objects.zs`): `DFACTIONS`, `DFFLATOUT`, `DFDFLATS`,
  `DFDLIGHTS`, `DFDOORS`, `DFRULE` printed on every dungeon load. Found by the first console screenshot (below), gated
  inline the same way. The converter copies these files verbatim into the startup pk3s (`privateershold_doors.pk3`,
  `ddruntime.pk3`); runtime-converted caches carry only data lumps, since ZScript loads only at startup.

## Verification

Build: `cmake --build D:\dev\DoomDaggerfall-build\uzdoom-encounters --config Release` (that tree is configured from this
worktree). Demo and checks: `python tools/debug_messages/debug_messages.py assemble | solo | e1m1`.

- `assemble` copies review\cleanlaunch (same bridge layout: its DLL postdates the last bridge header change), drops
  in this build and doomerfall.pk3, and gates the generated runtime scripts in the startup pk3s with the same text
  change the converter now makes (ddruntime 2 lines, privateershold_doors 5). I did not rebuild the converter itself:
  the CityExport.cs change is inside a verbatim string, and the .zs files are read at conversion time.

    still listed DFDOORS/DFFLATOUT/DFDFLATS/DFDLIGHTS/DFACTIONS (converter runtime, fixed above).
  - after the fix: with the option off, the open console shows only engine startup and the map title

  - `tools/demo_combined/retarget.py review\no-debug-messages tools/ammo/ammo.py take` (paired, both games, reads

  - `tools/climb/run_test.py` (reads `DFCLIMB` from stdout), wrapped in quiet_run: 14/14 passed.
- Not run: a full play.bat New Game session through shops, doors and town by hand (needs a person; on the play-test
  list), and the many other harnesses, which read the same stdout/log paths the two above prove.

## How to turn it on

`+dd_debugmessages 1` on UZDoom's command line (launcher: `--uzdoom-arg +dd_debugmessages --uzdoom-arg 1`), or
`dd_debugmessages 1` in the console. It is not saved to the ini, so it is off again at the next launch.

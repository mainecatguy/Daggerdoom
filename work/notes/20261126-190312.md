# Show damage numbers option (2026-11-26, run 20261126-190312)

## Goal
A "Show damage numbers" option in Doom's options menu: hitting an enemy shows a small number over its body. Off by
default, on by default in a dev launch, works without Daggerfall, stock Doom still starts.

## Does it already exist?
No. Searched the extracted DRLA Arsenal, DRLA Monsters, DRLAX (and the other extracted mods) and their CVARINFO for
damage / number / popup settings, UZDoom's `wadsrc/static/zscript` for any damage-number or screen-projection code, and
the Doomerfall mod. Nothing. So it is new, in the Doomerfall mod only (pure ZScript, no engine change).

## What was built
- `mods/doomerfall/src/zscript/DoomerfallDamageNumbers.zs`: a StaticEventHandler.
  - `WorldThingDamaged` records hits on monsters (`bIsMonster`) whose damage source is a PlayerPawn (direct hits and
    the player's projectiles). Hits on the same monster in the same tic add up into one number (shotgun pellets).
    Capped at 64 live numbers; each lives 30 tics. Display only: nothing in play changes. Static handler, so nothing
    goes into saves; the list clears on level load/unload.
  - `RenderOverlay` projects the monster's top (it follows the monster while it exists, interpolated with FracTic) to
    the screen with the hardware renderer's own projection: pixel stretch on heights, pitch adjusted to match
    (`r_utility.cpp`), vertical FOV from the horizontal one over 4:3 (`hw_entrypoint.cpp`), viewport from
    `Screen.GetViewWindow()`. Gold SmallFont with a dark shadow, rises 24 pixels (scaled) and fades. Size is two steps
    under Doomerfall's other labels (`DoomerfallText.Scale() - 2`, 3x at 1280x800), so `dd_hudtextstep` still scales it.
- `CVARINFO.txt`: `nosave int dd_damagenumbers = -1` (client-side, archived) and `nosave noarchive bool dd_dev`.
- `MENUDEF.txt`: `AddOptionMenu "HUDOptions"` appends "Show damage numbers" (On/Off) to Options > HUD Options, as a
  `DDDamageNumbersOption` (Doom's On/Off option, subclassed so that while no choice is made it shows the launch's
  default instead of "unknown").
- Dev flag: there was no existing dev flag (the play folder passes `-dfflow`, bridge log paths, etc., all functional).
  Added `+dd_dev 1`; `scripts/play/install.py` now passes it, so the owner's play folder is a dev launch after the next
  install. dd_dev is never saved.
- Default logic (revised after verifier review): `dd_damagenumbers` stays -1 ("no choice") until the player picks On
  or Off; the effective value is `value < 0 ? dd_dev : value` (`DoomerfallDamageNumbers.Shown()`), worked out every
  time it is read. The launch's default is never saved, so one config can serve normal and dev launches and each gets
  its own default. Options > Reset to defaults (`reset2defaults`) sets it back to -1, and it then follows the launch
  again at once. The first version wrote 0/1 into the config on the first UI tic; that saved the default as if it
  were a choice, and a reset left the option at -1 showing nothing and "unknown" in the menu until restart.
- `manual.md`: a short "Damage numbers" section.

## Judgment calls (ordinary engineering, within the owner's request)
- Only the player's hits show numbers, not monster infighting: in slaughter-sized packs infighting would cover the
  screen, and the owner asked for "how much damage they took" when hit, which reads as the player's hits.
- The number is the damage the engine reports to event handlers (after Daggerfall multipliers and the target's own
  damage factors), including overkill on the killing hit.
- Numbers are drawn over walls (no occlusion test); they only appear for hits you landed, so this rarely matters.
- There is no "Default" entry in the menu: it shows On/Off as currently in effect. Once changed, the only way back to
  following the launch is Reset to defaults (or `resetcvar dd_damagenumbers`).

## Verification (all through quiet_run, private configs, UZDoom from the play folder, no engine build needed)
`tools/damage_numbers/damage_numbers.py` runs UZDoom alone on DOOM.WAD E1M1 with a fresh doomerfall.pk3 and a test-only
harness (`tools/damage_numbers/harness.zs`) that holds a zombieman 200 units away, 22 degrees off centre, and hits it
with the player as source, then takes screenshots (shot a during hits, shot c after they faded).
Each run checks the stored value, whether numbers show, what HUD Options displays, and what the config holds after
quitting (never `dd_dev`, and `dd_damagenumbers=-1` unless a choice was made). Final results after the revision:
- `run dev --dev` (DRLA): stored -1, shown, menu On, three same-tic hits summed to 21, shot a shows gold numbers
  rising over the monster, shot c none. PASS.
- `run normal`: stored -1, not shown, menu Off, no numbers in shot a. PASS.
- `run off --dev --set 0` and `run on --set 1`: explicit choices win over the launch's default. PASS.
- `run resetdev --dev --reset` / `run resetnormal --reset`: a choice opposite to the default is made mid-game
  (menu flips), then `reset2defaults`; the value goes back to -1 and the menu and numbers follow the launch again
  (On in dev, Off in normal) in the same session. PASS.
- One config, no choice: `run cross1` (normal, Off) then `run cross1 --keep-config --dev` (On); `run cross2 --dev`
  (On) then `run cross2 --keep-config` (Off). PASS.
- `run chosen --dev --set 0` then `run chosen --dev --keep-config --expect 0 --expect-stored 0`: a choice is kept. PASS.
- `run stock --stock --dev` (no DRLA): shown. PASS.
- `check`: `-norun` exit 1337 on DOOM.WAD stock, with DRLA, and with DRLA + doomerfall.pk3. PASS.
Screenshots are in `D:\dev\DoomDaggerfall-build\damage-numbers\<run>\`.

Failed approaches / test pitfalls (for the next agent):
- A DORMANT monster takes no damage at all (DamageMobj returns early), so no event fires. The harness freezes it by
  resetting its position instead.
- UZDoom's `logfile` takes a name, not a path (`log-<name>.txt` in the working folder); absolute paths fail with
  "Could not start log". The runner reads `-stdout` instead, which arrives line by line.
- On the private desktop frames render rarely, so a screenshot can land seconds after it is asked for. The harness
  keeps hitting until the runner sees the PNG on disk and acknowledges it (`set dn_ack N`).
- The private desktop renders at 320x200, so screenshots are small; the projection was checked there only.

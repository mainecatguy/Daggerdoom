# ammoicon: the loaded ammo's coloured HUD icon, and a notice on ammo change (2026-11-27 run 175653)

Goal: the HUD's ammo symbol shows the loaded tier's icon in its tier colour, and changing ammo pushes a top notice.
Done when, in a paired run, loading Silver, Daedric, then Regular bullets changes the icon each time and shows a top
notification each time. **Met:** `tools/ammoicon/ammoicon.py paired` passes all three presses (log and screenshots).

## Plan, and what I found

1. **The notice already existed.** `DoomerfallAmmo.cs HandleChange` calls `DaggerfallUI.AddHUDText("Loading Silver
   Bullets.")` on the Change Ammo control, and `hudmessages` 01 forwards every `AddHUDText` to Doom's top message area.
   The automatic change says "Out of ammo: loading X." the same way. No Daggerfall change was needed; the paired run
   shows the line arriving in Doom for each press (engine log, and `notice-*.png`).
2. **Which "symbol"?** Doom's HUDs draw an ammo item's own `Icon` (`shared_sbar.cpp GetInventoryIcon`). DRLA's
   fullscreen HUDs (SBARINFO `ammoicon2`), stock Doom's HUDs and the alternative HUD draw the reserve ammo's icon,
   the generic clip/shell/rocket/cell. But DRLA's **default status bar** (screen size 10, `statusbar.txt`
   "statusbar normal") draws no ammo icon at all: its ammo box has the word "AMMO" painted into the background
   graphic (RLZHUD1). On a fresh install that bar is what the owner sees, so I read "the symbol" as that word, and
   covered both:
   - **Every HUD that draws ammo icons:** `DoomerfallAmmoTiers.TickIcons` (DoomerfallAmmo.zs) gives the player's
     reserve item of the loaded type the tier's icon each tic, and puts every other reserve item back to its class
     icon. Checked every tic because Doom makes a reserve item afresh when that ammo first arrives.
   - **DRLA's default bar:** `DrawBarIcon` (in the existing `RenderOverlay`) covers the word AMMO with the loaded
     tier's icon, in the bar's own 320x200 coordinates (`Screen.VirtualToRealCoords`, the same 4:3-centred mapping as
     SBARINFO's `forcescaled`; measured in a 1252x721 shot before and after). Only when screen size <= 10, DRLA's
     RLZHUD1 graphic exists, and the player has no `RLSpecialHUD` (DRLA's other bar).
3. **The icons:** `mods/doomerfall/src/TEXTURES.ammoicons`, 40 graphics `DFAI<C|S|R|E><tier>`, each the stock pickup
   sprite with the tier's translation. Generated by `tools/ammoicon/make_textures.py` from TRNSLATE's `DFAmmoTier<n>`
   strings, so the icon colours always match the pickups and the existing overlay. TEXTURES patch translations accept
   the same `%[..]:[..]` desaturated ranges (`multipatchtexturebuilder.cpp` -> `AddToTranslation`). No engine change.
4. Everything runs only when Daggerfall's rules are active (`rules`, set by `dfi_rules:1`) and a tier is loaded.
   Stock Doom and the DRLA set in E1M1 keep stock icons (`ammoicon.py check`).

The existing overlay above the ammo box (tinted icon + "Silver Bullets", ammotiers/05) is unchanged. With the icon now
in the box it is partly redundant; I left it because removing it was not asked (question below).

## Failed approaches and snags

- The worktree's own `daggerfall-unity-master/Builds/Windows64` was built from other source (bridge schema f3f7...,
  this branch's source is 38b1...), so the launcher refused it; the tool uses the batch7 stage's matching build.
- Minimized launches render at 320x200, too small to see the icon; the paired run is unminimized with a set window
  size, as `tools/hud_messages` does (still on the private desktop).
- `FindInventory("RLSpecialHUD")` with a literal class name failed to compile without DRLA (caught by the stock E1M1
  check); it is now looked up at run time.

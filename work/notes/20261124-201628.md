# flatcollision: Daggerfall sprites keep their original collision (run 20261124-201628)

Result: **BLOCKED on an owner decision.** The research is done and a census tool is in place. The collision change
itself is not built, because the rule the card asks to match doesn't exist in the way the card assumes.

## Plan

1. Find where Daggerfall decides which flats are solid: data flags, Daggerfall Unity code, and classic behaviour.
2. List the solid flats, then give them Doom collision in dungeons, interiors and towns.
3. Test blocking in all three, and check that regular WADs are unaffected.

Steps 2 and 3 stopped after step 1. See Findings.

## Findings

### 1. Daggerfall's data has no "solid" flag for flats

- RDB (dungeon) flat records hold texture, flags, magnitude, sound index, faction/mobile id, next object and action
  (`daggerfall-unity-master/Assets/Scripts/API/DFBlock.cs:1025-1065`, `RdbFlatResource`). The flags field is described
  as "Flags for action, NPC, etc.". Nothing marks a flat as solid.
- RMB (interior and town) flat records hold only position, texture, faction id and NPC flags
  (`DFBlock.cs:453-481`, `RmbBlockFlatObjectRecord`).
- `ARENA2/FLATS.CFG` maps flats to NPC faces. It has no collision data.

### 2. Daggerfall Unity makes no flat solid

- `DaggerfallBillboard.cs:345-352`: NPC flats get a BoxCollider with `isTrigger = true`. A trigger never blocks movement.
  It only catches clicks.
- `RDBLayout.cs:994-1000` and `GameObjectHelper.cs:323-330`: flats with actions get a trigger BoxCollider "for
  raycasting". Again it doesn't block movement.
- No other collider is added to any billboard in `Assets/Scripts`. Nature billboards are batched with no colliders
  (searched: no tree, nature or billboard collider anywhere).
- The converter already follows this on purpose: `tools/dungeon_converter/action_objects.zs:32` says "An ordinary
  Daggerfall billboard. It has no collision, as in Daggerfall Unity." `DFCityFlat`, used for town and interior flats in
  `CityExport.cs`, is `+NOINTERACTION +NOBLOCKMAP` too.

So in Daggerfall Unity a brazier in a corner can be walked through, the same as on our converted maps today.

### 3. Classic Daggerfall: not confirmed

I couldn't find a primary source on classic collision with flats. The dfworkshop forum refuses automated fetches
(403), and FALL.EXE can't be tested here. One forum search result describes classic nature sprites as intangible,
meaning you walk through trees. My unverified recollection is that classic flats are walk-through too. Daggerfall
Unity normally aims for parity with classic, which also points that way.

**Conclusion:** I can't find a "Daggerfall rule" that makes braziers solid. Daggerfall Unity has none, classic seems to
have none (unverified), and the data has no flag. The card says to report rather than choose when the sources disagree
or are missing, so making some flats solid needs the owner's list. See the question.

### 4. Census of every flat picture placed in Daggerfall's blocks

## How it would be built once the list exists (no engine change needed)

- Dungeons: `DFDungeonFlat` in `action_objects.zs`. Interiors and towns: `DFCityFlat` in `CityExport.cs`
  (RuntimeScript and CityScript). Each of these knows its texture name (`dfflat/aNNNrMM.png`) and scale when spawned.
  A ZScript table of solid archive:record pairs would clear `NOINTERACTION`/`NOBLOCKMAP`, set `+SOLID`, a radius of
  about a third of the drawn width (capped), and the drawn height. Only flats whose bottom is near the floor would be
  made solid, not hanging ones.
- Town and interior flats come from the runtime asset package, so that package must be rebuilt. The DFDFLATS and
  DFFLATS lump formats stay the same.
- Nothing changes for regular WADs: the classes exist only in converter-generated packages.
- Packs: a solid flat in a 1-cell corridor would block monsters. The converter's reach tools (`reach_all.py`) could
  report doorways and corridors a solid flat narrows below a monster's width. The card asks to report those rather than
  choose.

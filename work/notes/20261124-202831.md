# Doom movement keys pan Daggerfall's map screens (run 20261124-202831)

## Plan

1. Doom side (`UZDoom/src/dd_bridge.cpp`, `MapPanKey`): while Daggerfall's map menu (`DFB_UI_MAP`) or travel map
   (`DFB_UI_TRAVEL_MAP`) is open, a key whose Doom binding is exactly `+forward`, `+back`, `+moveleft` or `+moveright`
   is forwarded to Daggerfall as Up, Down, Left or Right arrow instead of itself. The binding is read from Doom's
   `Bindings` at each key press, the same way the menu's own close key is found (`IsOpenMenuKey`), so rebinding in
   Doom's Customize Controls works at once. No bridge header change, so no layout hash change.
2. Daggerfall's dungeon/interior automap and town (exterior) automap already pan with the arrow keys
   (`DialogShortcuts.txt`: AutomapMove*/ExtAutomapMove* = arrows). Nothing to change there.
3. The travel map has no keyboard panning at all. Nearest equivalents, added in
   `DaggerfallTravelMapWindow.PanWithKeys` (active only while a Doom menu feeds input, `DoomerfallInput.Active`):
   - region view, zoomed (right-click): held keys pan the zoomed view (120 native px/s), clamped to the map edges;
   - region view, not zoomed: a press steps to the neighbouring part of a region drawn on several maps, exactly like
     the on-screen arrow buttons;
   - world (province) view: nothing pans; it is one fixed picture. The keys do nothing there.

## Why this design

- Translating in Doom keeps the "which keys" decision with Doom's bindings (owner decision) and needs no new bridge
  message. Daggerfall's map code keeps using its own arrow shortcuts, so modifiers keep Daggerfall's meanings
  (for example Shift+forward = Shift+Up = rotate the 3D automap camera up).
- The raw key is replaced, not sent alongside, so a movement key never also triggers some Daggerfall shortcut.
  Typing (automap notes) is unaffected: characters travel as separate WM_CHAR input.
- Doom is paused behind every Daggerfall menu and the window procedure consumes the keys, so the player cannot move.

## Known gaps

- Only keyboard keys are translated. A mouse button or gamepad stick bound to movement (e.g. `mouse3 +forward` in
  the original bindings, `lstickup +forward`) does not pan.
- A binding that combines commands (e.g. `+forward; something`) is not recognised; only the exact command.
- In the 3D dungeon automap view, "forward" moves the camera forward (Daggerfall's own meaning of its forward key);
  in the 2D view it moves the view up.
- Zoomed travel map panning stops at the edge of the current map part; it does not continue into the next part.

## Results

Harness: `tools/map_keys/mapkeys.py` (assemble | default | rebound | check), test folder and demo in
`D:\dev\DoomDaggerfall-loop\review\mapkeys` (`play.bat`). One paired session per binding set, DRLA loaded, start
outside Privateer's Hold (DDT07154). The bridge's `-dfuitest` opens, through the real commands, the town's exterior
automap, the travel map, then (after the harness walks through the dungeon door) the dungeon automap. Key presses
are real WM_KEYDOWN/UP posted to Doom's window, so they go through `DD_BridgeUiWndProc` and `MapPanKey`.
Daggerfall's `-dfmapkeystest <file>` (`DoomerfallMapKeysTest.cs`, starts itself from the flag, with no hook in a game
class) logs each map view: the automap camera position, or the travel map's region, part, zoom and zoom centre.

- `default` (W S A D): **12 passed, 0 failed** (`review\mapkeys\run\default\`). Exterior automap camera: W z -2.9 to
  45.8, S back to -4.0, A x to -52.5, D back to -3.1. Dungeon automap camera: W z -7.6 to 14.5, and so on. Travel map
  zoomed: S y 113, W y 54, D x 140, A x 82. Doom's player position is identical before each menu opened and after it
  closed (MKPOS lines). Daggerfall only ever held arrow keys, never W/A/S/D.
- `rebound` (`unbind w; bind i +forward`): **15 passed, 0 failed** (`review\mapkeys\run\rebound\`). I pans every
  screen, and W, once unbound, pans none of them (Daggerfall receives a plain W, which the maps ignore).
- `check`: DOOM.WAD E1M1 stock exit 0, no errors; with the DRLA set exit 0 and 3 script errors ("translation" line 1
  and two DoomRL_Monsters menudef lines). An older UZDoom (`review\doom-items\uzdoom`) gives the same 3, so they come
  from the mod data. Bridge lines 0. `-norun` exit 1337.
- Daggerfall Player.log: only the known startup NullReferenceException (DaggerfallUI.SetupSingleton, already reported).

Not covered by the automated test: the unzoomed part stepping on the travel map. The player's region in the test
(region 17, Daggerfall) is drawn on a single map, so the keys correctly did nothing there. That is on the play-test
list. The interior (building) automap is the same window class as the dungeon automap
(`DaggerfallAutomapWindow`), so it was not run separately.

## Findings and failed approaches

- `dd_ui_test_menu` could not be set from ZScript ("Attempt to change CVAR outside of menu code"). I added
  `CVAR_MOD` to it, like its sibling `dd_ui_test_hold`. It is a test-only cvar.
- Posting to a window on quiet_run's private desktop fails with error 1400 (invalid window handle) from a thread on
  the user's desktop. The driver finds Doom's desktop with EnumDesktops/EnumDesktopWindows and moves its own thread
  there with SetThreadDesktop (the thread owns no windows). Other harnesses that use EnumWindows and PostMessage could
  use the same fix (`tools/map_keys/mapkeys.py`, class `Doom`), instead of `--user-desktop`.
- The first travel map pan re-derived the centre from the integer crop offset each frame. At high frame rates a
  frame's move is under a pixel, so horizontal panning never moved. The centre is now clamped in floats.
- Dungeons now load below the town in the same map (the player was at z -11333 inside), not as a separate DDS map, so
  the harness detects "inside" by depth too. It uses a StaticEventHandler so its stage survives the door.
- `+bind i +forward` on the command line does not work, because `+forward` starts a console command of its own.
  The rebound run execs a small cfg file instead.
- Builds: UZDoom, bridge and launcher came from this worktree's earlier `uzdoom-newgameesc`, `bridge-newgameesc` and
  `launcher-newgameesc` trees (configured from this worktree path). The bridge header is unchanged. The Unity player
  was built through quiet_run with `--user-desktop`, because Unity's license check fails on a private desktop
  (reported by an earlier lane).

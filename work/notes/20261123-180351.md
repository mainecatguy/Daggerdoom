# Re-entering a dungeon loads it broken

Branch `agent/reentry-20261123-180351`. Demo: `D:\dev\DoomDaggerfall-loop\review\dungeon-reentry\play.bat`. It starts facing the Privateer's Hold entrance.

## Result

Fixed. From the second entry on, the dungeon was drawing the **town's mesh** over its own collision map. It was not a race, and the fireball did not matter.

## Exact reproduction

1. Start in Gothway Garden (`DDT07154`).
2. Enter Privateer's Hold, leave, and enter again, without walking out of the town map in between.
3. The second visit draws the town's 181,227 triangles instead of the dungeon's 8,418.

Leaving the town map for the overworld between visits hides the bug, because the overworld updates the stale check described below.

## Root cause

`Active()` in `hw_dfmesh.cpp` decides whether to load the fixed `DFMESH` lump, which holds the dungeon, and only looks when the map name differs from `checkedMap`. Generated towns and interiors return earlier, so they replace the one shared GPU buffer without updating `checkedMap`.

Town to dungeon to town to dungeon therefore looks like "same map as last time", and the buffer keeps the town. Doom's collision and sectors stay correct, which is why the player sees the outdoors but still collides with the dungeon.

## Fix

`Active()` now compares the loaded mesh key on every call and reloads when it is wrong. No delay was added. Maps without a `DFMESH` lump never reach that line.

## Evidence

`python tools/dungeon_reentry/check.py --exe <uzdoom.exe> --cycles 10`. Every `DFMesh: loaded` line is a buffer replacement, so the last one before leaving a place shows what was drawn there.

## Known gaps

- **Projectiles do not survive a door trip, on the old or the fixed build.** A stationary fireball left in the dungeon was gone on all return visits (`DRCARRIED projectiles=0`). `BeginHandoff` keeps only monsters and items. This was already true and is not caused by this fix. It conflicts with the goal's "world state survives" list. I did not change it, because what happens to projectiles across map swaps is the owner's open question, which is on hold.
- **"Can no longer exit" was not reproduced as a separate bug.** Doom's exit worked on every scripted cycle, but the script teleports to the exit. The likely explanation is that the wrong mesh hid the real door. This needs a hand test.
- **One unexplained stall.** One no-bridge fixed-build run stopped after a town arrival that took 3.7 seconds instead of about 0.6, then hit the time limit. It did not recur in 20 further runs (256 cycles) of that scenario or in the final matrix. The cause is unknown. Machine load is possible but unproven.
- The demo was launched minimized, so nobody has looked at the corrected picture yet.

## Failed approaches

- ZScript names are case-insensitive, so a `DOOR` constant clashed with a local `door`.
- A harness constant of 0 in `if (BRIDGE && ...)` stopped `WorldTick` from doing anything without an error. A local variable avoids it. I did not investigate the compiler behavior.
- Running the travel test and cycle check together caused timeouts. Run them one at a time.

## Play-test list

1. Run `play.bat`, press Use, walk in, leave, and enter again several times. The dungeon should look right each time.
2. Let a monster shoot at you before leaving, as in the original report.
3. On a repeat visit, walk to the exit by hand and use it.
4. Repeat with a building, then go building, town, dungeon in a mixed order.
5. Save inside the dungeon after a repeat visit, load, and walk out.

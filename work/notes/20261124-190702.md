# Turn off Daggerfall's resets and respawns (run 20261124-190702)

Goal card: `work/goal.md` (backlog detail `work/backlog/turn-off-daggerfall-resets.md`). Owner decision: persistence is
total. Shop shelf and house container restocks are an open question and stay as they are.

## Plan

1. Find every Daggerfall Unity path that resets, refreshes or respawns a place's monsters, loot or state.
2. For each, say what it did and whether it still runs in a bridge session. Turn off the ones that do, in bridge
   sessions only (`DoomerfallBridge.SessionActive`), so plain Daggerfall Unity keeps them.
3. Report anything that would break with a reset off, rather than changing it.
4. Paired run: clear a dungeon, leave, pass several days on Daggerfall's clock, return, and check it is still cleared.

## What would break with a reset off (reported, not changed)

- A quest sent to a dungeon the player already cleared finds only its own quest foes there; the dungeon's ordinary
  army stays dead. That is total persistence working as decided, but quests whose text implies a populated dungeon
  ("the place is crawling with ...") will read oddly. Nothing in Daggerfall's quest system depends on the respawn
  mechanically: quest foes and quest items are placed by the quest each time, and Doomerfall lists quest foes from the
  active quests, not from the death ledger.
- Saves grow with every interior visited, because the scene cache no longer drops places. It stores only loot
  containers that differ from new (shelves and house containers that were never opened are skipped,
  `SerializableLootContainer.ShouldSave`) and action doors, so the growth is small next to the encounter ledger
  growth already raised in question 20261124-133643.

## Code changes

- `daggerfall-unity-master/Assets/Scripts/Internal/PlayerGPS.cs`: path 1 is skipped when
  `DoomerfallBridge.SessionActive`. One condition, no test logic.
- `daggerfall-unity-master/Assets/Scripts/Doomerfall/DoomerfallResetsTest.cs` (test only, `-dfresettest <days>`, no
  hook in any game class; it starts itself from `RuntimeInitializeOnLoadMethod`): the first time Daggerfall follows the
  player out of a dungeon it caches a marker scene, passes the days on Daggerfall's clock, forces PlayerGPS to see a
  map pixel change (as walking onto the next pixel would), then logs whether the marker survived and how many
  FoeSpawners exist.
- `tools/daggerfall_resets/resets.py`: the paired run. It reuses the location ledger route in Privateer's Hold with a
  real kill quest, kills every monster in waves until none is left, leaves, waits outside about 4 s while Daggerfall
  passes the days, re-enters, and passes only if nothing is alive; it also compares every corpse and loose item at
  leaving and on re-entry.

No UZDoom change, so DOOM.WAD E1M1 is unaffected.

- Player.log has one `NullReferenceException`, the known start-up one in `DaggerfallUI.SetupSingleton` already
  reported by another lane.

## Findings and failed approaches

- Almost every Daggerfall reset had already been made harmless by earlier work, through Doomerfall's own ledgers
  rather than by switching Daggerfall's code off. The only Daggerfall reset still running in a bridge session was the
  scene cache wipe on a map pixel change.
- First Unity build failed on a missing `using DaggerfallWorkshop.Utility` in the test file; fixed.
- The test does not walk to the next map pixel; it forces PlayerGPS's change check by resetting its private
  last-pixel field, which runs the real code path. Walking a whole map pixel on the treadmill would have cost far more
  for the same check.

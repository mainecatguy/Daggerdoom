# Arrival wait covers the dungeon's monster spawn (run 20261126-185032)

Goal: `work/todo.md`, first item. Background: `work/notes/20261126-lockpick-rethink.md`, Finding 3.

## Plan

1. Find why Daggerfall's monster list came ~5 s late in New Game when the spawn was a setup system.
2. Fix that cause, then register the spawn with the setup gate (`DD_SetupWait("monsters")` on bridged dungeon entry,
   `DD_SetupDone` after the spawn in `dd_monsters.cpp`).
3. Build UZDoom and Daggerfall Unity from this branch, install a fresh test folder, run `run_freeze.py normal` (and the
   other modes), the paired lockpick take/load/entry/newgame runs, and the stock E1M1 checks.

## Finding: the 5 s was a deadlock, broken only by the gate timeout

There is no real 5 s delay in Daggerfall. Three waits form a loop:

1. The arrival freeze (`DD_BridgeArrivalFrozen`, `dd_bridge.cpp`) holds `maptime` at 1 until the setup gate is ready.
2. New Game's `NgDoor` step (`PumpNewGame`) says "arrived" to Daggerfall (`DFB_KIND_NEWGAME_ARRIVED`) only once
   `primaryLevel->maptime >= 2`.
3. Daggerfall holds the new character with the game not in progress until that "arrived". `DoomerfallMonsters.Update`
   publishes the monster list only while `sync.InGame` (`GameInProgress`), which turns on in
   `FinishNewCharacterStart`, after "arrived". For a plain load (Daggerfall save with no Doom half), the same holds with
   `sync.LoadRunning`, which stays on until "arrived".

So with "monsters" in the gate: freeze waits for monsters → monsters wait for Daggerfall's list → the list waits for
"arrived" → "arrived" waits for maptime 2 → maptime waits for the freeze. The gate's 5 s timeout ends it, and then
everything follows in ~0.4 s, which matches the "~5.4 s after the map loaded".

Evidence from the lock-rethink New Game run (without the trial, `review/lock-rethink/test/newgame-uz.log` and
`newgame-df.log`): setup done at 806.490, Doom said "arrived" at 806.533, Daggerfall's "quests and clock started" at
806.653, and Daggerfall's `monsters: list 1` at 806.681, 28 ms after the game started. The list itself is fast once
Daggerfall is allowed to send it.

## Fix

- `dd_bridge.cpp`, `NgDoor`: a frozen arrival (`DD_BridgeArrivalFrozen()`) counts as arrived, as well as
  `maptime >= 2`. Doom is in the dungeon and the handoff is done at that point. Only the playsim is held. One condition
  changes. It covers New Game and plain load, which share the step.
- `dd_monsters.cpp`: `DD_SetupWait("monsters")` in `DD_MonstersEnterDungeon` when bridged, and
  `DD_SetupDone("monsters")` in `ApplyRows` right after `SpawnEncounters` for this dungeon's list (`mapLeaders`). A
  revisit whose army is all dead or present still calls `SpawnEncounters` (it returns early), so its gate also opens. A map
  restored from a save has an inactive gate (`DD_SetupLevelLoaded(fromSave)`), so the wait is a no-op there. Without a
  bridge nothing changes (`bridged` false, and no session means no gate).

Rejected alternative: let Daggerfall publish the list while the character is held (bypass `InGame`/`LoadRunning` in
`DoomerfallMonsters`). It works too, but it has to reach into two different gates on the Daggerfall side
(`ItemSpace` is shared with items), and it needs a Daggerfall Unity change for something Doom's own step ordering causes.

Side effect: in New Game, Daggerfall now starts its clock and quests while Doom's playsim is still frozen for the spawn
(a few hundred ms). The player is frozen by New Game itself until Daggerfall's "go" anyway. The diagnostic log line
"new game: N monsters on the map" now runs before the spawn and so reports 0 monsters.

### Verifier round 1 fixes

1. **Extra arrival autosave in New Game (and plain load).** Telling Daggerfall "arrived" during the freeze lets it start
   (flow hold off, phase PLAY) before the gate opens, so `PumpArrival` found `SaveReady()` true and wrote an `auto`
   save that used to be dropped (`flow 1`). Fix: `NgSendArrived` clears `arrivalSave` while an arrival is pending and
   logs `save: dropped the autosave for a map change, a New Game or plain load is arriving`. The freeze and the gate still
   run to the end. The flow's own save (`PumpNewGameSave`, `-newgame.zds`) is unchanged.
2. **Lost place record (found while re-running New Game).** One New Game run timed out on `place` as well: Daggerfall
   logged `sent the record of D187853213`, but Doom never got it. Daggerfall queues the reply (`DoomerfallLocations.Post`,
   sent on its next `Update`). When "arrived" lands in the same Daggerfall frame, `FinishNewCharacterStart` fires
   `OnStartGame`, and `ForgetWorld` calls `sendQueue.Clear()`, so the queued reply is dropped. Before this goal, "arrived"
   always came after the place record had been applied (the freeze ended first), so the race could not happen. Fix: in
   `NgDoor` a frozen arrival counts only once `DD_LocationsWaiting()` is false, which brings back that order for the
   place record. Only the monster list, which needs Daggerfall's game started, comes after "arrived".
3. **Freeze test count.** `run_freeze.py` now requires the whole army (`ARMY = 73`): in normal mode
   `monsters + spawned == 73`, and in slow, nosave and use `monsters == 73` (snapshotted and checked unchanged).
   **Stated plainly:** in normal mode the spawn is the last thing setup waits for, so all 73 monsters spawn on the
   freeze's last tic. The harness counts them as `spawned` (they appeared inside the freeze, after its last snapshot).
   It never sees a frozen frame with them, so it cannot check them unchanged. They never act before the freeze ends,
   and they are in the arrival autosave. The slow, nosave and use modes show the same 73 held and unchanged.
4. **Plain load into a dungeon, tested.** `tools/plain_load/run_plain_load.py` gained `--root` and `--source`. A
   `.zds` source gives a plain Daggerfall save made of the bundle's Daggerfall files, with no `Doomerfall*.json`, plus a
   `Screenshot.jpg`, which Daggerfall's Load window reads or else throws. The source was this run's New Game save,
   inside Privateer's Hold.

## Problems found

### 1. The placer changes the army based on what is standing on the map (desync risk, engineering fix)

The design needs "the planner is a pure function of place, seed, area level and plan version", because a mook entry
names a mook only by its index. The planner is pure, but the placer is not, and the placer changes the army:

- `dd_encounter_placer.cpp` lines 9-15: "A spot is valid when the mook's own body fits there by P_CheckPosition,
  **actors included**", and "when a placement's whole walkable area is full, the planner **promotes its mooks to
  fewer, stronger ones** (up to three times), then the rest move to the nearest placement with room". The leader is
  "the highest-point mook that fits at the origin".
- So the classes, the number of mooks and who leads can change with the live map: door blockers (`DFDoorBlocker` are
  solid actors that move with the door), action object cells (`DFActionCell`, solid, move with the platform), the
  player's body, and restored monsters. Card 1 already hit this and made restored monsters non-solid during a revisit's
  planning (`dd_monsters.cpp` `SpawnPass`), but doors and platforms were never part of it because they never kept a
  state between visits.
- With the record, door and platform states are restored and the mook entries refer to indices. If a re-plan promotes
  differently, an entry saying "mook 812 is dead" lands on a different monster, or on nothing.

**Suggested fix (engineering, I can do it):** plan and place against the bare map: every actor made non-solid while the
placer runs (not only monsters), and the plan runs before door, switch and action states are applied. Then the plan
depends only on the converted map, the facts and the plan version. The converter version stamp (design rule 7) covers
map changes. A plan version bump on any placer change.

### 2. Quest foes are inside the planner request today (planned change, larger than the design implies)

`dd_monsters.cpp` `SpawnEncounters`: quest foes are placements in the same request as the map markers ("Pass 2 holds
quest foes that came after it, planned with everything"), and the first visit's quest placements are frozen per
dungeon in `ddplans` so a revisit plans the same army. So today the army *does* depend on which quests were active on
the first visit. The design's overlay ("quest foes never change the seeded army", `gamedesign.md`) means: plan the map
markers alone, then plan quest foes as a second, separate request. That is an engineering change on top of an owner
rule, and I can do it, but it changes the army of every dungeon that was first entered with a quest active, and old
saves' dungeons will come back with different mooks (format change; fine at this stage, noted).

### 3. Player drops that bypass Daggerfall piles (missing state, owner decision)

Dropping from Daggerfall's inventory window makes a pile (confirmed by the design and card notes). Doom has its own
drop paths that spawn Doom pickups directly, with no pile:

- **DRLA's weapon drop** (`ArsenalRLWeapon.txt` line 73, `WeaponDrop` state). A modded gun becomes a `...PickupModded`
  actor carrying its mods as inventory on the pickup (`work/notes/20261124-002144.md`, play-test 5 uses exactly this).
- **DRLA's Special Item Dropper**, bound to M by default (`keyconf.txt` lines 23-26; `ArsenalCVarChangers.txt`
  `DropBackpack` runs `RLBackpackToss`).
- **Doom's own `weapdrop` / `invdrop`** commands (`d_net.cpp` 2742, `DEM_INVDROP` -> `DropInventory`).

Today (card 1) these become dynamic world table rows and survive. In the new record nothing holds them, so they would
vanish when the player leaves. The design says "route it into a pile", but a Daggerfall pile looks like a Daggerfall
loot bag, not the dropped gun, so this changes what the player sees. Options:

- **A. Route into a Daggerfall pile** when the player leaves (or at the drop): one ownership rule, Daggerfall holds the
  contents, gun mods go into the item's `GunState` like a Use take does. The gun shows as a pile on return.
- **B. Keep them as exceptions** in the place record (class, low-resolution spot, amount, mod tokens). The gun still
  looks like the gun. Costs a few dozen bytes per dropped item and a second ownership path for loose items.
- **C. Turn Doom's drop paths off** on Daggerfall maps, so the inventory window is the only drop.

This is the owner's call (what the player sees). My suggestion is A at the moment of the drop (the pickup is replaced
by a pile at once), so it never looks different between "before leaving" and "after returning".

### 4. A Daggerfall pile emptied before a save can come back as a ghost (desync, small fix)

Answer to "can a pile emptied or removed before a save come back from the snapshot": **yes, rarely.**
`DoomerfallItems.zs` `RemoveExcept(generation)` removes pile actors whose `dfGeneration` differs from the newest list.
After a load, the snapshot's pile actors keep the generation number from the session that saved, and Daggerfall's
counter (`DoomerfallItems.cs` `generation++`, never saved) restarts at 0 in a new launch. If the first list after a load
happens to have the same number as a restored pile, that pile is kept although Daggerfall no longer has it: a ghost
marker that Use cannot take. In the same launch the counter only grows, so it cannot collide there.
`DD_ItemsResync` (`dd_items.cpp`) never sends `dfi_clear`, which would remove them all until the list arrives.
**Fix:** send `dfi_clear` from `DD_ItemsResync`. One line. The same pattern does not apply to containers' contents
(Daggerfall holds them), only to the markers.

### 5. Doors, switches, lifts and action objects keep state only in the snapshot (confirms the design)

Doors (`DFDoor`: `swung`, `moving`) and action objects (`DFAction`: `fraction`, `phase`, `activationCount`,
`forwardOnly`) are ZScript actors spawned on `WorldLoaded` from the `DFDOORS` and `DFACTIONS` lumps. `Park` stores only
monsters and inventory, and every Daggerfall map is loaded fresh on each visit (not a hub), so **every door and lift
resets to closed and at start when the player leaves and returns**. They survive only a save and load inside the same
map. The design's "doors keep their state" is therefore new work, not a port. Notes for it:

- Index order: line order of `DFDOORS` and record order of `DFACTIONS` (both from Daggerfall's data, fixed per
  converter version).
- 2 bits per object is enough for at start / at end, plus one bit for "used" on one-shot actions (`forwardOnly`,
  activation counts). A door or lift caught mid-move is stored at the end it was heading to.
- Door and lift states must be applied *after* the plan (problem 1).
- Town doors and city gates use the same `door_objects.zs` (`CityExport.cs` 273, 834).

### 6. The overworld is not one place

Exterior state is a sliding window, not a place one leaves. Card 3 keyed it by world chunk (32 x 32 tiles) and fetched
every chunk record from Daggerfall once after each load, holding chunk building until the answer arrived. With Doom's
table no longer saved, that is still needed: Doom keeps a session copy of the records it has sent or received (never
saved), replaced from Daggerfall after every load. Overworld pack monsters walk across chunk borders, so an entry stays
in its home chunk's record (its id is built from the home chunk, `dd_treadmill.cpp` `BuildSeeds`) with coordinates
that may fall outside the chunk; the 13-bit x, y need a box a few chunks wide (for example 4-unit cells over 4 chunks).
These are engineering details the design leaves open; no owner input needed.

### 7. Smaller notes

- Leader drops are Daggerfall loot piles rolled from Daggerfall's tables (`DoomerfallMonsters.cs` `Roll`, kept in the
  death ledger with their items). They are pile contents, so they stay in Daggerfall's ledger by the ownership rule.
  Only followers' death rows (most of the 310 KB `DoomerfallMonsters.json` in card 2) move into the record.
- Monster *Doom* drops rerolled from the seed depend on `drla-fixed-drop-seed.md`. If that is not done first, the
  simplest correct fallback is a compact drop list per place (a per-place class name table plus one u64 per loose drop:
  class index, cell, height band, amount), about 8 bytes per drop instead of card 2's 68.
- The world table today is not only "the current map": `ddoverworld` in the `.zds` holds every changed actor of every
  visited place (361 KB for one cleared level-30 dungeon in card 2), plus `ddplans` and `ddspaces`. The new design
  removes it, which is most of the dungeon saving.
- Overworld automap marks (sector `moreflags` drawn bits, line mapped flags) also live only in the snapshot. Cosmetic.

## Owner's question: "I think we sync the zds just so that maps that are loaded look good. Are we doing that, is that a problem, and is it a hole in this design?"

**What the `.zds` holds.** UZDoom saves only the current map's snapshot (Daggerfall maps are not hubs, so no other
map's snapshot is kept), plus today's world table text inside it. The snapshot is not just looks: it is the only copy of
the live fight (monster positions, health, targets and AI states, projectiles, summons), the player's Doom-side state
(equipped gun, magazines, DRLA mod tokens, powerups), door and lift poses, and ZScript handler state. That is why the
design keeps it as the authority for the current map, and that part is right.

**Is the overworld snapshot a problem?** Yes, a size problem, and the design's answer is correct. Measured in
`D:\dev\DoomDaggerfall-loop\review\locledger2\run\saves\resume.zds`, `ddover01.map.json`:

| | raw | packed (zlib 6) |
|---|---|---|
| as saved | 5,451,541 | 1,344,465 |
| without sector `floorplane` / `ceilingplane` | 947,291 | **15,011** |

`sectors` is 4,768,225 bytes, and the only sector fields saved are `floorplane` and `ceilingplane` on all 32,768
sectors (plus 11,049 cosmetic `moreflags`). Both are written by the treadmill and rewritten on every load:
`DDTreadmill_Serialize` restores `originX/Y`, then `Resume` -> `PrepareLevel` sets every ceiling to `SKY_HEIGHT` and
`FillWindow` + `RewriteGrid` set every floor plane and floor texture. The saved values are never used. The remaining
raw bytes are mostly empty `{}` per line and side, which pack to almost nothing. **Fix:** one hook just before
`arc("sectors", sectors, loadsectors)` in `p_saveg.cpp` that, on DDOVER01 while the treadmill runs, copies the
treadmill-owned fields (both planes and the floor texture) into `loadsectors`, so the delta writer skips them. An
overworld save drops from about 1.33 MB to about 15 KB packed.

**Is it a hole?** Not for the current map. The holes are what the snapshot holds that nothing else keeps once the player
*leaves*: door and lift states (problem 5, in the design), player drops through Doom's own drop paths (problem 3, not
in the design), and wounded or awake monsters (in the design). Summons are dropped by design.

### What already exists (second look)

- **Doom already finds every loose item without hooking any drop path.** `dd_treadmill.cpp` `Park` (called for every
  actor when a place is left or a chunk slides out) stores every `Inventory` actor that its map or seed would not
  rebuild unchanged as a `KItem` row: class, Daggerfall-unit position, angle, amount, dropped flag. Player drops (all
  three Doom paths), monster drops and moved map items all land there. DRLA's tossed backpacks are plain item classes
  (`DroppedRLCombatBackpack` ... from `DRLALIB_Backpack.acs` `TossItem`), so they are covered too.
- **Card 2 already moved those rows to Daggerfall** (branch `agent/locationledger-20261124-141035`,
  `DoomerfallLocations.cs`, `dd_locations.cpp`, bridge kinds 200-205). Per place: a class name table and one text
  line per fact; Doom drops are kept by position (`DFB_FACT_SESSION`); places are keyed `D<map>`, `B<map>:<building>`,
  `O<cx>,<cy>` (exterior chunks); the record goes to Daggerfall on leaving and on save, and comes back on entry. Paired
  runs brought back 1,932 loose items in a slaughter dungeon with 0 rows unmatched. Size: 68 bytes per fact in
  `DoomerfallLocations.json`.
- So the owner's collection is card 2's loose item facts. It does not need a new path, only a smaller format and one
  missing field.

### Gap found: carried state is lost today

`Park` and `Restore` store only class and amount. A DRLA `...PickupModded` gun keeps its mods as inventory on the
pickup (`+INVENTORY.TRANSFER`), so after leaving and returning, a dropped modded gun comes back unmodded. This is true
on integration now (card 1 table) and in card 2. Restoring it is safe: the pickup's spawn runs DRLA `GetWeaponMods`,
which copies mods from the pickup's *master* (the dropping player) and terminates when there is none
(`DRLALIB_Mods.acs` line 79ff: `SetActivator(0, AAPTR_MASTER); if (PlayerNumber() < 0) terminate;`). A restored
pickup has no master, so the script leaves the inventory Doom gives it alone. The other per-pickup state
(`user_floorhit`, the rarity beam) is rebuilt by the spawn states. The text form is the existing `GunState` text
(`name=amount;...`, `dd_items.cpp` line 489ff), so Use-taking a restored gun already carries the mods to Daggerfall.

### Final proposal for loose Doom items

1. Keep card 2's transfer and place keys. Loose items are one list per place, no piles.
2. Entry, packed into one u64: class index into the place's name table, x and y in the place frame, a height band,
   amount. Field widths fixed after measuring the largest dungeon extent (expected: 10 class, 16 x, 16 y, 12 z,
   10 amount). An item that does not fit (amount, class count) is written as a plain card 2 line.
3. Carried state: an optional string per entry, the `GunState` text, only for items that carry inventory.
4. On disk: the entries as one base64 byte array per place plus the names and the carried-state strings.
5. Ids: the entry's position in the list is enough. Doom rewrites the whole list for a place at leave and save, so a
   taken item is simply absent and needs no message.
6. Restore spawns the class at the spot, drops it to the floor below the stored height band, then gives its carried
   inventory.

**Size.** Card 2's dungeon: 1,932 loose items at 68 bytes = about 131 KB in JSON. Packed: 8 bytes each, about 15 KB,
about 21 KB as base64. A few dozen player drops are under 1 KB either way; packing only matters because monster drops
share the list (unless `drla-fixed-drop-seed` lands, which would remove most of them).

### Placer, confirmed in code

`dd_encounter_placer.cpp`: spot checks pass `actors = true` (lines 325, 356, 497), and `NearMover` (line 202) skips
spots next to a line special or a sector that is moving at plan time. With doors resetting on each visit, the varying
inputs are the player's body and restored monsters (card 1 already makes those non-solid). Fix: during placement make
players, monsters, `DFDoorBlocker` and `DFActionCell` non-solid. Keep static solid decorations solid, so mooks still
do not start inside pillars (a global `THRUACTORS` would lose that).

### Gap found: the mod-set rule is not enforced

UZDoom checks only the IWAD and map WAD names on load (`g_game.cpp` `G_CheckSaveGameWads` line 1989), and
Daggerfall checks nothing. A save loaded under different mods runs, and rows whose class is gone are skipped with a log
line (`Restore`, "class ... no longer exists"). Suggest a mod list stamp in the Daggerfall save that refuses a
mismatched load. Not part of this item.

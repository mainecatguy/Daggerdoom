## 1. The owner's play build HAS Skill XP, but Daggerfall dropped every report (fixed)

(Rewritten after the verifier's review. The first version guessed from git that the build predated Skill XP. That was
wrong: PowerShell could not list the play folder, but the Read and Grep tools can read it.)

Evidence from `D:\dev\DoomDaggerfall-loop\play`:
- `play.bat` line 4 still says "integration at 399b9c24" (2026-11-27 00:51). 399b9c24 has no Skill XP source, so that
  label is stale and the folder's binaries were updated later. The verifier found `DoomerfallSkillXp` and
  `DoomerfallSkillsWindow` in the folder's `Assembly-CSharp.dll`, and the Skill XP mod code in `doomerfall.pk3`.
- `play\run\uz.log` has 131 `skillxp: sent N XP ...` lines (the first at line 115206, `273013.610 skillxp: sent 1 XP`)
  and 4 lines `ui: Daggerfall opened menu 15` (the Skills menu, lines 116632-116877). So Doom counted the owner's
  damage and sent it, every send returned 0 (success), and the owner opened the Skills menu 4 times.
- `play\run\df.log` covers the same times (line 162082 onward is 273010.x) but has **0** `skillxp` lines. Its heartbeat
  shows `unknown=0`, so the events arrived and were dispatched (`DoomerfallBridge.cs` case `KIND_SKILL_XP`).
- The owner's keys (`play\run\uzdoom.ini` lines 970-975): **U is bound to Rest (df_rest). The Skills menu is on M and
  on the comma key.**

**Cause:** `DoomerfallSkillXp.OnEvent` returned early on `DoomerfallNewGame.HoldsNewCharacter`. Despite its name, that
property is `instance != null`: true for the whole of any `-dfflow` session, and the play folder always runs `-dfflow`
(New Game or Load from Doom's title). So in real play every Skill XP report, and the weapon-skill uses that come with
it, was thrown away before the pool and before the log line. The skillmenu tests passed because `-dfsynctest` starts a
ready-made character with no flow. This matches the owner's report: XP never grows, so the menu always shows 0.

**Fix** (`DoomerfallNewGame.cs`, `DoomerfallSkillXp.cs`): a new `DoomerfallNewGame.HoldingCharacter` is true only while
a finished new character is held waiting for Doom to arrive (`CharacterPlaced` to `OnArrived`), and Skill XP checks
that instead. During normal play in a flow session it is false.

  RLDemon 15 times for 150 HP and killed it (`SXFIRING ... hits 15, HP 150`). Doom then sent `skillxp: sent 1 XP`, and

- **Bulk damage earns XP.** The DamageMobj phase (Baron, 2 zombies, 5 Cyberdemons, a townsperson) gave

  226 -> 203, earned only True`. The menu text changed from `Skill XP: 226 ... Skill: 3` to `Skill XP: 203 ... Skill: 4`.
- The rest of the old test still passes: bought points reach a level-up (1 -> 2), buying waits during a pending
  level-up, save/load keeps pool 777 and Mysticism 18, and a second bought level-up works (2 -> 3). `SXDONE`.
- `skillxp.py check`: E1M1 stock exit 0 and DRLA exit 0, with 0 bridge or skillxp lines and 0 fatal errors. The 3

  `-norun` exit 1337 (run 3 builds: no UZDoom or mod code changed in this run, so these still stand for the fix,

These runs use `-dfsynctest`, not the owner's `-dfflow` session, so they could not show the bug in section 1.

## 3. Why the owner may still see little, even with the fix

These are not bugs. They come from the owner's own numbers (`gamedesign/decisions/20261126-skill-xp-rate-owner.md`,
`XpPerUse = 7.5`, buy multiplier 2):

- Earning is slow at the start. The starting RLPistol does about 10 HP a hit, so a Demon (150 HP) is 1.5 Skill XP and
  a zombie (20 HP) is 0.2. One point of a skill at 3 costs 23 XP (about 15 Demons). A skill at 30 costs about 188 XP
  (18,800 HP of damage), which is roughly 125 Demons.
- Nothing in Doom tells the player that Skill XP went up. The pool shows only in the Skills menu and on the sheet. This
  is asked in "Questions for the owner" below, not built: it is a UI design choice.

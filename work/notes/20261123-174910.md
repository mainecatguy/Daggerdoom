# Generate the C# bridge definitions from the header

## Result

`bridge/doomerfall_bridge.h` is now the single definition of the bridge. C# constants, structs, payload views, and native imports are generated from it.

## How to regenerate

```
python bridge/generate_bindings.py
```

This writes two files, which are committed and must never be hand-edited:

- `daggerfall-unity-master/Assets/Scripts/Doomerfall/DoomerfallBridge.g.cs`: constants (`Dfb.KIND_HP`), explicit-layout structs, typed payload views (`ev.hpEvent.amount`), byte-array helpers, and `DfbNative`.
- `bridge/doomerfall_bridge_check.g.h`: `static_assert`s for every constant value, struct size, field offset, and field type, plus `DFB_SCHEMA_HASH`.

An event kind's `payload: dfb_x` header comment creates its typed C# view.

## How drift is caught

| Layer | What it catches | Proof |
|---|---|---|
| `generate_bindings.py --check` | Any difference in generated output, including new definitions and comments | `bridge/test/check_bindings_drift.py`: 9 of 9 deliberate changes caught on scratch headers |
| Strict parser | Header syntax it cannot represent (exit 2) | Same test |
| C++ `static_assert` | Changed constants or layouts, even without Python | Scratch build with `DFB_KIND_HP` changed failed to compile |
| CMake | Stale files fail the bridge, launcher, and UZDoom targets | Real bridge build exited 1 with the stale message |
| `CliBuild` | Stale files fail the Unity build before it starts | Real Unity run exited 1: `CliBuild result: Failed (stale bridge bindings)` |
| Attach | Wrong or older DLL | See below |

The schema hash covers every constant, struct field, and function signature. Comments do not change it. It also feeds `dfb_layout_hash`, so all native binaries refuse a peer built from a different header.

## Moved out of hand-written C#

Protocol version, side and result codes, all event kinds, transition actions, save status and path slot, HP types and flags, UI ids, states, reasons and input types, world contexts, phases, surface limits, all mirrored structs, the DllImports, and all manual payload packing and unpacking.

## What remains manual, and why

- `VOID_PARAMS` in the generator says what each `void *` parameter is in C#, because the header cannot express it. `dfb_surface_acquire` is not imported, because C# does not use it and its `void **` has no safe form.
- Python tests such as `bridge/test/save_handshake_test.py` still copy some struct layouts. Shared Python test helpers were out of scope.
- `dfb_struct_size` stays as a small extra check.
- UZDoom's C++ uses the header directly, so it needed no generated copy.

## Behavior and memory layout

No struct, constant value, or protocol version changed. The additions are the `dfb_schema_hash` export and the new layout hash value. Header comments were expanded for future readers.

The last header edit, after the test runs, changed only the `DFB_KIND_HOLD` comment. It does not change the schema hash. The games were not rebuilt after it.

## Real-game verification

All runs used a private folder, `D:\dev\DoomDaggerfall-loop\review\bridge-codegen`, private configs, a portable renamed Daggerfall, and minimized windows.

- `bridge_stress`: all passed.
- Door, save, and load suite, 11 runs: 17 building entries across 16 types, no wrong types, no failed transitions, no new Daggerfall exceptions, all 6 loads resumed in both games.
- Death and load suite: `cycle`, `death`, `menu`, and bad saves `flipped` and `wrong-hp` all passed.
- HP: 25 of 25 events sent and applied in order, including a lethal hit.
- Inventory opened and closed through the real bridge.
- Fast travel reached Akhidai, and Daggerfall reported Doom at the same map pixel.
- Map opened and closed in a town and in a building.
- No session: stock `DOOM.WAD` E1M1 entered with 0 bridge lines. With DRLA it entered with the same 3 load errors and 763 unknown-class lines as the prior build.
- Plain Daggerfall: 0 bridge mentions and 0 exceptions. It was stopped by the 12-second test limit, as that check expects.
- Owner's Daggerfall registry key was unchanged.

### Mismatch refusal

- Older DLL without the new export: `bridge DLL does not match this build (it is older): dfb_schema_hash`.
- Same protocol, wrong schema: `schema 1111222233334444, expected 7b5f737dd51b564f`.
- Older UZDoom with the new launcher: it exited with code -1 about 1.6 seconds after launch, before opening its bridge log. This matches its fatal attach path, but the error code itself was not captured.

## Failed approaches

- The first stale-DLL test could not swap the DLL because a just-closed Daggerfall still held it. The script now waits for the file to be free and never kills the holder.

## Not run

The full `bad` save list, `skip`, and the suite's stock load cases were not run. Five of the load suite's cases were selected to limit cost.

## Noted, not changed

- C# sends `DFB_KIND_HELLO` with an empty payload although the header names `dfb_hello`. Nothing currently reads it.
- `SendText` can throw on text over 48 UTF-8 bytes when it contains non-ASCII characters. Current messages are short ASCII.

# Lanes hang when a run ends (run 20261126-114648)

## Plan
1. Find the cause from the harness code and the lane logs.
2. Reproduce it with a free fake lane.
3. Fix it, prove it with the same fake lane.

## Findings
- Lane logs: `queue-lockpick.log`, `lane-travel/queue-skillcore.log` (and daynight) all log "Finished" at exactly
  2026-11-26 11:38:29, when the owner killed the leftover games, although `run.ps1` had written its reports hours earlier.
- Cause: `queue.ps1` runs `& powershell.exe run.ps1 ... *>> log`. PowerShell reads the child's output pipe until it
  closes, and every descendant inherits that pipe (`Start-Process` in `Invoke-Logged`, Claude's tools, and
  `quiet_run.py`'s `CreateProcessW(..., bInheritHandles=True)`). A game that outlives its agent holds it open.
  Details: `tools/lane_hang/README.md`.
- Reproduced with `python tools/lane_hang/run_fake_lane.py` on the current harness: `run.ps1` wrote its report
  ("minutes: 0") but the lane never logged Finished within 70 s while the 90 s fake game ran. FAIL, with a plain game and
  with a game on quiet_run's private desktop (`--quiet-run`).

## Fix
`tools/lane_hang/harness-fix.patch` (run.ps1: each child in a Windows job ended when it exits; queue.ps1: output to
files and wait on the process, not a pipe). **Not applied:** every file involved is in `scripts/overnight/`, which
agents may not edit and `run.ps1` rejects. The owner applies it with `git apply tools/lane_hang/harness-fix.patch`.

## Results (fake lane, 90 s fake game, 70 s limit)
| Harness | Lane done | Games left | Result |
|---|---|---|---|
| current | no (stuck on card 01) | 1-2 | FAIL |
| patch, plain game | 2.6 s, both cards | 0 | PASS |
| patch applied with `git apply`, quiet_run game | 2.5 s | 0 | PASS |
| run.ps1 change only, quiet_run game | 2.4 s | 0 | PASS |
| queue.ps1 change only | 2.2 s | 2 | FAIL (no hang, games survive) |

The run.ps1 job alone fixes both symptoms. The queue.ps1 change is a backstop for anything that escapes the job.

## Trade-offs and known gaps
- Leftover processes now end at the end of each round, check, verifier and review, not only at the end of the run.
  That includes MSBuild reuse nodes, mspdbsrv and Unity's licensing client started by builds; the next build restarts
  them (a few seconds). Agents cannot keep a game running across rounds (they had no way to reach it anyway).
- A process started outside the tree (WMI, Task Scheduler) or one that asks to break away is not ended. It no
  longer stalls the lane thanks to the queue.ps1 change.
- Not tested against a real $10 run, as the goal asked. The first real lane after applying is the live check.
- `queue-<lane>-output.log` now gets each run's output after the run; watch `queue-<lane>-run.log` live.

## Play-test list
None (harness only). After applying: start one lane, confirm `queue-<lane>-run.log` fills live and the lane moves on.

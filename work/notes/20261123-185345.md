# Speeding up town and interior transitions

Branch `agent/transitions-20261123-185345`. Demo: `D:\dev\DoomDaggerfall-loop\review\transition-speed\play.bat`. It starts in the City of Daggerfall.

## Result

Returning to the City of Daggerfall is about 30% faster, but it is still a visible freeze of about 1.2 s. The remaining cost is mostly the size of the converted map text, which belongs to the converter and is outside this task. See "Decision for the owner".

## Where the time went

Almost all of a return is main-thread CPU work. The disk is not the bottleneck. A city return read only 4.3 MB, and wall time matched CPU time to within a few percent.

First profile of a city return, about 1.6 s:

| Cost | Time | Cause |
|---|---|---|
| Parsing the map text | 450 to 700 ms | The city's `TEXTMAP` is 43.5 MB. The tokenizer is already about 37 ns per token |
| Building render sections | 390 to 680 ms | Two quadratic searches on large sectors |
| Loading nodes | 210 to 310 ms | Mostly repeated MD5 hashing of the whole map |
| Render setup, vertex buffers, other | The rest | Proportional to map size |

The walk-in time of 1.0 s recorded earlier was not re-measured. A return does a full level load every time.

## What changed

1. **Section building (`r_sections.cpp`).** Two quadratic searches became indexed lookups that visit items in the same order. Outlines fell from 340-520 ms to 50-60 ms in the city.
2. **Map checksum (`p_openmap.cpp`, `p_setup.h`).** One load hashed the full map up to four times. It now hashes once per opened map.
3. **Town stays in memory (`dd_towncache.cpp`, `dd_treadmill.cpp`).** The player's outdoor location can no longer be evicted while they are in it or in one of its interiors. After a load indoors, it is read in the background.
4. **Profiler.** `-ddtranslog <file>` records each load phase and frame. Without the option it does nothing.

The owner's cache idea is item 3. It is a safeguard and not the main speedup: in a seven-building route the city was never evicted, so the old cache was not causing today's stutter. The guard's eviction case was not forced in a test.

## Memory

No new cache of level data was added, and peak private memory was the same before and after (about 1.4 to 1.6 GB on the city route). The town cache still holds at most 4 ready entries, plus up to 2 still held by the current map and the distant view. The city entry is 78.9 MB decompressed, so the worst case is about 470 MB if every held entry were city-sized. A typical case is one town and small interiors, about 80 MB.

## Slower-drive estimate

These are calculations and were not measured on a slower drive.

| Drive | Normal return (4.3 MB) | Town not in memory (14.2 MB) |
|---|---|---|
| This SSD | Under 5 ms | Under 15 ms |
| SATA SSD, 500 MB/s | About 9 ms | About 30 ms |
| Slow SSD, 100 MB/s | About 45 ms | About 140 ms |

A town not in memory also needs about 110 ms to decompress on a worker thread. A normal return is CPU-bound, so a slower CPU will matter much more than a slower drive.

## Failed approaches and problems

- My first route failed because the door harness applied the dungeon's exit to every door when dungeon data was loaded. `door_test.py` now passes it only on dungeon routes.
- My first two-game suite failed with bridge error -5, because the `dungeon-reentry` launcher and Daggerfall are older than this branch's bridge. The suite now uses `bridge-codegen`.
- Copying files from the build folder was refused by this session's permissions, and I did not work around that. **So `sndfile.dll` and `soft_oal.dll` are not beside the exe as the goal asked.** `play.bat` runs the exe from `D:\dev\DoomDaggerfall-build\uzdoom-transition\Release` and finds the DLLs through `PATH`. A later rebuild in that folder changes what the demo runs.
- The demo depends on the `bridge-codegen` review folder for its launcher, Daggerfall, and mods.

## Decision for the owner

The largest remaining cost is proportional to the 43.5 MB of map text. Shrinking it means changing the converter's output, which this task was told to avoid because a parallel lane may be working there. Parsing is about 350 ms of a city return, and other costs also scale with map complexity.

# Startup and save flow proposal

Research only. No engine, mod, or launcher code changed.

Evidence labels: **[C]** confirmed by reading code, **[M]** measured on this machine, **[A]** assumption that still needs a test, **[O]** owner decision needed.

## 1. Recommendation

1. **One save file holds both games.** A Doomerfall save is a normal UZDoom `.zds` zip with Daggerfall's save files inside it under `doomerfall/`. Replacing one file is atomic, so the two halves cannot drift apart, and orphaned halves cannot exist.
2. **Daggerfall stays the save controller.** It approves or refuses each save, supplies the authoritative game state, and restores first on load. Doom only packages the file, because it already owns the save format and the window.
3. **Doom's menu is the front door.** A gated Doomerfall main menu offers New Game, Load Game, Options, and Quit.
4. **New Game uses Daggerfall's real character creation** through the overlay being built for fast travel.
5. **Save and Load reuse UZDoom's existing save menus,** rerouted in a Doomerfall session. They already have thumbnails, descriptions, delete, keyboard, and gamepad support.
6. **Regular WADs do not enter this path.** All of it is gated on a new launcher flag.

### Why one file

| Evidence | Result |
|---|---|
| [M] Stock UZDoom build, DOOM.WAD E1M1: saved with a radiation suit active, added a real 12-file Daggerfall save and a manifest to the `.zds`, loaded it, saved again | The power-up survived the load. A control save without the suit did not contain it. The zip stayed valid with 17 entries. |
| [M] Real 2.5 MB Daggerfall save (one sample, `SAVE0`) | Compresses to 476 KB in 11 ms |
| [M] Write, flush, and atomically replace a file of that size, 50 runs | Write p50 1.46 ms, max 3.24 ms. Replace p50 0.40 ms, max 0.58 ms. |
| [C] Unknown zip entries are ignored | `G_ReadSnapshots` only matches `.map.json` and `.mapd.json` (`g_level.cpp:2155`). Other reads are by exact name. |

This test did not cover DRLA, a generated Daggerfall map, or a late-game Daggerfall save.

## 2. What the code does today

### Startup

- [C] Doom drops into a game because the demo passes `-skill 3 +map E1M1` (`review/launcher/play.bat:8`). Without a map, UZDoom runs its title loop (`d_main.cpp:4057-4066`), which includes demo playback.
- [C] The bridge is transport only. It has no save, load, or lifecycle events. `df_phase` is defined but Daggerfall never sets it (`DoomerfallBridge.cs:265-268`).
- [C] Bridge events carry 48 bytes (`doomerfall_bridge.h:87`). Paths must go through a bulk slot or be derived from the session and transaction ID.
- [C] Daggerfall boots to its Start window through `dfuiInitGame` and `InitGame` (`DaggerfallUI.cs:545`, `:1707`).
- [C] New characters finish in `StartNewCharacter` (`StartGameBehaviour.cs:353`). It **unpauses the game and starts the main quests right away** (`:439`, `:446-447`), so Daggerfall must be held until Doom has arrived.
- [C] The default start is a dungeon at cell 109,158 (`defaults.ini.txt:169-171`). New Game therefore depends on Doom being able to enter a dungeon at runtime (todo 10).
- [C] Character creation can play three cinematics (`DaggerfallStartNewGameWizard.cs:592-602`), so the overlay must handle video.
- [C] A first run without valid Daggerfall data goes through Daggerfall's setup wizard, in its own scene (`DaggerfallUnitySetupGameWizard.cs:733`).

### Daggerfall saves

- [C] Saves overwrite files in place, with no error path (`SaveLoadManager.cs:718-721`, `:1161-1173`). A failure partway leaves a mixed slot.
- [C] State is serialized **before** the screenshot wait (`:1099-1135`, `:1148`), so a frozen game gives a consistent save.
- [C] The screenshot reads Daggerfall's own screen (`:1150-1152`), which will be empty or wrong with 3D drawing off.
- [C] Daggerfall has no autosave. `autoSaveName` is declared and never used (`:44`).
- [C] `LoadGame` destroys live state first (`:1335-1338`). If it stops early or throws, `loadInProgress` stays true and **every later load is ignored** (`:406`, `:1375`, `:1407`, `:1548`).
- [C] `LoadGame` prefers cached save data (`:1341`, `:1371`). The cache is cleared only after a successful load (`:162-165`). If the player declines a mod warning and a different save is then loaded directly, it would mix the cached save data with the other save's files.
- [C] Death runs a timer, then `TitleMenuFromDeath`, which wipes the session (`PlayerDeath.cs:89-94`, `StartGameBehaviour.cs:325`).

### Doom saves

- [C] All save and load entry points reduce to four places: `G_SaveGame`, `G_DoAutoSave`, `G_LoadGame`, and `DoReborn`. Menu, quicksave, and console commands all call the first or third.
- [C] Death in single player **loads the last save or restarts the map on its own** (`g_game.cpp:1799-1813`). The `PlayerRespawning` event is not reached on that path, so this needs an engine gate.
- [C] `G_DoSaveGame` writes the target file directly (`g_game.cpp:2540`, `writezip.cpp:185`), so stock saves are not atomic.
- [C] Autosaves and rotating quicksaves use global names, `autoNN` and `quickNN` (`g_game.cpp:2312`, `:2355`). Two characters would overwrite each other's.
- [C] `-savedir` gives a separate save folder with no per-game filter (`savegamemanager.cpp:634-638`).
- [C] The save list silently skips saves from another IWAD or a newer version (`loadsavemenu.cpp:190-210`). A player could think those saves vanished.
- [C] `TryRunTics` returns before `G_Ticker` while `pauseext` is set (`dd_bridge.cpp:3-4`), so a frozen save must run from the bridge pump.
- [C] **F9 means opposite things:** Daggerfall quicksaves on F9 and quickloads on F11 (`InputManager.cs:1031-1032`). Doom quicksaves on F6 and quickloads on F9 (`doommenu.cpp:492`, `:547`).

## 3. Player flow

| Moment | What the player sees | Owner of the step |
|---|---|---|
| **First launch** | Doomerfall title. If Daggerfall needs setup, its setup wizard appears in the overlay. | Launcher starts both. Daggerfall runs setup. |
| **Title** | New Game, Load Game, Options, Quit. New and Load stay disabled until Daggerfall is ready. | Doom |
| **New game** | Daggerfall's character creation and cinematics inside Doom. Backing out returns to the title. | Daggerfall creates. Doom shows. |
| **Entering the world** | Loading screen, then both games start together. | Daggerfall names the place. Doom loads it and confirms. |
| **Load** | Doom's load menu shows only valid Doomerfall saves, with character, location, and date. | Doom lists and validates. Daggerfall restores first. |
| **Manual save** | Doom's save menu. A short freeze. Refusals show Daggerfall's reason. | Daggerfall approves. Doom packages. |
| **Quicksave** | Saves at once to this character's rotating quick slot. | Same |
| **Autosave** | Happens on location arrival, per the owner's earlier decision. Skipped if Daggerfall refuses. | Doom triggers. Daggerfall approves. |
| **Death** | Daggerfall decides the death. Doom plays the death view. What follows is **[O] question 2**. | Daggerfall |
| **Return to title** | Doom's End Game option resets both games to the title. | Doom asks. Daggerfall resets. |
| **Quit** | Doom's quit prompt, then both close through the launcher. | Doom and launcher |
| **Crash** | Both close. The last committed save is untouched. Leftover temporary files are removed on next launch. | Launcher and save code |

## 4. Bridge messages

All transaction messages carry a `txn` ID, and receivers ignore duplicates.

| Message | Direction | Purpose |
|---|---|---|
| `df_phase`: boot, setup, menu, loading, play, dead | DF state | Lets Doom enable menus and gate actions |
| `OpenDfUi(new_game)` | UZ to DF | Opens character creation |
| `UiClosed(result)` | DF to UZ | Reports backing out |
| `WorldEnter(txn, reason, place)` | DF to UZ | Doom loads this place. Position data can use a bulk slot. |
| `WorldReady(txn)` / `WorldFailed(txn, reason)` | UZ to DF | Doom has placed the player, or could not |
| `Resume(txn)` | DF to UZ | Both start together |
| `SaveRequest(kind, slot)` | UZ to DF | Manual, quick, or auto |
| `SaveBegin(txn)` / `SaveRefused(reason)` | DF to UZ | Daggerfall's decision |
| `SaveBarrier(txn)` | UZ to DF | Doom has frozen. All earlier Doom events have been sent. |
| `DfPrepared(txn, files, bytes)` / `SaveAbort(txn, reason)` | DF to UZ | Daggerfall's files are staged. All earlier Daggerfall events have been sent. |
| `SaveDone(txn, ok)` | UZ to DF | File committed or failed. Both resume. |
| `LoadBegin(txn)` | UZ to DF | Validated files are staged |
| `DfLoaded(txn)` / `LoadFailed(txn, reason)` | DF to UZ | Daggerfall restored, or could not |
| `UzLoaded(txn)` | UZ to DF | Doom restored. Daggerfall then sends `Resume`. |
| `ReturnToTitle(txn)` / `TitleReady(txn)` | UZ to DF, DF to UZ | Clean reset |
| `PlayerDied`, `PlayerRevived` | DF to UZ | Already in contract section 5 |

### Save sequence

1. Doom sends `SaveRequest`. Daggerfall checks that it is in play, not loading, not dead, and that `IsSavingPrevented` is false.
2. Daggerfall sends `SaveBegin`. Doom finishes its tic, sets `pauseext`, and sends `SaveBarrier`.
3. Because the queue is ordered, once Daggerfall reads the barrier it has applied every earlier Doom event. It pauses and writes its save to a fresh staging folder.
4. Daggerfall sends `DfPrepared`. Doom applies any earlier Daggerfall events.
5. Doom writes `name.zds.tmp` with its own data, the Daggerfall files, and the manifest, then flushes and reopens it to verify.
6. **Commit point:** Doom atomically replaces `name.zds`. Any failure before this leaves the old save intact.
7. Doom sends `SaveDone`. Both resume, and staging is deleted.

If either side does not respond within 10 seconds, the save aborts and the old file stays.

### Load sequence

1. Doom freezes and validates the file **before anything is destroyed**: zip checksums, manifest, Doom version, and required WADs.
2. Doom extracts the Daggerfall files to staging and sends `LoadBegin`.
3. Daggerfall restores from staging and sends `DfLoaded`, publishing HP.
4. Doom loads its half and applies Daggerfall's HP, then sends `UzLoaded`.
5. Daggerfall sends `Resume`.

After step 3 starts, the live session is gone. A failure at that point returns to the title with a message. The save file is never changed by loading.

## 5. Keeping saves matched

- **Location:** the launcher passes `-savedir <Doomerfall saves>`. Normal Doom saves and the player's real Daggerfall saves are never touched.
- **Manifest** (`doomerfall/manifest.json`): format version, campaign ID, save kind, character name and level, location, in-game date, Daggerfall version, UZDoom save version, and mod manifest hash.
- **Campaign ID:** a GUID created at New Game and stored in Daggerfall's data. It keys the auto and quick slots, such as `<campaign>-quick00.zds`, so characters do not overwrite each other. Character names are not unique.

| Save found | Behavior |
|---|---|
| Valid bundle | Offered |
| Normal Doom save | Not offered. It lives in a different folder. If copied in, it has no manifest and is hidden. |
| Normal Daggerfall save | Not offered. Importing is **[O] question 5**. |
| Bundle with damaged contents | Listed as unusable, never loaded |
| Bundle from a newer build or another IWAD | Listed as unusable with the reason, instead of silently vanishing |
| Doom half too old, Daggerfall half fine | Unusable for now. The Daggerfall half stays in the file, so the future ledger rebuild in contract section 16.1 can recover it. |
| Leftover `.tmp` or staging | Removed at launch |

## 6. Regular WADs

- The gate is a new launcher flag, `--flow`, which passes `-dfflow` to UZDoom.
- `-dfbridge` alone must not enable it, because today's bridge demo and tests run E1M1 over the bridge.
- Without `-dfflow`, the four save gates, the main menu, and death behave as stock. UZDoom started directly, or the launcher with `--no-bridge`, is unchanged.
- Portal maps inside a Doomerfall session would use unified saves. That detail belongs to the portal design in the backlog.

## 7. Alternatives

### Save storage

| Option | Advantages | Disadvantages |
|---|---|---|
| **Single bundled `.zds` (recommended)** | One atomic commit, no orphans, delete and copy just work, existing menu lists it | Doom packages Daggerfall's files. Changes the wording in `architecture.md`. |
| Slot folder with generations and a `CURRENT` pointer | Also atomic, keeps plain files, closest to the architecture text | More code, needs a custom listing, delete, and cleanup |
| Paired files plus manifest (contract 16.2) | Small change | Two commits, so a crash can leave a mismatch. Needs repair logic. |
| Swap whole folders | Simple idea | Windows cannot atomically replace a non-empty folder, so there is a crash window |

### Save and load menu

| Option | Advantages | Disadvantages |
|---|---|---|
| **UZDoom's existing menus, rerouted (recommended)** | Almost no UI work, works without the overlay, gamepad support, thumbnails from the real view | Looks like Doom rather than Daggerfall |
| Daggerfall's real save window in the overlay | Authentic | Needs the overlay, its screenshots break with 3D off, adds a second save path to protect |
| Custom ZScript menu | Full control | Most new UI to build and maintain, for little gain at MVP |

The overlay remains required for character creation either way.

## 9. Differences from bridge contract section 16

- Daggerfall writes first and Doom writes the final file, instead of Daggerfall storing a Doom blob.
- A single file replaces the separate blob and `DoomerfallManifest.json`, which resolves gap G7 for Doomerfall saves.
- The barrier runs in both directions, so events in flight are not lost.
- Validation happens before Daggerfall's destructive load.
- The contract's snapshot and ledger split still stands. The ledger would live in Daggerfall's data inside the bundle.

## 11. Questions for the owner

1. Do you approve the single bundled save file and reusing Doom's save and load menus? Recommended. The main alternative is a slot folder with Daggerfall's real save window, which feels more like Daggerfall but needs more work and depends on the overlay.
2. What should happen after the player dies? Recommended: Doom's death view, then a screen with Load Last Save, Load Game, and Main Menu. Alternatives are Daggerfall's death video then the title, or an instant Doom-style reload.
3. How should New Game choose Doom's player class and difficulty, which Doom normally asks for before starting? Recommended: one difficulty prompt after character creation and a fixed default class until class mapping is designed.
4. Which quick keys should Doomerfall use, and should quitting save automatically? Recommended: keep Doom's F6 and F9 with a load confirmation, because Doom owns input, and do not save on quit.
5. Should existing Daggerfall saves be importable into Doomerfall? Recommended: not for MVP. It needs the world ledger so Doom can rebuild the location.

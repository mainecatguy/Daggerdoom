# monsterhitbox: monsters narrower for movement only (run 20261124-212938)

Continues `work/notes/20261124-210422.md`. That run narrowed monsters on Daggerfall maps by shrinking their radius,
which also shrank their hitboxes by 34%. Owner (2026-11-24): monsters must be narrower for movement collision only.
Their hitbox, and how hitscan, projectiles, splash and melee hit them, stays stock. Only on Daggerfall maps. A small
engine change is fine. Bigger monsters that still fit no open doorway are accepted. The player is not changed here.

## Plan

1. Leave `radius` stock (Doom uses it for every hit test) and add a movement width used only by movement collision.
2. Put the rule and the one "is this a Daggerfall map" test for monsters in the engine. The mod stops resizing.
3. Keep everything that sizes bodies ahead of time (placer, planner, door scripts, door check) on the movement width.
4. Prove: hits at the stock edge on Daggerfall maps, regular maps unchanged, door checks and placement as in the last run.

## Design

- `AActor::MoveRadius()` (`UZDoom/src/playsim/actor.h`, inline): `radius × DD_MonsterMoveScale` for a monster
  (`MF3_ISMONSTER`, not a player, not a missile, not a charging Lost Soul), otherwise `radius`. Off Daggerfall maps the
  scale is exactly 1, so the result is bit-for-bit `radius` and stock maps behave exactly as before.
- `DD_MonsterMoveScale` and `DD_OnDaggerfallMap()` live in `UZDoom/src/dd_monsters.cpp`. `DD_BodiesBeginMap` sets the
  scale as each map starts, before its things spawn (called from the existing `DDTreadmill_BeginMap` hook in
  `P_SetupLevel`, so no new line in vendored setup code). This runs for new maps, saves and hub returns.
- Movement paths that now use `MoveRadius` (`p_map.cpp`, all marked `[Doomerfall]`): `P_CheckPosition` (line box and
  thing search), `P_FindFloorCeiling`, `P_TeleportMove`, the portal-line box, wall sliding (`FSlide::SlideMove`), and the
  dropoff check in `P_NewChaseDir` (`p_enemy.cpp`). Body-against-body distances use `DD_MoveBlockDist(mover, other)`:
  both movement widths, unless the mover is a missile or a charging Lost Soul, which use both stock radii. Used in
  `PIT_CheckThing` (and its "already overlapping, let them separate" test), `P_TestMobjZ`, `P_TeleportMove`,
  `P_PlayerStartStomp`, and `P_FindAbove/BelowIntersectors`.
- Untouched, so hits stay stock: `P_LineAttack` and hitscan traces, a missile's own `P_CheckPosition` (its target's stock
  radius), `P_RadiusAttack` (splash), melee range checks, autoaim, blockmap linking (stock is a superset of the narrow
  box, so the narrow thing search still finds everything), polyobjects, bouncing.
- ZScript natives on `Actor` (`actor.zs`, `vmthunks_actors.cpp`): `DD_MoveRadius()`, `static DD_MonsterMoveScale()`,
  `static DD_OnDaggerfallMap()`.
- Mod: `DoomerfallBodies.zs` is now a static helper class (no event handler, removed from MAPINFO). `MonsterScale()` and
  `OnDaggerfallMap()` return the engine's values, so the planner (`EncounterBudget.zs Fits`) uses the same rule.
- Placer (`dd_encounter_placer.cpp`): reads `DD_MonsterMoveScale` directly. Its probe is flagged as a monster (so lines
  that block monsters block it), so it now gets `radius = r / scale` to keep its movement width at `r`. Without this it
  would have been narrowed twice.
- `dd_monsters.cpp SpawnMook`: the spawn-time narrowing call (`NarrowNow`) is removed. The width now applies from the
  first moment a monster exists, so the "wide for one tic" problem from the last run cannot happen.
- Door runtime (`tools/dungeon_converter/door_objects.zs`, baked into generated door packages): `Clear()` measures
  bodies with `DD_MoveRadius()`, so a door waits only when it would really touch a body's movement box.
- Door check (`door_check/zscript.zs`): `DFTestBody` is the player stand-in. It is flagged as a monster, so it now sizes
  itself so its movement width is 10.5. `WidestThrough` reports movement widths. `DTMONSTER` prints both
  `radius=` and `move=`. `action_regress.py monster_doors` now requires `radius=20.000 move=13.125`.

### One source of truth

Monster rules now have one test, in the engine (`DD_OnDaggerfallMap`), exposed to ZScript. The player-width handlers
are a different matter: they are baked into generated packages (`PlayerScale.cs` with its `df_playersize` CVar,
`CityExport.cs` twice, `gen_overworld.py`). The town cache has no converter version check, so changing the generators
would not reach already cached locations, and the goal says not to change the player here. They are left as they are.
A later change could make the generators call `Actor.DD_OnDaggerfallMap()`, so that new packages share the test.

## Known gaps

- Monsters' sprites and hitboxes are now stock while their movement boxes are narrower. Two monsters can stand closer
  than their hitboxes, so a shot can hit the nearer one where the sprites overlap. That is normal Doom behaviour for
  overlapping sprites. Play-test item 2.
- A monster that crowds the player (narrow body against a 10.5 player) stands closer than before. Melee reach uses the
  stock radius, so monsters can hit from slightly farther away relative to how close they stand. Play-test item 3.
- `MoveRadius` reads the global scale, not a per-level value. Only the primary level sets it, which is all Doomerfall uses.
- Polyobject blocking (`po_man.cpp`) still uses the stock radius. Daggerfall maps use no polyobjects for doors (doors are
  `DFDoorBlocker` actors).
- Saves made with the previous branch build (radius actually shrunk) would keep shrunk radii. That build was never merged.
- The other session's untracked files `UZDoom/src/playsim/dd_bodies.cpp/.h` (see below) are still in the worktree. They
  are not in CMake or in any commit. They should be deleted, because they would clash with `DD_MonsterMoveScale` if
  they were ever compiled.

## Failed approaches and notes

- The first projectile hit test always read as a miss, even on E1M1: a dormant (`Deactivate`d) monster takes no damage,
  so the health check never moved. The test now records contact through the missile's `SpecialMissileHit`, which
  `PIT_CheckThing` calls exactly on collision.
- A second Claude session (`worktree-22`) was working on the same goal in this worktree. It wrote
  `playsim/dd_bodies.cpp/.h` and edited `g_level.cpp` and `CMakeLists.txt`. We coordinated: it backed out its tracked
  edits and stopped. Its delete permission was refused, so its two untracked files remain. I left them alone rather than
  delete files for a session whose own delete was refused. Its review notes (the placer probe and `DFTestBody` being
  flagged as monsters, the remaining radius sites, and the duplicated map test) were all checked and handled above.

# Fix the in-dungeon test harness, then verify enemy drops

Branch `agent/harness-20261123-223511` (from `integration`). Demo: `D:\dev\DoomDaggerfall-loop\review\dungeon-harness-drops\play.bat`.

## Result

- **Cause:** a bug in the test script, not in the game, the machine, or shared data. The presave mode added near the end of the monster deaths work put this in `MDHarness.WorldTick`, inside the `switch`:
  `if ("normal" == "presave" && !st.saved) { ...; break; }`
  In a normal run, the condition is a comparison of two literals, so it folds to a constant false. That constant-false `if`, holding a `break` inside the `switch`, made UZDoom 5.0.3 never run the handler's `WorldTick`. The route waited at the town door until the timeout. Presave runs compare `"presave" == "presave"` and kept working, which hid the problem: the last passing normal run (`stock4`, 20:29) used the harness from before the presave change, and the passing runs after it (`pre5`, `preload5`) were presave runs.
- **Fix:** the mode is now a field set in `OnRegister`, so the condition is no longer a constant (`tools/monster_deaths/harness.zs`). The harness also prints `MDSTATUS` (step, timer, map, Daggerfall phase) every 10 seconds, so a stuck route says where it stopped.
- The drops verification now passes in the dungeon, stock and with DRLA (below).

## How it was found (plan as it went)

1. Read the drops notes and the harness. Compared the failing `baseline` (22:10) and the drops `final5` logs with the passing `pre5` (20:31) log. Same `uzdoom.exe` (20:27) and the same data files.
2. Reproduced it at once with the old monster-deaths build (`run probe1`), with no other games running, so contention was not the cause. Daggerfall reached play (phase 3) in every run.
3. Probes, each a real bridged run (logs in `review\monster-deaths\run\log-probe*.txt`):
   - `OnRegister` and `WorldLoaded` of `MDHarness` ran (probe2). `WorldTick` never did, even with the handler ordered first (probe4) or made static (probe7).
   - A thinker spawned from `WorldLoaded` did tick, and Daggerfall's phase reached 3 (probe9). The game's own `DDOverworldSize.WorldTick` ran: a radius set to 20 went back to 10.5 on the next tic (probe10).
   - A tiny `MDTiny` handler in the same pk3 ticked, while `MDHarness`, with the same print as its first line, did not (probe11). So the problem was inside `MDHarness`'s code, not event dispatch.
   - Diffing the passing `stock4` harness with the current one showed only the presave block. Making the mode a runtime value fixed it (`run fixed1`: `MDDONE passed`).

## Failed approaches and side findings

- **The drops lane's "the handler never ran" was right, but the guesses (other games, Unity builds, shared data) were wrong.** The old demo failed the same way because it was run with the current harness, not because of anything outside it.
- **The `baseline` run at 22:10 also had a slow Daggerfall** (about 4,500 frames in 70 s, and areas loading 17 s late). That alone could fail a route, but it was not the cause here: the harness fails the same way on a quiet machine.
- **A ZScript compile error in a test pk3 does not reach `+logfile`.** UZDoom stops at `LoadActors` with a hidden dialog, and the run just times out. Some probe versions hung like this with the JIT on and ran with `+vm_jit 0` (probe9). I did not track that down. If a harness run's log ends at `LoadActors`, check the script first.
- `git merge` of the drops branch was refused in this session, so the drops game was not merged here. The drops build already staged in `review\real-enemy-drops` (built from `agent/drops-20261123-212059`, final game and not the audit build: no `DoomerfallDropAudit` in `Assembly-CSharp.dll`) was tested with the fixed harness. `tools/real_drops/` and the `EXTRA_DF` hook were copied unchanged from the drops branch, so a later merge should not conflict.

### Things the runs showed

- **The test quest's site is random.** `-dfmonsterquest N0C00Y12` sometimes picks "Daggerfall with 6 spawn markers" instead of Privateer's Hold (7 of 21 fresh runs tonight). Then no quest foe is in the dungeon, `DDMON test kill found nothing` is printed, and the route quietly kills a placed monster instead. The route still passes, but that run did not test the quest kill. Read the `df ... test site` line before counting a run as a quest kill test. I did not change this, because it is in Daggerfall-side test code.
- **Loading a save from before a kill re-rolls the drop** (`v-pre` Gold Pieces, `v-preload` Pine Branch). This follows from rolling at death. The drops notes record that design, so this is a finding, not a bug.
- `Player.log` always has one `NullReferenceException` in `DaggerfallUI.SetupSingleton` at startup. It is in the old build too, and it is unrelated.

# The fist is always on hotkey 1 (run 20261126-192745)

Goal (owner, 2026-11-26): the player always has the fist. It sits on hotkey 1, cannot be unbound or replaced there,
and is not an item in Daggerfall's inventory.

## Base

Card 01 of this lane (no DRLA class, `DoomerfallPlayer`) is on commits `a0a0437f`, `806779a9`, which are not on this
branch. Cherry-picking needed approval that an overnight run cannot get, so this work does not depend on them and
touches different files (except `tools/new_game/run_new_game.py`, which card 01 does not change). The fist logic
works with any Doom player that has a fist: stock `DoomPlayer` (`Fist`), every DRLA class, and `DoomerfallPlayer`
(all carry `RLFist`). DRLA's `RLFist` replaces `Fist` (`actors/weapons/standard/Fist.txt`, `replaces Fist`, not
derived from it), so Doom finds the fist with `Actor.GetReplacement("Fist")`.

## How it works

- Doom already keeps the fist: `DoomerfallGuns.zs` `PickupFor` returns "" for a weapon with no pickup and no world
  sprite, so the fist is never stashed, adopted, or sent to Daggerfall. It was never an inventory item. That stays.
- Daggerfall's hotkey table (`DoomerfallHotkeys.cs`) now always holds a fist square at key 1, plain square 1 (index 0).
  It has kind `'f'`, no item UID, and is put back by every reset (new game, load). It is not saved, because it is implicit.
  `Assign` and `Clear` refuse that square. The popup shows "FIST" there, has no REMOVE button under it, and clicking it
  says "The fist is always on hotkey 1."
- Pressing 1 (Doom's slot key on a generated map, already routed to Daggerfall as `DFB_KIND_HOTKEY`) reaches the fist
  square and sends `DFB_KIND_GUN_EQUIP` with the new flag `DFB_GUN_FIST` (bridge header; bindings regenerated).
  `DoomerfallGuns.zs` raises the fist (gives it first if it is somehow missing). No gun changes hands: the active gun
  stays in Doom, lowered, as Doom already handles fists (`GUN_SELECT` "perhaps lowered for the fists"). Pressing the
  gun's key raises it again with `GUN_SELECT`. Pressing 1 again cycles to key 1's other plain squares, if any.
- Old saves: an item a save had on key 1 square 1 moves to the next free plain square of key 1, or loses its hotkey.

## Engineering calls (within the owner's decision)

- **Only the fist's square is fixed. Key 1's other squares (plain 2 and 3, Ctrl+1, Alt+1) stay assignable.** Doom's
  slot 1 holds the fist and the chainsaw, and pressing 1 again cycles. The owner said the fist "sits on hotkey 1 and
  cannot be unbound or replaced there", not that key 1 holds only the fist. Asked in questions.
- **The fist does not count as "a key with hotkeys"** for the auto-hotkey rules (a taken gun goes on its free slot key;
  the starting gun goes on key 2 when the table is empty). Otherwise a slot-1 melee weapon (chainsaw, DRLA melee) could
  never be auto-placed and the starting pistol would no longer land on key 2. A slot-1 gun goes on key 1's square 2.
- **The active gun stays in Doom while the fist is up**, instead of going back to Daggerfall. This is how Doom already
  behaves when a gun runs dry and Doom switches to fists. It keeps the gun's live magazine in Doom, and raising it again
  needs no state round trip.
- The fist uses Hand-to-Hand: already done (`342e8f13`, "fist is Hand-to-Hand").

# Loading holds for long operations (run 20261127-025856)

Goal: long operations pause the game behind a loading message, keep the window responsive, and resume when done.
Cases: (1) New Game or plain load into an unconverted dungeon, (2) the first door press on an unconverted dungeon,
(3) a slow dungeon spawn on re-entry.

## Plan (as it went)

1. Read the existing arrival freeze (`DD_BridgeArrivalFreeze`, `DD_BridgeHoldFrame`, `DD_BridgeDrawLoading` in
   `dd_bridge.cpp`). It already freezes the playsim after a map change and shows "Loading..." after 1 s, but it only
   covers the arrival wait. The conversion waits ran in the live town.
2. Generalize it into one named hold (`UZDoom/src/dd_loading.cpp`) that any system can take and release. Wire it into
   the three places the arrival freeze already uses (P_Ticker freeze, frame hold, loading draw) and into saving.
3. Use it for the conversion wait (treadmill) and for big dungeon spawns (dd_monsters).
4. Test with a test-only file (`dd_loading_test.cpp`, `-ddloadingtest`) in paired runs of each case. Check E1M1.

## What was built

- **`dd_loading.cpp`**: `DD_LoadingHold(name, on)`, `DD_LoadingActive`, `DD_LoadingShown`, `DD_LoadingAgeMs`. A level
  load drops every hold (`DD_BridgeLevelLoaded`). Logs to the bridge log only.
- **While any hold is active** (no new hooks in vendored files except one in `G_SaveGame`):
  - `DD_BridgeArrivalFreeze` (already called from P_Ticker) freezes the primary level: no player think, thinkers,
    WorldTick or sector specials. `DDTreadmill_Tick` and network events still run, so the conversion, door entry and
    Daggerfall's answers proceed.
  - `DD_BridgeHoldFrame` / `DD_BridgeDrawLoading` draw a black "Loading..." screen every frame at once (no 1 s delay
    for holds), now with the Daggerfall window, console and menus on top. The window stays live and the player can
    quit or open the menu.
  - Saving is refused: `SaveReady()` (bridge saves and autosaves wait) and `G_SaveGame` (menu save and quicksave; the
    quicksave key otherwise bypasses the bridge) print "Cannot save while loading."
- **Conversion wait** (`dd_treadmill.cpp` `HoldWhileConverting`, called at the top of `DDTreadmill_Tick`): holds while
  a pressed door (`pendingDoor`), New Game / plain load dungeon (`dungeonRequest`) or plain-load building
  (`buildingRequest`) waits in a town. It keeps holding through the door's handoff until the new map loads (first run
  showed the player drifting 0.47 units in the ~300 ms between door entry and map load otherwise). After 180 s it gives
  up as a failed conversion does ("This door will not open."), because the frozen player can no longer walk away to
  cancel. The New Game / plain load 60 s deadline is extended while the hold lasts (up to 180 s): before, a 90 s
  conversion on a busy PC failed the New Game.
- **Big dungeon spawn** (`dd_monsters.cpp` `SpawnMayRun`): the plan-and-spawn runs synchronously on the main thread.
  When it is expected to be slow, it takes a hold, waits one tic so a frame with the message is presented, then runs.
  Expected slow = this dungeon's spawn took >= 250 ms earlier this session, or (first visit) markers x area level >=
  1000. Data: Privateer's Hold 42 markers, level 1 = 321 ms (91 mooks), level 30 = 988 ms (2,040 mooks); a level-17
  spider nest, 55 markers = 31 ms. Small spawns stay as before (no flash).

## Other long operations (listed, not covered)

- **Bundled save** (Daggerfall blocks 2-3 s): Doom already pauses (`pauseext`) and keeps drawing the paused frame, so
  the window is live and nothing moves. A "Saving..." text would need a per-hold message; not done.
- **Bundled load**: runs behind the existing load flow (title / load screens). Not changed.
- **Map and town building** (town conversion on the overworld, `GetBlocking` in `BeginTravel`): towns convert in the
  background while the overworld stays playable, which is intended. `DDTownCache::GetBlocking` during travel can block
  the main thread; it was not measured tonight. The same `DD_LoadingHold` + `DD_LoadingShown` pattern as the spawn
  gate would fit if it turns out slow.
- **Arrival wait** after every map change is the existing freeze; unchanged except it now also draws console, menus
  and Daggerfall windows when it shows "Loading...".

## Known gaps

- Daggerfall keeps running during a door-press hold (case 2): its clock advances and its own effects (poison,
  disease) can still tick, as they already do while Doom's menu is open. In cases 1 and plain load Daggerfall is held
  by the New Game flow anyway. Pausing Daggerfall would need a new bridge message; see questions.
- A Daggerfall window (inventory etc.) can be opened during a hold through its hotkeys; it now draws over the
  Loading screen instead of being invisible.
- "Opening..." and "Cannot save while loading." go to the message log; the Loading screen does not show them.

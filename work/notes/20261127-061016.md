# Daggerfall menu text at full resolution (run 20261127-061016)

## What was actually wrong

Not 320x200 itself. The chain is:

1. Daggerfall Unity draws its art at the classic 320x200 scale but its text (SDF fonts, `SDFFontRendering=True`) at the
   window's own pixel resolution.
2. In a bridge session Daggerfall's window is fixed by the launch line to 1280x800 (`DoomerfallWindow.DefaultWidth/Height`,
   and every demo `play.bat` passes `-screen-width 1280 -screen-height 800`). The UI surface Doom shows is that window
   (`DoomerfallUi.ChooseSurfaceSize`, logs: `ui: menu 2 opened, surface 1280x800`).
3. Doom stretches the surface to its own screen (`dd_bridge.cpp` `UiRect` / `DD_BridgeDrawUi`) with nearest filtering.
   At any Doom window bigger than 1280x800 the text is upscaled by a non-integer factor and turns blocky; the art,
   already chunky, looks the same. At 1920x1080 fullscreen (the owner's Daggerfall Unity settings.ini says 1920x1080) the
   factor is 1.35.

Evidence (before the fix, `review/menu-text-runs/`): `base-show` (Doom 1252x721 client) shows "15.70 / 75" sharp;
`big-before` (Doom 1892x1121) shows the same text with stair-stepped pixels. Crop sheet: see Screenshots below.

## Fix

Doom tells Daggerfall the size it will show the UI at, and Daggerfall renders at that size.

- `bridge/doomerfall_bridge.h`: `dfb_ui_command` gains `screen_width`, `screen_height` (UI_OPEN; 0 = unknown, old behavior).
  Bindings regenerated (`python bridge/generate_bindings.py`).
- `UZDoom/src/dd_bridge.cpp` `SendUiCommand`: fills them from `screen->GetWidth()/GetHeight()` (one line; bridge sessions only).
- `DoomerfallWindow.MatchDoom` (Daggerfall): on UI_OPEN, resizes Daggerfall's (hidden) window to Doom's size, clamped to
  the shared surface limit `DFB_SURFACE_MAX_W/H` (1920x1200) keeping Doom's aspect, so no extra resample happens on
  Daggerfall's side. Logged to df.log: `ui: window AxB resized to CxD for Doom's ExF screen`.
- `DoomerfallUi`: the capture loop re-picks the surface size whenever the window size changes (it previously only did so
  in one branch), and logs `ui: surface WxH for a WxH window`.

Art keeps its classic look because Daggerfall Unity itself scales art from 320x200; only the text gains pixels.

## The 320x200 / fixed-size audit (where Daggerfall's UI reaches Doom)

| Place | Assumption | Status |
|---|---|---|
| Daggerfall window in bridge sessions (`DoomerfallWindow`, play.bat `-screen-width 1280 -screen-height 800`) | fixed 1280x800 regardless of Doom | **fixed**: resized to Doom's screen on each menu open |
| `DFB_SURFACE_MAX_W/H` 1920x1200 (shared mapping, three BGRA frames) | screens above 1920x1200 (1440p, 4K) still get an upscaled surface | **known gap**: raising it grows the mapping (4K: ~100 MB) and changes the ABI; left for the owner (question) |
| Doom's draw of the surface (`DD_BridgeDrawUi`) | nearest filtering on upscale | unchanged; only matters above the surface cap now |
| Doom HUD text from Daggerfall (`DFB_KIND_HUD_TEXT`, INFO_TEXT, LOOK_TEXT) | drawn by Doom with its own fonts at Doom's resolution | not affected (text, not pixels) |
| Quest faces (`dfb_face.display_width/height` "in 320x200 HUD units") | layout units only; pixels are Daggerfall's face art | not affected (art) |
| Test tools (`tools/inventory_menu` `point()`, `tools/menu_text`) | native 320x200 -> surface mapping for clicks | test only, correct |
| Doom resized while a menu is open | Daggerfall keeps the size it got at open | minor gap: fixes itself at the next open |

`menufont` card: not run yet in this branch (no font/texture pack code found). Nothing here conflicts: font packs draw
through the same SDF path, so they also gain from the larger window.

# Locked doors: Doom owns the live lock (run 20261126-131954)

Redo of the door bridge step as the approved review describes (`work/notes/20261126-lockpick-review.md`). Earlier runs:
`20261125-073553.md`, `20261125-202715.md`, `20261126-114215.md`.

## Plan

1. Bridge: drop the locked-list protocol and `DOOR_ACTION`; keep `DOOR_USE` (now the lock ask, carrying Doom's lock
   value), `DOOR_STATE` (answers and facts), `LOCKPICK`, `DOOR_TEXT`; add `DOOR_FACTS` (193, reused number).
2. Doom (`door_objects.zs`): `DFDoor.lockValue` is the live lock, with Daggerfall's meaning (0 open, 20+ magic).
   `Toggle` runs `DaggerfallActionDoor.ToggleDoor(true)`'s order in one place. Action records 16/17/18/20 change it
   locally with `DaggerfallAction`'s rules. A pick hit unlocks and calls the same toggle.
3. Daggerfall (`DoomerfallDoors.cs`): answers the ask from the lock value in it; does the pick bookkeeping; keeps the
   doors the player picked open as a per-dungeon fact in a ledger saved with the game.
4. Doom-only harness for picking, refusals, levers and the door order. Paired runs for take, load (plus leave and
   re-enter), New Game. Stock check. Notes, manual, demo.

## What changed and why

### Who owns what

- **Doom**: the live lock of every door on the current map (`DFDoor.lockValue`, `armed`). Both are actor fields, so
  Doom's save snapshot keeps them. Action records change them with no bridge message.
- **Daggerfall**: the rules (chance, labels, magic refusal, pick breaking, skill tally), the player's picks, and one
  permanent fact per dungeon: the LoadIDs of doors the player picked open (`DoomerfallDoors.json` beside the other
  ledgers in the bundled save; cleared on New Game and on a plain Daggerfall load).
- Daggerfall's hidden `DaggerfallActionDoor.CurrentLockValue` is no longer read or written. Only the Lock and Open
  spells write it (out of scope, card 01); they will need a "set lock" message to Doom later.

### Arming: no unopenable doors without Daggerfall

Doors start unlocked. After Doom builds a dungeon map fresh (not from a save), `DFDoorHandler.WorldLoaded` sends
`dfdoor_facts`. In a bridge session `dd_doors.cpp` forwards it (`DFB_KIND_DOOR_FACTS`). Daggerfall waits until it is in
the same dungeon (its MapId equals Doom's space target, as before), then answers `DFB_DOOR_ARM` followed by one
`DFB_DOOR_FACT` per picked door. Doom arms each door at its starting lock and unlocks the picked ones. Without
Daggerfall nobody answers, so a converted map played alone, or a stock WAD, never has a locked door. Action 16 also
locks only armed doors.

This replaces the review's "unlocked bit in the location record's door fact": that record (`DFDoorHandler.Distill/
Restore`) does not exist yet (`work/backlog/location-record.md`). The ledger holds only what Daggerfall decides, the
player's picks, so it can move into the location record when that lands.

### The door order in one place

`DFDoor.TryUse` = `Toggle(user)`, then the record's direct trigger (PlayerActivate). `Toggle` follows
`DaggerfallActionDoor.ToggleDoor(true)`:

- moving: nothing.
- open: door trigger, then close.
- shut: a first-activation DoorText record runs (door trigger) before the lock check; then, if `lockValue > 0`, Doom
  asks Daggerfall (`dfdoor_ask:<id>:<lock>`) and the door stays shut; otherwise the door trigger (unless DoorText already
  ran it), then the swing.

A pick hit (`dflp_result:<id>:hit`, which the engine now also lets through to the mod) sets `lockValue = 0` and calls
`Toggle(player)`, as `AttemptLockpicking` calls `ToggleDoor(true)`: the door trigger runs once, no direct trigger.
`DFDoorListener` now has `IsFirstDoorText`, `DoorTrigger` and `DirectTrigger`; `DFAction` implements them.

### Action records 16/17/18/20 (`DFDoor.RunAction`)

As `DaggerfallAction`: 16 sets 16 if not locked; 17 sets 0; 18, when not fully open, sets 0 and opens; 20, when fully
open, closes and restores the starting lock. Doom's door now really moves, so "fully open" is Doom's state, which also
fixes the old stand-in where Daggerfall's hidden door was never open.

### The ask and the label

- `DOOR_USE` carries the lock value. Daggerfall answers: 20 or more, the magic message (no minigame); no picks,
  "Locked." (card 01); otherwise `DFB_DOOR_PICK` with `CalculateInteriorLockpickingChance` for that value.
- The look label asks `DFB_INFO_DOOR` with the **lock value as the id**, so the label cache is keyed by lock value and
  stays right when a lever changes the lock (the old `DD_LookForgetDoor` is gone). An unlocked door is "Door" with no
  ask.

### Castle Daggerfall foyer doors (the "Wayrest throne room" item)

The code at `DaggerfallAction.cs:263-283` is `CastleDaggerfallMagicDoorsSpecialOpenHack`: Castle Daggerfall
(MapId 1291010263), doors 29331574 and 29331622, magically held, opened anyway when the player teleported into the
dungeon, so they cannot be shut in the throne room. The goal card calls it Wayrest; the code and its comments say
Castle Daggerfall. Handled in the ask: for a magic lock, Daggerfall checks the same conditions
(`PlayerTeleportedIntoDungeon`, MapId, LoadID) and, after the magic message, answers `DFB_DOOR_OPEN`. Doom unlocks the
door and opens it, not as the player's toggle (the hack calls `ToggleDoor()` without the player flag). Same experience
as Daggerfall Unity: the message, then the door opens. Not run for real (Castle Daggerfall is not in the converted test
data); the Doom half (`dfdoor_open`) is in the Doom-only harness.

### Removed

Locked-list protocol (`LIST_BEGIN/END`, `DOORS_REQUEST`, hash poll, `dfdoor_clear`, `dfdoor_lock`, `DD_DoorsResync`),
`DOOR_ACTION`/`OnAction`/`TellLockAction`, the stale-list "open" reply, `DoorOpenedUnlocked` and the `locked`
parameter, `DoomerfallLocks.Find`, `-dflocktestmagic`, `DD_LookForgetDoor`. Kept: Lockpick item and loot, the minigame,
`Chance`/`ApplyAttempt`/`Label` (now from a lock value), labels, converter LoadID and lock export, the paired setup.

### Problems found on the way

- ZScript names are case-insensitive: a method `Swing()` clashed with the constant `SWING` ("Attempt to redefine
  'SWING'"), caught by the Doom-only run. Renamed `StartSwing`. I patched the same rename into the installed
  `ddruntime.pk3` instead of running the whole install again; the converter copies the script verbatim, so the next
  install produces the same file.
- The runtime dungeon's `_doors.pk3` needs `ddruntime.pk3` for the door classes; the Doom-only runner loads both.
- The harness's Use at the closed-door spot misses a swung-open leaf, so the open-door cases call `DFDoor.TryUse`
  directly.

## Known gaps

- Lever-driven lock changes are live state only: after leaving and re-entering, a door is back at its starting lock
  unless the player picked it (then unlocked). A door relocked by action 20 after being picked comes back unlocked.
  The location record (backlog) is where door states belong.
- DoorText records' text is still not shown in Doom (the `doortext` rule request is a diagnostic only), so Doom does not
  hold the door shut on the first click as Daggerfall Unity does when there is text. Unchanged from before.
- Interior and exterior building doors: unchanged, see `20261126-114215.md`.

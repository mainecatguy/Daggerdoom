# Daggerfall publishes the character sheet to Doom (20261123-212059)

## Result
Daggerfall publishes its character sheet through shared memory. Doom keeps a read-only copy. This was proven with both real games (see Proof). One gap remains: the real `-dfflow` character-creation path, which is code-reviewed but not run.

## What is published, and why
Bridge protocol 6. The sheet lives in Daggerfall-owned bulk slot 0 (`DFB_SHEET_SLOT`). It is a flat array of 150 `int32` values, and every index is a `DFB_SHEET_*` constant in `bridge/doomerfall_bridge.h`. A flat array was chosen because the binding generator supports only byte arrays inside structs, and an index table stays readable on both sides. The bulk slot's seqlock means a sheet is always read whole, never torn. The state half (256 bytes) was too small.

| Group | Values | Why Doom will need it |
|---|---|---|
| Header | format, epoch, valid, level | Staleness guard. Level drives many Daggerfall formulas. |
| Vitals | fatigue current/max (Daggerfall's raw units, 64 per point), magicka current/max | HUD bars, spell costs. HP is already in the state half. |
| Stats | 8 base + 8 live | to-hit, damage bonus, speed, carry |
| Skills | 35 base + 35 live, in `DFCareer.Skills` order | weapon skill to-hit and damage, stealth, dodging, and so on |
| Armor | 7 base + 7 live (base + effect armor modifiers, the value `CalculateArmorToHit` uses), plus both modifiers | Damage contract |
| Resistances | 5 base + 5 live elemental resistances, effect-granted roll flag and chance | Elemental damage contract |
| Saving throw inputs | 7 career tolerances, 4 live race flag sets, 3 biography modifiers, magic resist | Lets Doom later reproduce `FormulaHelper.SavingThrow` exactly |

Base excludes active effects and live includes them. Both are published because Doom will apply live values in combat, while a character screen or a future mapping may need base values. The rule is that if it works some way in Daggerfall, it works the same here, so Doom should be able to run Daggerfall's formulas on the same inputs.

Not published: gold, encumbrance (needs an item walk every frame), career and race names, spells, inventory, and quests. These have their own owners or contracts, or Doom does not need them yet.

## When it updates
`DoomerfallSheet.Publish()` rebuilds the array every Daggerfall frame, without allocating, and writes the slot only when a value changed. So level-ups, training, equipment, effects, and drains are all caught with no per-system hooks.

Staleness rules:
- `SaveLoadManager.OnStartLoad` raises the epoch and immediately publishes `valid 0`, before Daggerfall restores the player. `OnLoad` makes it valid again. A failed load stays invalid. The load handshake's `PublishNow` also publishes the sheet, so it is in place before `LOAD_READY`.
- Flow new game: `BeginCreation` sets invalid and raises the epoch. `CharacterPlaced` makes the new character valid with a new epoch. A cancelled wizard restores the old character. A dropped held character goes invalid.
- A non-flow new game (`OnStartGame`, as in the test) raises the epoch.
- A flow session starts invalid, because Daggerfall's blank default player behind Doom's title is not a character.
- Whenever `valid` is 0, every value except format and epoch is zero.

## How Doom reads it
`UZDoom/src/dd_bridge.cpp`: `const int32_t *DD_BridgeSheet()` returns the copy, indexed by `DFB_SHEET_*`, or `nullptr` when there is no session or no valid character. It refreshes on demand, so a caller handling an event always sees the newest sheet. It is also refreshed every frame for logging. Callers must drop anything derived from the sheet when `DFB_SHEET_EPOCH` changes. Nothing uses it for gameplay yet, which is out of scope. There is no ZScript access yet. That can be added when the first consumer exists.

The engine change is inactive without a bridge session, because `RefreshSheet` returns at once when `session` is null.

## Proof (real games)
- `python bridge/test/sheet_test.py` launched both games through the launcher (Doom on DOOM.WAD E1M1, Daggerfall in `-dfsynctest -dfsheettest`, private portable copy). RESULT PASS: Daggerfall published 12 versions, and Doom read all 12 with matching FNV checksums, each 1-8 ms later. Sequence: invalid at boot → character → Archery 4→11 (training) → level 2, Strength 53 → iron helm, head armor 100→65 → Fortify Strength (Strength live 65, base 53) and Resist Fire (roll flag 1, chance 102) → save → Archery 31 → load: `valid 0`, epoch 2, then Archery back to 11 with the effect restored → new character: epoch 3, level 1, Strength 42.
- `python bridge/test/no_session_check.py doom D:\dev\DoomDaggerfall-loop\review\skill-publishing`: stock E1M1 38/38 log lines identical to the baseline exe, DRLA set 2149/2149 identical, `-norun` exit 1337.
- `... no_session_check.py dfu ...`: a normal Daggerfall launch with the bridge DLL hidden ran without any bridge mention. It logged only to its private PortableAppdata.
- Test launches used the registry-isolated "Doomerfall Local" portable copy. Saves went to its PortableAppdata only.

## Failed approaches and fixes on the way
- The first run's Doom log line had a comment that swallowed one argument, so the checksum printed wrong. Fixed.
- The test first waited for `DF_PHASE_PLAY`, which never happens while Doom is on E1M1 outside a Daggerfall map. It now waits for `InGame`.
- A harness comparison bug (a leaked loop variable) reported FAIL on a good run. Fixed.

## Known gaps
- The flow new-game path (`CreationStarted` / `CharacterPlaced` / `CreationCancelled` / `CharacterDropped`) is code-reviewed but was not run. It needs the full `play.bat` flow with the real wizard.
- A non-flow new game publishes the new character's values under the old epoch for the frames between `AssignCharacter` and `OnStartGame`. Only the test uses that path. Real sessions use the flow.
- The log line skips changes to fatigue and magicka alone, so their versions are not compared by the test.
- The Unity build modifies four Addressables assets as a side effect. They were left uncommitted.

# 2026-11-28 05:27 — Doom poison goes through Daggerfall's damage and death rules (Q&A item 52)

## Findings

UZDoom has two poison paths for a player:

1. **ZDoom-style** (`PoisonDamage` / `PoisonDuration` on a projectile or puff): `P_PoisonMobj` stores it on the actor
   and `AActor::Tick` (p_mobj.cpp ~5083) deals each pulse through `P_DamageMobj` with damage type `Poison`. That path
   already ends at `DD_BridgeHpHit`, so it already went to Daggerfall first. No change needed.
2. **Hexen-style** (`PoisonDamage` with `PoisonDuration == INT_MIN`, or ZScript `player.PoisonPlayer`): `P_PoisonPlayer`
   sets `player->poisoncount`, and `PlayerPawn.CheckPoison` calls `P_PoisonDamage(1)` every 16 tics. `P_PoisonDamage`
   subtracted Doom health itself and called `CallDie` when it reached 0. Daggerfall only heard about it at the next
   `DD_BridgeHpThink` ("direct assignment"), and if the hit was lethal in Doom the player was already `PST_DEAD`, so
   `DD_BridgeHpThink` returned early and Daggerfall **never** heard: Doom dead, Daggerfall alive. This is item 52.

No stock Doom, DRLA, DRLA Monsters or DRLAX actor uses poison (grep of `GameMods/ExtractedData` found it only in
ColourfulHell and Schism, which we do not load), so this is a latent hole today, not one players hit yet.

## Change

- `UZDoom/src/playsim/p_interaction.cpp` `P_PoisonDamage`: after the existing Willpower step, the health change and
  Doom death are wrapped in `if (!DD_BridgeHpHit(player, damage, "poison")) { ... }`, exactly like `P_DamageMobj`.
  In a bridge session the hit is sent to Daggerfall as a normal `DFB_HP_HIT`, Doom health is left alone, and death
  comes from Daggerfall's `DFB_HPF_DEAD` through the existing `DD_BridgeHpThink` kill. The pain state still plays.
  `player->attacker = source` moved above the block (nothing in between reads it). Outside a session
  `DD_BridgeHpHit` returns false, so stock behavior is unchanged.
- `DD_BridgeHpHit` takes an optional log label (`"damage"` default, `"poison"`), only for the bridge log.
- Daggerfall applies the hit in `DoomerfallHp.OnEvent` like every other Doom hit. It has no damage types or
  resistances for Doom hits yet; when `damage-types-and-resistances` lands, the poison call site is the one place to
  tag it as Poison (both paths: ZDoom-style already carries damage type `Poison` in `P_DamageMobj`).

## Test

`-dfhptest poison|poisonhit` (test only, `UZDoom/src/dd_bridge_test.cpp`) and `tools/poison_rules/run_poison.py`:
ZDoom-style poison first (hits must reach Daggerfall), then Daggerfall HP is set to 4 and the player is poisoned
Hexen-style (`poison`: `P_PoisonPlayer` 100, ticking 1 per 16 tics; `poisonhit`: one `P_PoisonDamage` of 50 in one
tic). Checks: every poison hit is sent, the player is alive in the poisoning tic, stays alive until Daggerfall reports
death, dies only after that, Daggerfall applied the lethal hit itself (hp -> 0), events in order.

Known gaps:
- The `-dfsynctest` character has no live stats, so Willpower scaling (which already runs on poison before the hook)
  is not exercised here; it was covered by the willpower work.
- Daggerfall applies Doom hits unchanged (no resistances yet), so "its resistances apply" means the poison hit takes
  the same path every other Doom hit takes. Tagging it as Poison waits for `damage-types-and-resistances`.
- Nothing we load deals poison today, so this cannot be seen in normal play.

Failed approaches: the first runs failed only on setup (DFU build had no bridge DLL, then no `Portable.txt`), and
the script first looked for `log-log-<name>.txt` because `+logfile <name>` already writes `log-<name>.txt`; fixed,
and the fatal-error check now also requires the console log to exist.

## How it was measured

`tools/quiet_probe/quiet_probe.py` runs any command and watches its process tree for:

- **shown**: a top-level window shown on screen and not minimized, even for a moment (WinEvent `EVENT_OBJECT_SHOW`)
- **onscreen**: a window found on screen by a 50 ms poll
- **focus**: a window of the tree became the foreground window
- **flash**: a taskbar flash request (`HSHELL_FLASH` from a shell hook)
- **audio**: a Windows audio session of the tree, and its peak meter (above 0 means real sound)

Membership uses process creation times, so a reused pid does not pull in another lane's process. That bug showed up
once and was fixed.

`tools/quiet_probe/self_test.py` checks the probe with signals too small to notice: a 3x3 pixel window shown without
activation, one taskbar flash, and a -60 dB tone, then a silent command. Result: `PASS`.

Limit: sounds Windows plays in the shared "system sounds" session, such as the message box error chime, are not
counted. The old UZDoom crash box used `MB_ICONSTOP`, so it probably chimed. It no longer appears under `-noactivate`.

## Changes

1. `daggerfall-unity-master/Assets/Scripts/Doomerfall/DoomerfallQuiet.cs` (new): with `-dfmute`, sets
   `AudioListener.volume = 0` before the first scene and holds it at 0 every frame. It works with or without a bridge
   session. Without the flag it does nothing. `DoomerfallNewGame.BeginCreation` now uses `DoomerfallQuiet.Volume(1)`,
   so no sound leaks for even one frame.
2. `launcher/main.cpp`, `--minimized` only:
   - adds `-dfmute` for Daggerfall Unity and `-nosound -noactivate` for UZDoom
   - creates the desktop `doomerfall-test-<pid>`, starts Daggerfall Unity there, finds its windows there for the
     graceful close, and closes the desktop at the end
   - leaves UZDoom on the user's desktop, minimized as before, so its rendering is unchanged

   Why a desktop: Unity shows and activates its window when it starts, whatever `STARTUPINFO` asks. The launcher's
   20 ms poll could only re-minimize it afterwards. A window on another desktop can never be seen and never takes the
   user's focus, and dialogs from Unity's crash handler, a child process, land there too. The rejected alternative was
   Unity's `-parentHWND`. It changes how Unity sizes, receives input, and closes, and the launcher would need a message
   pump.
3. UZDoom `i_crash.cpp` and `i_system.cpp`, under `-noactivate` only: no crash dialog and no config retry box.
   Marked `// Doomerfall`.
4. `tools/quiet_probe/e1m1_check.py`: DOOM.WAD E1M1, stock and with the `play_drlax.bat` DRLA set. It runs a `-norun`
   startup check (1337 expected), then 15 s of play under the probe.

Rejected: muting games from outside through Windows' per-app volume (`ISimpleAudioVolume`). Windows remembers that
mute per exe path, so the owner's own play of the same exe would stay muted. It also leaks sound until the session
appears.

## Still disturbing, and why

- **Unity editor builds** show windows and take focus until `quiet_run.py` gains `--desktop` (owner decision, patch
  ready). Builds through the patched copy were silent and invisible.
- **Direct Daggerfall Unity launches** in stock and no-session checks: the window flashes until the same patch is
  applied, and stock builds still play title music. Those tools could pass `-dfmute` once their review builds include
  this change.
- **Taskbar buttons** for minimized UZDoom still appear and disappear on the user's taskbar. Moving UZDoom to the
  private desktop was not tried, because tests depend on its rendering.
- **Tests that do not use `--minimized`** or forget `-noactivate` are not covered. The launcher's normal mode, which
  the owner's play uses, is unchanged.

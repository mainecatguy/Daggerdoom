# 20261124-202337: Hotkeying an item removes its other hotkeys

## Plan
1. In `DoomerfallHotkeys.Assign`, clear every other square holding the same inventory item (same UID) before writing
   the new square. Every assignment path goes through `Assign`: the inventory popup (`DoomerfallHotkeyPopup`), the
   taken-gun rule (`OnGunTaken`), the starting-gun adoption (`OnEquipped`, key 2), and the plain-load starter pistol
   (`BeginPlainStart`). So one change covers manual and automatic assignment.
2. If the moved item is the drawn gun and its old square was the active square, the active square follows it, so
   pressing the new key again cycles from the right place.
3. Save and load: the table is saved as written, so a move survives. An older save that already holds one item on
   several squares is cleaned on load, keeping the first square by hotkey order (keys 1-9, then 0, as `BeginPlainStart`
   orders them).
4. Standalone test `-dfhotkeyuniquetest <dir>` (own file, no hook in the main class; started by
   `RuntimeInitializeOnLoadMethod` like `-dfhotkeyshots`).

## Decisions (engineering calls within the owner's rule)
- "Same item" = same `DaggerfallUnityItem.UID`. Two separate daggers, or two separate potion stacks of one kind, are
  different items and may sit on different keys. A potion stack is one item: moving it moves the whole stack.
- Automatic assignment always places a newly created item (a taken gun, an adopted starter gun, a plain-load starter
  pistol), so it can never collide in practice; it still goes through the same rule.
- Not changed: a consumable square whose stack ran out re-points to the next item of the same kind (`Resolve`). If the
  player had put two separate stacks of one kind on two keys and one runs out, both squares can then point to the
  same remaining stack. That is not the player assigning anything, so I left it; asked the owner (see questions).

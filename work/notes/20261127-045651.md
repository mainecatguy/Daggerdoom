# Hold the Doom view after resting until NPCs are in place (20261127-045651)

Goal: after a rest or loiter, NPCs jumped to their new places about a second after the Doom view came back. Hold the
view until Daggerfall's people are synced.

## What caused the jump (measured)

Daggerfall's townspeople list (`DoomerfallTownspeople`) is published every 0.5 s of real time. While Daggerfall's rest
window runs, the clock moves fast: loitering is 1.25 s per game hour, so one poll interval is about 24 game minutes.
Doom is paused behind the menu, so it applies the last list it received on its first tic after the close. If the player
closes the end-of-rest message quickly, that list is up to 0.5 s stale. The next poll (up to 0.5 s later) corrects
it, and people more than 128 units off are moved in one step (`Place` in `dd_townsfolk.cpp`), while others vanish or
appear. A slow click hides the bug because a poll lands while the message is up.

Before (old install `review/ammoname`, `restsync.py run street --fast --root ...ammoname`): 6 tics after the view came
back, 8 townspeople jumped (41 to 1974 units in one tic, 4 of them within 3000 units of the player) and 2 vanished.

## What was built

- **Bridge**: `dfb_ui_state.pad` is now `flags`, with `DFB_UI_CLOSED_TIME_PASSED` (bindings regenerated).
- **Daggerfall** (`DoomerfallUi.Finish`): if the clock moved at least one game minute while a menu was open (any menu:
  a rest, a loiter, or a rented room through Daggerfall's own windows), and it was not a journey, a new game or a load,
  it calls `DoomerfallTownspeople.PublishNow()` and `DoomerfallNpcs.PublishNow()` (the normal poll, run immediately),
  then sends the close with the flag. The bridge ring is ordered, so Doom has the fresh lists when it reads the close.
- **Doom** (new `dd_resync.cpp`, hooks in `dd_bridge.cpp`): on that close, `DD_ResyncBegin` holds the frame
  (`DD_BridgeHoldFrame`) and freezes the playsim through the existing arrival freeze hook (`DD_BridgeArrivalFreeze`, so
  `p_tick.cpp` is unchanged). The townsfolk tick still runs (it is before the freeze in `DDTreadmill_Tick`) and places
  the pending list with snapping (`DD_TownsfolkSnapPending`, new `snapList` in `dd_townsfolk.cpp`), so nobody slides
  or jumps. The hold ends on that tic. With no list (dungeon, wilderness) it holds one tic. It is limited to 3 s; past 1 s
  it shows the existing "Loading..." screen (`DD_BridgeDrawLoading`, the generic loading message from the arrival
  wait; the todo's full loading-screen system is not built yet).
- NPC presence lists (`dd_npcs.cpp`) are applied per frame as events arrive, so the list sent before the close is
  applied before the first frame.
- Logs go to the bridge logs only (`resync: ...` in Doom's, `ui: N game minutes passed ...` in Daggerfall's).
- Stock Doom: everything needs a bridge session and the flag from Daggerfall.

## Gaps and decisions

- **Dungeon with NPCs**: not run. Privateer's Hold has none. Dungeon NPCs are fixed actors from the converter, and Daggerfall
  does not list their presence in dungeons (`DD_NpcsFrame` asks only in interiors), so nothing about them changes
  with the clock. The hold still runs there (one tic). Running another dungeon would need a new conversion.
- **House with residents at home**: the tavern has no residents at home, so the interior "at home" list was empty in
  the run. That list is published by the same `PublishNow` (it calls the same `Update`), and Doom snaps it the same way.
- **The view during the hold** is the menu's last frame (the end-of-rest message), for one or two tics. It is not
  the stale world.
- The hold is for any menu that ran the clock by a game minute or more, not only the rest window. Daggerfall's
  own windows that pass time (a rented room's rest through `DFB_UI_DAGGERFALL`) get it too. Menus that pause time
  never trigger it.
- Failed approaches: none in the game code. In the harness, ZScript names are case-insensitive (`WATCH` vs `watch`), and
  a key press plus WM_CHAR typed each digit twice ("22" hours is over the 3-hour loiter limit).

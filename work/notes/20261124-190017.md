## DRLA corpses vanishing (owner bug)

Cause: DRLA Monsters' deaths never rest on a `-1` frame (`MonsterBase.txt`). `Death` goes through `DeathMain` and
`DeathEnd` to `DRLADeathEndLoop`, a 1-tic `CanRaise` frame that loops forever. `XDeath` ends the same way in
`DRLAXDeathEndLoop`. `FinalFrame` therefore found no resting frame, and `MakeRecord` marked every corpse gone. No DRLA
death spawns a separate corpse actor (checked with grep). `DestroyedEnd` shows TNT1 for monsters that leave no body.

Fix (`dd_treadmill.cpp`, `Settle`):

- A death now settles on a `-1` frame or on the loop a corpse ticks in.
- The walk follows DRLA's by-name jumps (`A_JumpIf(1, "DeathMain")`) into the dying class's own states. For the parser,
  the base class's `Goto DeathMain` points at its own state, so the class's frames would otherwise be skipped.
- The look is the last sprite and frame the walk sets, because the loop's frames are `"####" "#"`.
- A dead monster is always stored as a corpse. On restore, its look comes from its class and death label.
- `XDeath` labels resolve now. The engine stores XDeath as `Death.Extreme`, so before this fix gibbed corpses came back
  as ordinary deaths, in vanilla too.

- **Loop detection alone (p2first).** Corpses came back, but 51 of 53 showed their spawn frame. The `####` frames had no

- **Looking up `FindState(NAME_XDeath)`.** It always returned null, because the engine names that state
  `Death.Extreme`. I found this with a temporary state-name dump, which has since been removed.
- **Blaming the dungeon build for the load stall.** I first thought only saves made in a dungeon failed. The town save
  failed the same way.
- **Harness state in an inventory item.** DRLA swaps the player's class ("Player swapped to Portia", then "Terri" after
  a Phase Device), which loses the item or hands the new pawn a fresh one. The harness now keeps a copy in its

## Suspected oversights

- **Exterior piles may be invisible in Doom.** The item marker space (`ItemSpace`) covers indoor spaces only, so a pile
  dropped in town is kept and restored in Daggerfall but may not be drawn or usable in Doom. Confidence: medium, from
  reading the code, not from a run.
- **The exterior chunk formula is not checked against Doom's.** Daggerfall's piles use chunk = floor(world / 8192), and
  this has not been cross-checked against Doom's `ChunkKey`. Piles came back in every run. Confidence: low that it is
  wrong.

## Gun ammo glitch (owner task, added after the record work)

Owner rule (2026-11-24, now in `gamedesign.md`, "Ammunition"): **guns never give ammo**, from any source, on a first
take or a retake.

Cause: `dd_items.cpp` sent `dfg_ammo` on every Use take of a gun, and `DoomerfallGuns.zs` `GiveAmmoOnly` then gave the
gun class's default `AmmoGive1/2`, whoever dropped the pickup. Fix: no `dfg_ammo`, `GiveAmmoOnly` removed. One other
path could give a gun's ammo: `DD_UsePress` falls back to Doom's own pickup (`CallTouch`) for a class name too long for
the bridge (40 bytes), which for a gun runs DRLA's Pickup state (`AmmoPickup`: 4 shells when the gun is already held) or
a Weapon's `AmmoGive`. Guns are now refused there. Checked and fine: guns never pick up by touch in generated maps
(`DD_PickupNeedsUse`); a hotkey draw already puts ammo back after giving the weapon (`Equip`); guns are never "used"
from Daggerfall's inventory (hotkeys draw them).

Test: `tools/location_record/gunammo.py` (`gunammo.zs`, Daggerfall hook `-dfgundroptest` in `DoomerfallGunDropTest.cs`),
in town. Shell (and DRLA's magazine `RLShotgunClip`) after each step:

## Doom's own drops blocked (owner decision)

A gun (or any item) leaves the player only by Daggerfall's inventory window (card 4's path). A first fix that let Doom's
drops through and told Daggerfall (commit 11f844dc) was rejected as overcomplicated and reverted (21cee8a5).

- `d_net.cpp`, `DEM_INVDROP`: no `DropInventory` in a bridge session. This covers `weapdrop`, `invdrop` and `drop`. The
  commands and their bindings stay.
- `g_game.cpp`: DRLA's "Drop Item" key is Zoom, and every DRLA drop goes through each weapon's Zoom state: guns (and
  the Technician's scrap, which needs the drop's first press), mod packs, worn armor and armor mods. In a bridge session
  with DRLA loaded the Zoom button never reaches the ticcmd, so the key does nothing (owner: block it fully). DRLA's
  presence is `PClass::FindClass("RLWeaponDrop")`, the token its Zoom state checks, looked up once and cached for the
  process (the mod set cannot change without a restart). Without DRLA, Zoom works as normal (owner correction). The
  Technician's scrap stays blocked; it is now a future idea.
- DRLA's backpack toss: M runs `use RLSpecialItemDropper`, whose Use state runs `RLBackpackToss`. `DoomerfallGuns.zs`
  `WorldTick` keeps the dropper at 0 (it is `KEEPDEPLETED`), so its use fails. On stock the class name resolves to
  nothing. DRLA still tosses a backpack on death while its backpack picker is open; that path was left alone.
- `Doomerfall.zs`: the "Drop item" and "Drop weapon" entries of the Inventory controls menu and DRLA's "Drop Item"
  (`+zoom`) and "Remove Special Item" (`rl_specialitemdropper`) entries are removed from the menus at startup. Commands,
  bindings and DRLA's definitions stay.

## Card 5: hinged doors keep their position (owner, 2026-11-25)

Doors only: lifts, platforms, switches, lever chains, riddles and traps (`DFAction`) still reset on each visit (the
exception in `gamedesign.md`). Merged `claude/location-record-d20944` (89ced22c) first.

- `door_objects.zs` `DFDoorHandler.Distill`: one bit per door in `DFDOORS` order (thinker order, as `DFActionHandler`
  links doors), a moving door counted at the end it is heading to, as `"<stamp> <hex>"`. The stamp is an FNV-1a hash of
  the `DFDOORS` lump. `Restore` checks the stamp, then sets each door's `swung` to 0 or `SWING`, stops it, and runs
  `Place(false)`, `SetSightOpen` and `UpdateBlocking`. A stamp mismatch returns -1 and changes nothing, so the doors stay
  as the map built them.
- `dd_treadmill.cpp`: `SnapshotPlace` (on leaving and on a save) adds one fact of kind `DFB_FACT_DOORS` (4) whose death
  name is that text. `ApplyPlace` takes it out of the facts before anything else, restores the doors, and goes on as
  before, so a door fact never enters the world table or breaks the "cache matches" check. It runs when the record
  arrives, after the encounter plan is set and before the plan's mooks spawn.
- Daggerfall keeps the fact as one of its "full facts" (`DoomerfallPlaceCodec` exceptions) with the text in the place's
  names, so no Daggerfall code changed beyond the generated bridge constant. Its log counts the door fact under "gone"
  (it clamps unknown kinds); that is cosmetic.
- Doors linked to an action keep their position; the action resets with the map. Running a flag-18 action again on its
  open door does nothing (`ActionSet` returns when the door is already there).
- City gates are not covered: they live in town maps (`DFGATES`, spawned by `DFRuntimeTown.SpawnGates`), whose record
  is per exterior chunk, and they would need their own stamp and chunk key. Daggerfall's city gates may also follow
  their own open hours, which is a design question. Town building doors are entrances, not hinged doors, and building
  interiors have no hinged doors, so the "one town door" check had nothing to test.
- Rebuilt: ddruntime.pk3 only (this checkout's converter, `--runtime-assets`, 9 s; the town groups list was identical).
  No dungeon re-convert: Privateer's Hold's runtime doors package takes `door_objects.zs` from ddruntime.pk3. The new
  bridge constant changes the schema hash, so the launcher, the bridge DLL, UZDoom and Daggerfall Unity were all rebuilt
  for the runs.

Diff: game code 80 added, 2 removed (`dd_treadmill.cpp` +31/-2, `door_objects.zs` +48, `doomerfall_bridge.h` +1), plus
the regenerated bindings (+2/-1 twice). Tests: `doors.py`/`doors.zs` and `lever_doors.py`/`lever_doors/zscript.zs`.

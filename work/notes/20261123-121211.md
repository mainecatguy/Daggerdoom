## Reproduced before the fix

`tools/combined_bridge/run_door.py before --baseline`, real launcher, both games, City of Daggerfall building, two round trips:

| Moment | Hidden Daggerfall |
|---|---|
| Doom enters the building | Teleports to map pixel 999,0 |
| Doom leaves | Teleports back to 206,212 |
| Second trip | Same again. 8 teleports by the end of the run |

## Root causes

1. **Doom called every Daggerfall map "exterior".** `DDTreadmill_PlayerWorld` returned true inside interiors and dungeons. Those spaces live in a private coordinate range, about 1 billion world units out, so the map pixel clamped to 999,0.
2. **The arrival was misreported too.** During a door handoff Doom published the destination's private coordinates, so the jump began before the new map loaded.
3. **Daggerfall's indoor branch did too little.** It returned before setting `PreventEnemySpawns` and `DisableAI`, and before stopping the player if Doom started indoors. Fixing cause 1 alone would have let random encounters spawn while the player was indoors, because that flag is cleared after every update.

## What changed

- `dd_treadmill`: `DDTreadmill_PlayerWorld` returns none, exterior, interior, or dungeon. Each door handoff records what it is arriving in.
- `dd_bridge.cpp`: publishes the real context. Indoors the position and pixel stay at the last outdoor place. The travel menu will not open during a map handoff.
- `DoomerfallPositionSync.cs`: indoors, Daggerfall stays engaged with AI and encounters off, keeps answering menus, and does not move. **The `if (indoors)` block in `Tick` is the seam for the backlog task that moves Daggerfall into the matching interior.**
- `dd_ui_test_hold`: a test-only setting so a route can open the menu at a chosen place.
- `tools/combined_bridge/`: assembly, door route, no-session checks, and demo launch check.

## Checked and found fine

- HP needed no fix. Its mirror keeps working across map changes.
- Town handoffs and `dd_tm_warp` needed no fix. These had never been run with the sync before.
- No frame of "not on a map" appears during door trips, so Daggerfall's controls are not released mid-transition.

## Known gaps

- Doors were pressed through the `dd_tm_use` test hook. The real Use key and walking up to a door were not tested in this run.
- The menu was opened by the test command and closed by a posted Esc. Choosing a destination indoors was not run. It uses the same intercept as outdoors.
- That encounters stay off indoors rests on the code path. The log proves the hold ran each indoor frame, but no test tried to force an encounter.
- The registry hash was first taken after the earlier test runs in this session, so it does not cover them. Those used the same isolated copy.
- Daggerfall is at the door while the player is indoors, so anything that asks Daggerfall "is the player inside?" gets no. That is the backlog task.
- Loading a save made indoors was not run with the bridge. Saving and loading are out of scope.

## Failed approaches

- The first menu route aborted because scripts may only change settings marked for mods. The test setting now has that flag.

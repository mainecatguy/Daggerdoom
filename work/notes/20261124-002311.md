# Ground loot uses Daggerfall's loot-pile sprites

Branch `agent/groundloot-20261124-002311`. Review folder: `D:\dev\DoomDaggerfall-loop\review\groundloot`.

## Result

An item on the ground in Doom is now always drawn as a Daggerfall treasure pile, at the pile billboard's Daggerfall size. The item's inventory picture is no longer drawn in the world anywhere.

Only one place drew inventory art in the world: the `DaggerfallItem` actor in the item gallery (`DFGALLRY`). The pauldron "nearly as tall as the player" came from there. Real loot in a game already looked like vanilla, and its files are byte-identical before and after this change.

## Where each sprite is chosen

| Object | Who picks the sprite | Before | After |
|---|---|---|---|
| Real loot piles in a game: dungeon treasure, interior treasure, enemy drops, piles the player drops | Daggerfall. `DaggerfallLoot.TextureArchive/Record`, set by `GameObjectHelper.CreateLootContainer` (from `RDBLayout`, `DaggerfallInterior`, `CreateDroppedLootContainer`, and `DoomerfallMonsters` for Doom kills). The bridge sends them (`DoomerfallItems.cs` `Collect`) with the billboard's `Summary.Size`, and `DoomerfallWorldItem.Show` draws `DPaaarrr`. | Vanilla pile sprite and size | Unchanged |
| Furniture containers (shelves, wardrobes) | Map geometry. Doom only gets an aim box. | No sprite | Unchanged |
| `DaggerfallItem` in the gallery | `tools/item_gallery/ItemGallery.cs` wrote the item's inventory picture (`DaggerfallUnityItem.GetInventoryTextureRecord` logic), sized as if it were a billboard | Inventory picture, up to 169 px, about 127 Doom units tall | A treasure pile from `TEXTURE.216`, at that record's billboard size |

Every pile archive in `DaggerfallLootDataTables` (204, 205, 207, 209, 211, and 216) was already packaged as `DPaaarrr` textures, so the live game never fell back to inventory art.

## What changed

- `tools/item_gallery/ItemGallery.cs`: each gallery item shows one of vanilla's dropped-item treasure icons (`randomTreasureArchive` 216, `randomTreasureIconIndices`), at `MeshReader.GetBillboardMesh` size times 0.75, standing on the floor. Daggerfall Unity picks that icon at random. The gallery picks it from a hash of template, variant, and artifact, so runs repeat exactly. That is an engineering call for a test map. `dfitems.txt` gains two columns, the pile archive and record. The manifest gains a `pile` column. Inventory pictures are still packaged, unused, for a later inventory or HUD.
- `mods/daggerfall_items/zscript/DaggerfallItem.zs`: reads the pile columns when present. The overlay shows both the inventory picture and the pile.
- `tools/dungeon_converter/sprite_scale_check.py`: measures items against the pile record when the package has those columns.
- `tools/groundloot/groundloot.py`: builds the before and after packages, takes screenshots, and stages the demo.

No other sprite was rescaled. Eye height was not touched. No engine, bridge, or Daggerfall Unity code changed.

## Verification

- `python tools/groundloot/groundloot.py package before` was run before editing, and `package after` after. Each built 460 entries.
- `shots before` and `shots after` (`tools/item_gallery/check.py`): gallery `shown=460 total=460 broken=0` both times. Stock E1M1, E1M1 with DRLA, and E1M1 with DRLA and the package all pass, with no new error lines (766 DRLA baseline lines either way).
- `sprite_scale_check.py` on both packages. Before: 432 inventory sprites, 0.9999 to 1.0001 of their billboard size. After: 460 pile sprites, 1.0000 of the pile billboard size, with 0 off-size axes and 0 images changed.
- I compared the two packages entry by entry by CRC. Only `dfitems.txt` and `zscript/DaggerfallItem.zs` differ. Every image and `textures.dfitems`, which holds the `DPaaarrr` textures real piles use, is identical. So taking loot, containers, and enemy drops run the same files as before. I did not rerun the paired container or drop tests, because none of their inputs changed.

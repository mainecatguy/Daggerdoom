# Readable signs (run 20261127-130322)

Goal: Daggerfall's signs stand in the Doom world where Daggerfall Unity places them, and using one shows its text as in
Daggerfall Unity.

## What a "sign" is in Daggerfall Unity (from the code)

The only readable sign in Daggerfall Unity is the town **bulletin board**, model 41739 (`RMBLayout.BulletinBoardModelID`).
`TalkManager.GetValidRumors(readingSign)` calls reading it "reading a sign".

- **Placement.** `RMBLayout` builds it as a standalone model (never combined) and adds a `DaggerfallBulletinBoard`
  component. A census of every location (`DungeonConverter --list-boards`, new, `tools/dungeon_converter/BoardCensus.cs`)
  found them only in the four city-wall gate blocks `WALLAA08` to `WALLAA11`, as block-level (misc) models: **every one
  of the 409 walled towns (TownCity) has 8, two beside each gate**, plus one village group. 3,280 boards in all. Hamlets,
  villages, temples and the rest have none. The model is 64 x 88 x 12 Daggerfall units (48 x 66 x 9 Doom units), a
  free-standing board.
- **Reading it.** `PlayerActivate` checks for a board on every click, in every mode (Steal, Grab, Info, Talk).
  `ActivateBulletinBoard`: beyond `MobileNPCActivationDistance` (6.4 m) it shows "You are too far away." as mid-screen
  text; otherwise it opens a message box with the current location's name, then the news or rumors from
  `TalkManager.GetNewsOrRumorsForBulletinBoard` (or just the name when there are none).
- Hanging shop signs on buildings are part of the building models, not separate objects, and Daggerfall Unity gives
  them no text of their own: clicking one is clicking the building (Info names it), which Doom already does
  (`DoomerfallInfo`, Use on a building wall).

## Where things already stood

- **Placement was already done.** The town converter (`CityExport.AddBlock`) adds every block-level model, so the boards
  were already drawn in the Doom mesh at Daggerfall's position (same transform as every other model, covered by the
  earlier visual parity work). The new `--list-board-positions` diagnostic prints each board's Doom position; the map
  check (`signs.py convert`) found blocking raster lines 5 to 7 units from each of Cromwark Hamlet's 8 board centres, so
  the boards are solid in Doom too.
- **Use already asks Daggerfall about the wall in view.** A Use press outdoors that no door, item or NPC takes sends
  the point Doom's view ray hit to Daggerfall (`DD_InfoUseWall`, `DFB_INFO_BUILDING`), and the Info control does the same.
  Daggerfall answered only with building names.
- A message box Daggerfall opens by itself is already shown in Doom (`DoomerfallUi`, `DFB_KIND_UI_ASK`), as the building
  greeting work proved.

## Change

Mostly Daggerfall side, plus one small UZDoom change for the reach (below). No mod change.

- `DoomerfallInfo.cs`: for a `DFB_INFO_BUILDING` point, first look for a bulletin board whose model footprint (its
  mesh bounds, turned with the board, plus 0.5 m for Doom's 8-unit collision raster) holds the point. If there is one,
  Daggerfall's own board code runs, with the distance from the player to the hit point. Otherwise the building check
  runs as before.
- `PlayerActivate.cs`: `DoomerfallReadBulletinBoard(board, distance)`, a three-line public wrapper around the private
  `ActivateBulletinBoard`, like the existing `DoomerfallActivateLoot`.

So Use (and Info) on a board shows exactly Daggerfall Unity's box: the town's name and its news or rumors, or "You are
too far away." from beyond 6.4 m.

## Engineering calls

- **Footprint, not 3D.** As `FindBuilding` does, because Doom's heights do not match Daggerfall's exactly.
- **Distance comes from Doom.** The first version measured from Daggerfall's synced player position to the hit point.
  A test run caught it reading 226.6 m for a press from 8 m, because Daggerfall's copy of the position lags Doom's (the
  harness had just moved the player). Running at Doom speed covers about 2 m in one 10 Hz sync step, enough for a false
  "too far away". Doom now sends its view ray's length to the hit point in the request's `id` field for a building point
  (`dd_info.cpp` `RayLength`, unused before for this target; header comment updated and bindings regenerated, no layout
  change). That is also what Daggerfall Unity measures (camera to hit). The synced position remains only a fallback for id 0.
- **The look label** (crosshair name) is unchanged: Daggerfall Unity shows no name for a board.

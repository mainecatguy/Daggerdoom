# Shop levels 1: the shop level table (run 20261127-100827)

Goal: every classic shop gets a fixed level 1-30 by proposal C (band-locked rank), computed from classic data on
Daggerfall's side, with a Python port that agrees shop for shop. Nothing uses the level yet.

## Plan

1. Pick a building seed that is classic data, needs only MAPS.BSA, and is on the runtime `BuildingSummary`. Done.
2. Python port `tools/shop_levels/shop_level.py` (reference). Done.
3. C# `DoomerfallShopLevels`, built on the area level worker from the MAPS.BSA it already loaded. Done.
4. Test hook `-dfshopleveldump <dir>` in its own file, then compare with the port. See Results.

## Decisions (engineering calls)

- **Seed = lowbias32 chain of (0x5B0F0001, MapId, building type << 16 | NameSeed).** The goal suggested MapId plus
  the building key, but the building key (block x, y, record) only exists after merging the location list into
  BLOCKS.BSA (`RMBLayout.GetLocationBuildingData`), which is main-thread `ContentReader` work. (MapId, type,
  NameSeed) is unique for all 14,790 classic shops (checked against the block-merged dump: 0 duplicates; MapId plus
  NameSeed alone has 1 duplicate pair), comes straight from the MAPS.BSA list, and is on `BuildingSummary`, since
  `GetLocationBuildingData` copies NameSeed and Quality from the list entry.
- **Exact rank, not the seed-fraction estimate.** The notes' cell-count form estimates a shop's place inside its
  cell as `seed × cellCount`. With all classic shops in hand at warm-up, the worker sorts each band by
  (quality, town class, seed) instead, which is the cell-count form with the exact place inside the cell. That
  makes the per-level counts identical to `proposals.py` (they depend only on the band sizes) and costs nothing.
  Seed ties fall back to (MapId, type, NameSeed); none occur in the classic data.
- **Lookup key = (MapId, type, NameSeed, quality).** A building whose summary no longer matches the classic list
  (a mod-added location, or a building a mod's `BuildingReplacementData` changed) is not in the table and is placed
  by binary search among the classic keys of its band, not counted, so classic levels never move. Run on every
  classic shop, this fallback lands each on its own level (no key ties).
- **Town class:** village 0, hamlet 1, city 2, capital 3 (TownCity named after its region, aliases from
  `proposals.py`). The 22 castle (DungeonKeep) alchemists count as class 0, as in `proposals.py`.
- **Test hook:** like `DoomerfallAreaLevelsTest`, it starts itself with `RuntimeInitializeOnLoadMethod` when
  `-dfshopleveldump` is on the command line, so the bridge needed no line at all (the goal allowed one).
- `DoomerfallAreaLevels` changes: `BuildLocations` returns the loaded `BsaFile`, `Build` hands it to
  `DoomerfallShopLevels.Build` (which catches its own errors), and a `WaitUntilBuilt()` helper. Area levels are
  otherwise unchanged.

## Findings

- The research notes say "14,790 shops in 2,466 towns"; the towns with shops are 3,444 (1,834 villages, 1,200

- Python port: 14,790 shops, counts identical to `proposals.py` proposal C, contract violations 0, fallback 14,790 of
  14,790 on own level, 39 capitals. Runs in 0.3 s.

### Verifier fix: test logic out of the game class

The first version kept test-only members (`Status`, a public `PlaceAmongClassic`, `Counts`, `Classic`, and the
`counts`/`locations` bookkeeping) in `DoomerfallShopLevels.cs`. `DoomerfallShopLevels` is now a partial class: the game
file holds only the table, `Build` and `ForShop`. The test accessors (`TestStatus`, `TestPlaceAmongClassic`,
`TestClassic`) are in `DoomerfallShopLevelsTestAccess.cs`, and the test works out the per-level counts and location
count from the classic dump itself. The only diagnostic left in the game file is the build timer (a Stopwatch and one
assignment), which the goal asks to report. Rebuilt (`CliBuild result: Succeeded`) and reran `runtime_check.py`:
both CSVs 14,790 of 14,790 match, counts match, contract 0, fallback 14,790 of 14,790, 18 ms on the worker.

# Encounters 4: area facts, encounter markers, and leaders (2026-11-24)

Card 4 of the encounter queue. Design: `work/notes/20261123-205402-fractal-encounter-variety.md`, section 9.2.
Builds on card 3 (`work/notes/20261124-102050.md`). Branch `agent/encounters-20261124-104822`.

## Plan (as carried out)

1. Bridge: two new kinds inside each monster list, plus the quest foe's enemy type in `dfb_monster`.
2. Converter: an invisible marker per Daggerfall enemy, instead of a picked monster.
3. Daggerfall: send the facts; one encounter per quest foe member; only a leader's death counts.
4. Doom: read the markers, build the planner request, and spawn each placement's leader (member 0) on its exact point.
5. Prove it in a paired session: facts match, kill, save, reload, re-enter.

## What was built

### Bridge (`bridge/doomerfall_bridge.h`, then `python bridge/generate_bindings.py`)

- `DFB_KIND_ENCOUNTER_AREA 55`, payload `dfb_encounter_area`:
  - `generation`, `map_id`, `dungeon_index`, `location_id`, `region_index`;
  - `world_x`, `world_y` (map pixels; the pixel centre);
  - `dungeon_type`, `area_level`, `seed_offset` (0).
- `DFB_KIND_ENCOUNTER_TEXT 56`, payload `dfb_encounter_text`: the location name, region name, and dungeon type name
  (`DFB_ENCOUNTER_LOCATION_NAME`, `_REGION_NAME`, `_DUNGEON_TYPE`), 40 UTF-8 bytes each.
- Both are sent between `MONSTERS_BEGIN` and `MONSTERS_END`, so Doom gets the facts, the quest foes and the dead list
  in one list. `orchestrator.md` lists kinds used through 50-54, so 55-56 were free in this worktree. Other lanes may
  have taken them; check before merging.
- `dfb_monster.pad` is now `enemy_type`: a quest foe's Daggerfall `MobileTypes`.
- The layout hash changes, so old launchers and bridge DLLs no longer pair with this build.

### The contract fields, and where each comes from

| Field | Source |
|---|---|
| `dungeonIndex` | Daggerfall counts map table entries whose `DungeonType` is not `NoDungeon`, region by region in file order. Built once per run. The total is **4,232**, the count the design's genome assumes. Privateer's Hold is 1506. |
| `locationId`, `locationName` | `location.Dungeon.RecordElement.Header.LocationId`, `location.Name`. |
| `regionIndex`, `regionName` | `location.RegionIndex`, `location.RegionName`. |
| `worldX`, `worldY` | `MapsFile.LongitudeLatitudeToMapPixel(...)` + 0.5. |
| `dungeonType` | `dungeon.Summary.DungeonType`, as its number and its enum name (the planner uses the name). |
| `areaLevel` | `DoomerfallDrops.AreaLevel(location)`, the same value drops already use. |
| quest-use flags | Each living quest foe member is a placement with quest = 1. Map markers have quest = 0. See below. |
| `deadMookIds` | The existing `DFB_MONSTER_DEAD` rows. |
| `seedOffset` | 0. |

**Quest-use flags.** Daggerfall quests do not use the 199:15/16 enemy flats. Quest foes spawn at quest markers
(199:11). So the quest placements are the quest foes themselves. Each foe member becomes one placement with its own
hash, and the request marks it quest. Map markers are never quest placements.

### Converter (`tools/dungeon_converter/EnemyRoster.cs`, `Program.cs`)

- It no longer picks monsters. Each 199:15/16 placement becomes a `MapSpot` (9001, invisible and inert) at the exact
  Daggerfall point. The floor is the same span choice as before. The old code snapped monsters to the cell centre.
- The args carry the data:
  - arg0 = 7365, the marker magic;
  - arg1 and arg2 = the 49-bit placement hash, high and low;
  - arg3 = the record type (15 or 16);
  - arg4 = `FactionOrMobileId`.
- A UDMF `comment` shows the hash. `DDMONST` is no longer written.
- No mod is needed for the marker, so stock Doom loads the map.

### Daggerfall (`DoomerfallMonsters.cs`)

- **Facts.** Built in `BuildPlacements`, sent with every list, and logged as `encounters: facts ...`.
- **Quest foes.** One encounter per foe member. The placement hash is `FoeMemberHash(FoeHash(quest, symbol), member)`.
  The list row is that encounter's leader id (member 0).
  - Member 0 stands exactly on the marker. Later members keep the old 48-unit grid offset, now applied by Daggerfall,
    so leaders of one foe do not spawn inside each other.
  - `FindFoe` matches any member's hash and returns which foe member it is. The quest loot seed uses that foe member,
    as before.
- **The leader rule.** `OnDeath` records every mook in the ledger, so they all stay dead.
  - **Leader** (member bits 0): `SetInjured`, `IncrementKills`, and one drop roll, as before.
  - **Follower:** recorded with `rolled = true` and no drop, and does not touch quests. It logs
    `follower N, recorded only`. `Roll` also refuses followers.
- The `mookKilled` path is the existing `DFB_KIND_MONSTER_DEATH`, unchanged.

### Doom (`UZDoom/src/dd_monsters.cpp`, `mods/doomerfall/src/zscript/EncounterLeaders.zs`)

- **Markers.** `DD_MonstersEnterDungeon` collects the MapSpots with the marker magic on every visit, sorted by hash.
- **Spawning.** On a bridged first visit, the leaders wait for a list whose facts name this map.
  - When it arrives, `SpawnEncounters` builds the request: markers first, then the quest placements, in hash order.
  - It calls `DoomerfallEncounterLeaders.PlanText` through `VMCall`. The request is tab-separated text, and the answer
    has one line per placement.
  - It spawns each leader that is not dead and not already present, exactly on its point, with `ddRecordId` set to
    the leader id. A spawner gets a claim instead.
- **Quest foes.** Their leaders are planned the same way. They are spawned whenever Daggerfall lists them alive and
  they are missing, as before.
- **Fallbacks.**
  - No planner, or no facts: the old stock roster, picked by hash.
  - No bridge: the stock roster at once, so a converted map stays playable.
- **Checks.** Each plan's leader id is compared with `LeaderId(hash)`, and any mismatch is logged. There were none in
  any run.
- **When it spawns.** In `DD_MonstersTick` (playsim), not in the bridge frame, so prediction cannot destroy the actors
  (see the guard oversight).
- **Loads.** A loaded level already has its leaders, and the present check stops duplicates.

### Changes to the old route, and why (in the wrapper, not in the old tool)

- **The route never finished.** After the quest kill, the old route used Interact on the drop, which now opens
  Daggerfall's loot window (the containers card). The window pauses Doom, and the route cannot drive it. The wrapper
  leaves the drop on the ground and expects it to persist on re-entry. Taking the drop was proven by the earlier cards.
- **Only one kill.** The wrapper kills at least two placed leaders besides the quest foe, so normal leaders' drop rolls
  are covered.
- **Open windows.** It presses Back on any menu left open for a second. None appeared in the passing runs.

## Failed approaches and snags

- **Unreadable town cache.** The combined-bridge review data's town cache and converter are older than this UZDoom
  reads (`DDTCACHE group=7154 unreadable`). Doom started in MAP01 and the route could not begin. Fixed by using
  `review\doom-items\data`, as the recent harnesses do.
- **World position.** The first build sent 213.5,187853.5 because `GetPixelFromPixelID(MapId)` is wrong (a map id is
  not a pixel id). Fixed with longitude and latitude.
- **Load during a build.** One load run failed with "Daggerfall stopped responding" while a Unity build ran at the same
  time. The rerun without the build passed.

## Not proven, or left for later

- **Followers** (member ≥ 1) cannot occur until card 5 spawns them. Their ledger path (recorded, no drop, no quest
  credit) is written but not run.
- **The no-bridge roster fallback** and the **no-planner fallback** are not run.
- **The enemy type for random placements (199:15)** is sent as -1, because Daggerfall's random pick is not on the
  bridge. Fixed placements send their `MobileTypes`. The planner does not read `dfEnemyType` or `quest` yet, so this
  has no effect today.
- **Placements need markers.** A dungeon converted before this change (with monster things and no markers) gets no
  encounters. Every converted dungeon must be reconverted, and the runtime converter does this for new cache entries.
- **The old tool is stale.** `tools/monster_deaths/monster_deaths.py wad` still expects a `DDMONST` lump, so its `wad`
  step no longer works with the new converter. The new wrapper replaces it for this work.

## Engineering calls

- The markers are MapSpots with args, not a custom actor, so converted maps need no mod to load.
- Planning runs in ZScript and spawning in C++, so `ddRecordId` stays private to C++.
- Quest placements go into the same request as the map markers (design 9.2). This makes regular leaders' classes
  depend on whether a quest foe is present at first entry; see the question.
- The dungeon index uses the map tables' `DungeonType`. The count of 4,232 confirms it matches the design.

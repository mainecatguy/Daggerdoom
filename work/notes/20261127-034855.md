# Loading holds, continued: pause Daggerfall too; case 3 re-entry (run 20261127-034855)

Follows `work/notes/20261127-025856.md` (Doom side of the holds). Two items left by the orchestrator:
(1) Daggerfall kept running during a hold (clock, poison, disease could lower HP); (2) case 3, re-entering a cleared
level-30 dungeon, was untested.

## Plan

1. Daggerfall pause: Doom already publishes a phase in its bridge state each frame, and `DFB_UZ_PHASE_LOADING` was
   defined but unused. Publish it while any loading hold is active; Daggerfall pauses (`GameManager.PauseGame`, the
   same pause its own windows and the bundled save use) while it sees it. A state, not an event, so a lost release
   cannot leave Daggerfall paused, and a stale (dead) Doom releases it. No new bridge kind, no schema change.
2. Log Daggerfall's clock and HP at the start and end of each hold; a checker (`tools/loading_hold/check_df_pause.py`)
   fails a run if either changed.
3. Case 3: give the door test tool (`tools/runtime_dungeons/run_entries.py`) `--mod` (to load the Doomerfall mod, so
   the planner's army spawns) and `--clear` (kill every monster on the first arrival); run Privateer's Hold at
   `-dfarealevel 30`: enter, clear, leave, re-enter, and read the spawn gate lines.
4. Rerun cases 1 and 2 with the Daggerfall pause; E1M1 stock and DRLA.

## What was built

- `UZDoom/src/dd_bridge.cpp`: `uz_phase` is `LOADING` while `DD_LoadingActive()` (one line, takes precedence over
  PAUSED so an open Doom menu during a hold does not release Daggerfall).
- `daggerfall-unity-master/Assets/Scripts/Doomerfall/DoomerfallLoadingPause.cs`, ticked from `DoomerfallBridge`
  `FinishFrame` with `alive && peer.uzPhase == LOADING`. Pauses only if Daggerfall was not already paused (New Game
  and plain load flows pause it themselves) and resumes only its own pause. Re-asserts the pause each frame, because
  closing a Daggerfall window (inventory hotkey during a hold) unpauses the game. At release it does not unpause while
  a Daggerfall window is still open (the window keeps its own pause).
- `bridge/doomerfall_bridge.h`: comment on `DFB_UZ_PHASE_LOADING` only (bindings regenerated; schema hash unchanged).
- Measured from Daggerfall's first paused frame. The frame in which Daggerfall first sees the hold already had its time
  step fixed before the pause, so it moves the clock by one Daggerfall frame (the "lead-in", logged separately). In the
  door test this was 3 s of game time, because the hold began during Daggerfall's 0.33 s boot frames; mid-game frames
  are about 1 ms (lead-in 0 s in cases 1 and 3). The first version measured from that frame and failed its own check
  (4 s); per-frame logging showed the change was all in that one frame (frame 9, delta 0.326 s), then nothing.
- Tools: `tools/loading_hold/check_df_pause.py DF_LOG [UZ_LOG]` (pass = every hold released, clock and HP unchanged
  from the pause on), `tools/loading_hold/e1m1_check.py EXE OUT` (stock E1M1, stock and DRLA), `run_entries.py --mod
  --clear`.

## Findings

- The cleared level-30 re-entry now takes 23 ms to spawn, not the ~1.9 s measured on 2026-11-24 (notes
  `20261124-190017.md`); the first entry takes 735 ms. The gate holds on re-entry because the last spawn here took
  250 ms or more, so this re-entry shows a one-frame "Loading..." flash; it then records 23 ms, so later re-entries do
  not flash. Left as is: the flash is brief and the goal asks for the message on this re-entry.
- Daggerfall had no pause during the New Game wait either, contrary to the previous run's notes.

## Other long operations (unchanged from the previous notes)

## Known gaps

- HP was shown unchanged with an unpoisoned character only; the clock not moving is the evidence that timed effects
  (poison, disease) do not run, since they tick on Daggerfall's game minutes and frame time, both stopped by the pause.
- The lead-in frame: Daggerfall's clock moves by one Daggerfall frame when the hold starts (~1 ms of real time
  mid-game, ~12 ms of game time).
- `daggerfall-unity-master/Assets/AddressableAssetsData/Windows/addressables_content_state.bin` and
  `bridge/doomerfall_bridge_check.g.h` (line endings only) were touched by the builds and left uncommitted.

## Rerun after the verifier's review (supersedes the Daggerfall columns and tool notes above)

The verifier rejected the first version: `DoomerfallLoadingPause.cs` held the clock/HP measurement in a game class on
every launch. Changes:

- `DoomerfallLoadingPause.cs` now only pauses and resumes, with one plain log line at each end, and exposes `Held`.
- The measurement moved to `DoomerfallLoadingPauseTest.cs` (static, on only with `-dfloadingpausetest`; one hook
  line after `loadingPause.Tick` in `DoomerfallBridge.FinishFrame`). It also **poisons the player with Moonseed** at
  the first hold (no start delay, 1-9 HP per game minute), logs the poison's state at the hold and at the release,
  and logs the frame of the poison's first tick after the release with the HP change in that frame. A first try
  watched HP for 10 s after the release instead; monsters killed the player in that time, so HP alone could not show
  what the poison did. The poison's own state and the frame it ticks can.
- `check_df_pause.py` now also fails a hold whose lead-in exceeds one Daggerfall frame of game time (that frame's
  `Time.deltaTime` x 12, rounded up, + 1 s for whole-second rounding), whose poison state changed during the hold, or
  whose after-release poison tick did not take HP.
- Test tools pass the flag: `run_plain_load.py --loading-test` (and waits for the poison line),
  `run_entries.py --dfu-flag=-dfloadingpausetest`, `tools/loading_hold/run_cases_2_3.py KIT` (runs cases 2 and 3 and
  the checker).

# Fixed loot seeds for Daggerfall's random loot

Branch `agent/lootseeds-20261123-233755` (from `integration`). Not merged.

## Plan

1. Find every random loot roll: dungeon piles, building piles, Daggerfall's placed enemies, and Doomerfall's drop roll.
2. Add one small helper, `LootSeed`, that seeds Unity's generator (and `DFRandom`) from fixed facts, runs the roll, and restores both.
3. Feed each roll a seed built only from the place: map ID, block, marker position, and for Doomerfall the placement id.
4. Verify with an audit build (test code copied in only for that build) run in two fresh processes, and compare.

## What is seeded, and from what

All seeds are `LootSeed.Of(kind, text, values...)`, an FNV-1a mix with its own "loot" salt and a per-kind salt. Strings mix in by character, never .NET's `GetHashCode`. Inputs:

| Roll | Code | Seed inputs |
|---|---|---|
| Dungeon treasure pile | `RDBLayout.AddRandomTreasure` → `LootTables.GenerateLoot(loot, index, seed)` | map ID, RDB block name, block X/Z in the dungeon, marker X/Y/Z |
| Building treasure pile (taverns, Thieves Guild, Dark Brotherhood) | `DaggerfallInterior` → same | map ID, building key, marker X/Y/Z |
| Daggerfall's placed dungeon enemy (corpse loot and equipment) | `RDBLayout.AddEnemy` sets a pending seed, `EnemyEntity.SetEnemyCareer` takes it | map ID, block name, block X/Z, marker X/Y/Z |
| Doomerfall drop from a placement | `DoomerfallMonsters.Roll` → `DoomerfallDrops.RollEnemy(..., seed)` | the monster id without its tag: placement hash (map, block, marker, record, mobile id) and pack member |
| Doomerfall drop from a quest foe | same | map ID, quest name (not its UID, which differs per save), foe symbol, pack member |

- The pile roll covers `GenerateItems`, and the map, potion, and recipe extras inside `GenerateLoot`.
- The enemy roll covers the loot table, the equipment (including the class enemy's variant pick), and in a separate stream the map, potion, and recipe extras. Health, level, and spells are not seeded, so they stay as random as before.
- `LootTables.GenerateRandomLoot` reseeds with `items.GetHashCode()` only when no loot seed is active, so rolls without a fixed place behave exactly as before.
- Doomerfall's material roll (`DoomerfallDrops.RollMaterial`) used an unseeded `System.Random`. It now draws from Unity's generator, which the drop's seed has seeded.
- `DaggerfallDungeon.LayoutDungeon` names the block it is building (`LootSeed.BeginDungeonBlock`), because RDB layout code below it does not know its location. Outside a dungeon layout (editor tools) the seed falls back to the player's current map and the block name.
- The old 3-argument `GenerateLoot` stays, unseeded, for mods.

## Still depends on the player (out of scope, as the owner said)

Until area level replaces player level, these rolls still read the player's level (gold amount, ingredient chances, weapon/armor/magic levels, material), gender, and race (armor and clothing). Two players with the same character level, gender, and race get the same loot. Doomerfall drops already use the area level (currently always 1), so they depend only on gender and race. The pile and Daggerfall-enemy rolls in normal Daggerfall still use the player's level.

## Not covered, by decision or because it needs the owner

- **Unplaced enemies** (wilderness and rest ambushes, quest `create foe` spawns in Daggerfall's 3D world) have no fixed place, so they keep Daggerfall's old roll. They belong to the encounter seed work.
- **Daggerfall's random enemy type** in its own 3D dungeon is still clock-seeded by Daggerfall (`DateTime.Now.Ticks` in `LayoutDungeon`). That is an encounter roll, not loot. So in a plain Daggerfall launch a random marker can still be a different enemy in each game. Its loot seed is fixed, but a different enemy has a different loot table. Doomerfall's placements already pick a fixed type.
- **House containers** (`StockHouseContainer`, private property) and **shop shelves** restock by date. A fixed seed would make every restock identical. That is a design call, so it is a question for the owner.
- The pile icon choice is cosmetic and still random.
- Two copies of the same RDB block in one dungeon get different seeds because the block X/Z is included.

## Findings

- Daggerfall's enemy corpse loot reseeded Unity's shared generator with a fresh list's hash code, and never restored it, so it also disturbed everything that drew from Unity's generator afterwards. Seeded rolls now restore it.

## Verification

`python tools/loot_seeds/loot_seeds.py all` builds a separate audit game (the audit source `tools/loot_seeds/LootSeedAudit.cs.txt` is copied into the project only for that build, then removed), copies it to `D:\dev\DoomDaggerfall-loop\review\loot-seeds\audit-dfu` as a portable install with the product name "Doomerfall Local", and runs it twice in fresh processes. Each run deletes `PortableAppdata` first, starts Daggerfall Unity with no bridge and no save (Void start), and scrambles Unity's and DFRandom's state from the clock. It then:

- builds the real Privateer's Hold dungeon from `ARENA2` twice and writes every treasure pile and every placed enemy's corpse items,
- rolls Doomerfall drops for Archer, Orc, Imp, Warrior, and Spellsword at area 1 and 20, three placements each, twice with a re-scrambled state in between,
- checks that a seeded pile roll leaves the shared state exactly as it was, and that an enemy's loot seed leaves no trace (the same start state with two different seeds ends in the same state, since health is still rolled from the shared state, as in Daggerfall),
- rolls one unseeded control.

Result (latest run, `review\loot-seeds\first.txt` and `second.txt`):

| Check | Result |
|---|---|
| Both runs | `AUDIT PASS`, exit 0 |
| 8 dungeon piles, 30 Doomerfall drops, and the state checks, run 1 against run 2 | 40 of 40 lines identical |
| Same dungeon built again within a run (re-entry) | all 8 piles identical |
| 31 Daggerfall-placed enemies (Thief, Archer, Orc, Imp, Skeletal Warrior, and more) | all 31 matched placement and type, 0 with different loot. 14 carry items, for example the Thief at 11,7 has gold, a steel longsword, and leather pauldron in both runs |
| Different placements of the same enemy type | different loot (for example Orc area 20 placements 0, 1, 2 have 6, 4, and 5 items) |
| Unseeded control (`GenerateItems` with no seed) | differs between runs, so the comparison does detect differences |

Not run:
- **Building piles** (tavern, Thieves Guild, Dark Brotherhood) were not built in a real interior. That path is the same `GenerateLoot(..., seed)` call with a different seed, reviewed but not executed.
- **Save, load, and re-entry in a real game, and a bridged Doomerfall kill** were not run. Save and load restore pile and corpse items from the save file, and the Doomerfall ledger keeps each rolled drop. Neither code path changed. Only the seed in front of generation changed. The Doomerfall drop roll was run through the real `RollEnemy`, but not through a Doom kill.
- The shipped (non-audit) build was not rebuilt separately. It is the same source minus the audit file.

## Failed approaches

- First audit: a check that `RollEnemy` leaves the shared state unchanged failed. That was wrong, because the enemy roll also rolls health and level from the shared state, which is intended. It was replaced by the "no trace" check above.
- First audit also reported piles changing on rebuild. Only the height had changed: Daggerfall snaps a pile to the ground using its randomly chosen icon's size. The items were identical. The audit now keys piles and enemies by X and Z.

## Play-test list

1. Start two new characters with the same level, race, and gender. Enter the same dungeon (for example Privateer's Hold) in each, and open the same treasure pile. The items should match.
2. In a Doomerfall bridge session, kill the same placed monster in two new games and open its pile. The items should match.
3. Save, leave, re-enter, and load. Piles keep what you left in them, and kills do not roll again.

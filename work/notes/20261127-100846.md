## Verifier round 1: guard ids collided across sessions (fixed)

The verifier found by reading the code that guard ids were `tag | ++serial` with `serial` starting at 0 in every
Daggerfall session. A guard corpse is saved under its guard's id, so after a relaunch and load the first new guard got
the saved corpse's id again, and Daggerfall refused to keep its corpse ("already kept"). Doom would also have merged
the two bodies (same `ddRecordId`). My `guardload` run only listed the old corpse, so it could not catch this.

- **Fix.** `DoomerfallGuards.serial` now starts at `DateTime.UtcNow.Ticks` (about 6.4e17, inside the 61 serial
  bits), so a later session's ids are always above any earlier session's. Ordinary engineering call: it is the
  smallest change, needs no new saved state, and the ids are opaque to Doom (`ddRecordId` only).
- **Guards that outlive a load.** `copies`/`corpses` are in memory only. Guard bots should not survive a load (they
  leave at every level change, `dd_guards.cpp` header), but `CorpseOf` now falls back to the city watch corpse for
  any guard id it did not send, so a stray one would still leave its body instead of vanishing.
- **Verified** (Daggerfall Unity rebuilt, `CliBuild result: Succeeded`):
  `run guard guard` again: `guards: sent 88df4ca469a45d33 ...`, `corpse: kept 88df4ca469a45d33 ... as 380-1`, listed
  again after going out and back in. Then `run guardreload guardreload` (new harness mode: fresh launch from that
  autosave with `-dfguardtest`, kill one of the new guards): `town: ledger restored with 0 deaths and 1 corpses`, new
  guards `88df4ca48148c578`..`c57c` (no collision), `corpse: kept 88df4ca48148c578 ... 2 corpses in all`, and Doom
  lists both: `TCCOUNT gafterkill 2`, the old one at -280,-234.5 and the new one at -56,-18.8, both `DFBB380_1_0 shown`.

## Verifier round 2

### Daggerfall creatures in Doom (built)

The verifier asked for the ability itself: Doom showing a Daggerfall creature, whether or not a real exception exists.
**The finding stands: no Daggerfall creature reaches Doom today** (dungeon enemies become encounter markers that Doom
fills with Doom monsters). What is built now:

- **`DFCreature`** (`mods/doomerfall/src/zscript/DoomerfallCorpses.zs`): a monster base, args[0] = the Daggerfall
  mobile archive, args[1] = its Daggerfall `MobileTypes` value. Display only: it stands still. **How a creature moves
  and fights is a subclass's job and the owner's call** (see questions).
- **`UZDoom/src/dd_creatures.cpp`**: each tic (in a bridge session, from `DD_TownsfolkTick`) draws every live
  DFCreature with the runtime reader (`DD_MobileSprite`, the same path as guards and townspeople, so texture packs
  apply): attack records while in its Melee/Missile sequence, hurt in Pain, move in See, idle otherwise (move records
  if the archive has no idle). At death: Daggerfall's blood splash, the body hidden, and a corpse place sent with the
  creature's type. Outdoors the world position comes from inverting the treadmill's world-to-Doom mapping. A creature
  without an id gets a clock-based one (tag 0), so a saved corpse never matches a new creature.
- **Bridge**: `dfb_corpse_place` gains `creature` (MobileTypes + 1, 0 for a person). Bindings regenerated (struct 32
  to 40 bytes, schema hash changed, so the bridge DLL and launcher were rebuilt). All eight id tags are in use, so a
  new tag was not an option.
- **Daggerfall** (`DoomerfallTownspeople.OnCorpsePlace`, `DoomerfallCorpses.CreatureCorpse`): a creature's corpse is
  `EnemyBasics`' corpse texture for its type (Daggerfall's rule, as in `EnemyDeath`), kept in the same corpse ledger as
  townspeople and guards, so leave/return and save/load work the same way.
- **Test only**: `TCCreature` in `tools/town_corpses/harness.zs` (a rat, TEXTURE.255, type 0, that walks up and bites
  for 0), mode `creature`.

## Plan

1. Bridge kinds 200-205 (`PLACE_BEGIN/NAME/FACT/PLAN/END`, `PLACE_REQUEST`): one place's whole record, both ways.
2. Doom (`UZDoom/src/dd_locations.cpp`, new): report the current dungeon's record when leaving it and ahead of every
   save request; on entering a dungeon ask Daggerfall for its record and apply it before any mook is planned.
3. Doom's world table (`dd_treadmill.cpp`) becomes a cache: `Park` split into `MakeRecord` so a snapshot can reuse it;
   `DDTreadmill_SnapshotPlace` and `DDTreadmill_ApplyPlace`.
4. Daggerfall (`DoomerfallLocations.cs`, new): the ledger, keyed `D<map id>`, saved by `DoomerfallSave` as
   `DoomerfallLocations.json`; it wraps the death ledger (a corpse fact for a mook makes sure the mook is dead there).
5. Prove it: paired run at area level 30 in Privateer's Hold; then load; then load with the world table removed.

## Design decisions (engineering calls)

- **Events, not the bulk slot.** The card suggested the existing bulk slot. A bulk slot holds 64 KB and is single
  buffered, so a slaughter-sized record (1,000+ facts) would need chunking with acknowledgements, and the save request
  would have to wait for them. The ordered event ring already carries Daggerfall's monster lists one row per event, and
  it keeps the record ahead of the save request that follows it with no extra handshake. One fact is one 64-byte event.
- **What a fact is.** Exactly the world table row from card 1: kind (alive but moved or hurt, corpse, item, gone), Doom
  class and death label (by name), position in Daggerfall units in the place's frame (Doom map units / 0.75), angle,
  corpse height, health, item amount, dropped flag. Ids are Daggerfall-derived (mook ids, map pickup ids); Doom drops
  have no such id and are flagged `DFB_FACT_SESSION` and kept by position.
- **The dungeon plan travels too.** A revisit must plan with the first visit's quest placements (card 1). If Doom's copy
  is gone, the plan must come from Daggerfall, so the record carries it (`PLACE_PLAN`).
- **Apply only on entry.** A load inside a dungeon restores Doom's snapshot, which is newer than any record, so the
  record is applied only when Doom builds a place (`StartTown`), never on a resume.
- **Cache check.** When Doom's cached rows for the place equal Daggerfall's record (compared as the bridge carries them),
  nothing is touched. Otherwise the place is rebuilt from the record: what the cache restored is removed and every fact
  applied. Mooks the record does not list are spawned by the plan, as on any visit.
- **Order on entry.** `ApplyRows` (monster list, which plans and spawns mooks) waits until the record is applied, at
  most 5 s; without an answer Doom builds from its cache and logs it.
- Tombstones of map pickups now carry the pickup's spot (`itemSpots`), so a take belongs to its place. Before, a take of
  an item with no earlier row was stored at 0,0.
- "Unlocked or opened": no locks exist yet, so there is no fact kind for it. Adding one is a new `DFB_FACT_*` value.

- **Pacing.** A record is sent at most 2,048 events per frame on each side, and on Doom's side only when the outbox is
  empty; Doom's save request is queued behind its record, so the order holds. The ring holds 4,096 events and each
  outbox 16,384, so an unpaced record of about 20,000 facts (a big dungeon at area level 30) would fault the bridge.
- **Park decides every row before destroying anything** (`ParkAll`). Destroying a monster clears other monsters'
  `target` pointers, so alerted but untouched monsters turned "unchanged" partway through the loop. The snapshot (no
  destroys) then had 2 more facts than the table, which forced a needless rebuild on every visit. Found in a run.

## Findings

- A slaughter dungeon's record is dominated by Doom drops: 1,932 of 3,782 facts are loose items, mostly weapons and
  ammo the dead dropped (and their DoomerfallAmmo replacements). Corpses are the second half. Hurt or moved monsters
  are few, because untouched mooks are rebuilt from the plan.
- At area level 30 the stock pack infights for most of a minute after it is placed (living 2,197 -> ~935 in 50 s with
  the player invisible). That is outside this card, but it means many deaths Daggerfall records were not the player's.
- The cache comparison is cheap (4 ms for 3,782 facts) and in every normal visit and load the cache matched the
  record, so the record only changes the place when Doom's copy is missing or older.
- The record carries the dungeon's plan, so a place rebuilt without Doom's table planned exactly as the first visit
  (2,197 mooks, the same 48 untouched mooks respawned as in the normal load).

## Not tested

- **Map pickups taken (tombstones).** The packaged Privateer's Hold places no map items, so no `DFB_FACT_GONE` fact
  occurred; the take in the route was a dropped clip (a session item, which is simply absent afterwards). The gone path
  is the same code as the others, and tombstones now carry the item's spot (`itemSpots`), but it was not run paired.
- The death-ledger wrap ("N deaths added") never fired: every death event arrived.
- A record that arrives after the 5 s wait, and a record of a place the player already left (both logged and ignored).
- The rebuild after a cache that disagrees with the record about a map item: the original map item cannot be brought
  back if Doom's cache had removed it and the record has no row for it. This cannot happen in normal play (the record
  and the cache come from the same snapshot and the same save); it is logged as part of the rebuild counts.
- DRLA: these runs use stock monsters.

## For card 3 (towns and the overworld)

- Guard ids use tag 4 (bit 63 alone), which is also the pattern of Doom's session ids (`DYNAMIC_BIT | n`). In a dungeon
  there are no guards; in towns `IsSessionId` must tell them apart before guards' facts go to the ledger.
- `DDTreadmill_CurrentDungeon` and `DFB_PLACE_DUNGEON` are the only place kinds; interiors (`B<map>:<key>`) are
  already keyed by Daggerfall's ids in Doom's table (card 1) and can use the same record.

## Failed approaches and harness fixes

- First runs waited for the living count to hold still before acting; the slaughter pack infights for about 50 s, so
  the route timed out. It now waits a fixed 5 s.
- The leave and re-entry checks first differed for monsters stopped in mid-air or mid-slide, and then because the
  harness zeroed vertical speed every tic so re-spawned mooks could not land. The harness now stops only horizontal
  movement and the comparison accepts settling and falling.
- The first load run finished at once: the save carried the first route's state. The load route now resets it.

## Play-test list

- Clear most of a big dungeon at a high area level, leave and come back: every corpse is where it fell, nothing you
  killed is alive, the untouched monsters stand where they stood.
- Wound a strong monster, let it chase you to another room, leave: when you come back it is in that room with the same
  health, not back at its spot at full health.
- Drop a few items and take some, leave, return, save, load: the same items are on the floor.
- Notice the entry hitch at a high area level: the record adds about 5 ms, the planner still about 0.9 s.
- Save inside a dungeon full of corpses and load it: nothing doubles (corpses, drops, Daggerfall loot piles).

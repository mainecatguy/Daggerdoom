# Synchronized saving, proven with both real games

## Status

Saving on a Daggerfall map now makes one `.zds` holding a real Daggerfall save and Doom's save. Menu saves and autosaves both work with the real games, outdoors, in a building, and in a dungeon.

Run the suite with `python tools/synchronized_save/run_all.py`. Its last run passed 16 of 16 cases, and the scripted handshake test passed 45 of 45 on the same build.

## Plan

1. Run the existing code against real Daggerfall and see what breaks.
2. Fix it, and route autosaves through the bundle.
3. Prove failure handling, the hitch, and that stock behavior is unchanged.

## What broke and what I fixed

1. **Every real save failed.** The test character has no backstory, so Daggerfall's save threw a null reference while `bio.txt` was open. That also left the staging folder behind. Saving now tolerates a missing backstory.
2. **Autosaves were Doom-only.** On a Daggerfall map they now go through the bundle and keep their normal trigger and rotation.
3. **An autosave before Daggerfall is ready would have been lost or Doom-only.** It now waits up to 60 seconds, then runs. If Daggerfall never becomes ready it is dropped and no Doom-only autosave is written.
4. **Doom kept simulating after asking Daggerfall to save.** The request was sent mid-tic, so one more hit could follow it. The stress log showed this. Those saves matched only because Daggerfall read the extra event in time. Saves now start between tics, and the stress test shows 0 events after the freeze across 10 saves.
5. **Indoors, Daggerfall could save a stale position.** It updates once a second, so a quick door trip saved a spot about 3,100 units from the door. The save now applies the door position first.
6. **Saves were limited to the test start.** Daggerfall now accepts them in any game in progress. No real start flow exists yet to prove this.
7. **A failed automap write could be silently missing from a bundle.** It now fails the save and keeps the previous one.

## How failures are handled

Any failure before the final atomic file replace leaves the previous save byte-identical, tells the player, and resumes both games. Proven with real games by failing at Daggerfall's write, Doom's zip, and Doom's commit, and by crashing Doom after the temp file was written. After a crash, the leftover temp files are removed by the next save to that name.

## Autosave hitch

Time both games are frozen, measured from Doom's request to its commit. These ran minimized on the RTX 5080 machine.

| Case | Saves | Median | Worst |
|---|---|---|---|
| City of Daggerfall | 6 | 168 ms | 183 ms |
| City with 2,000 dormant monsters | 6 | 176 ms | 201 ms |
| City with HP events every tic | 10 | 165 ms | 189 ms |
| Building interior | 1 | 85 ms | 85 ms |
| Privateer's Hold | 1 | 122 ms | 122 ms |
| Held until Daggerfall was ready, just after startup | 1 | 340 ms | 340 ms |

The freeze is about a fifth of a second in the city, roughly 5 to 6 Doom tics. Doom's half takes most of it. The monsters were dormant imps, so a real DRLA fight on a Daggerfall map may cost more.

## Proven with the real games

- A real bundle: HP 80 and the same position in Doom's half, Daggerfall's half, and the manifest, after 20 hits in flight.
- Daggerfall's own loader loads the half taken from a bundle, with health 80/100 and the right position.
- A normal Daggerfall save through its own `Save` entry point writes all its files, including the screenshot. This ran inside a bridge-launched session.
- A plain Daggerfall launch with no bridge starts with no bridge activity.
- `DOOM.WAD` E1M1, stock and with the DRLA set, makes normal menu saves and autosaves with no Doomerfall content.
- The owner's Daggerfall registry key hash was unchanged across every launch.
- The thumbnail shows the real city view.

## Not proven, and known gaps

- A human has not used the real save menu on a Daggerfall map. The tests call the same save function the menu calls.
- Killing the real Daggerfall mid-save was not run. The scripted peer covers a silent Daggerfall.
- Saving from a real new game, because that start flow does not exist yet.
- Indoors, Daggerfall's half records the player outside at the door, because Daggerfall is not moved indoors yet.
- A mod that fails to save its data is logged and the save continues, as in normal Daggerfall.
- Loading a bundle back into both games is out of scope.

## Failed approaches

- `+logfile` turns its argument into `log-<name>.txt`, so my first console checks read nothing. Fixed in the runner.
- DRLAX prints a harmless `Script error` at every load, so it cannot count as a fatal marker.
- City of Daggerfall's dungeon is not converted, so the dungeon test uses Privateer's Hold.

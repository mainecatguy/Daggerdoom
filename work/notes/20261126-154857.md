# Pause the game during the arrival setup wait (20261126-154857)

Goal: during a stitched map change's setup wait (card 04: `PumpArrival` waits for `DD_SetupReady` before the arrival
autosave, the screen holds the old frame), Doom kept ticking, so monsters could act and hurt the player unseen for up to
the 5 s gate timeout. Pause the game for the wait, keep the window responsive, resume when setup is done or times out.

## Plan and why

- **A plain `pauseext` pause does not work.** The setup needs tics: the gate's own `dd_setup_settled`, `dfdoor_facts`,
  `dfdoor_arm` and `dfdoor_ready` are network events run in `G_Ticker`, and Daggerfall's place record is applied in
  `DDTreadmill_Tick` (`DD_LocationsTick`), which also spawns the dungeon's monsters. With `pauseext` no tic runs, so
  setup would never finish and every arrival would wait the full 5 s.
- **What was built: a playsim freeze inside `P_Ticker`.** `DD_BridgeArrivalFreeze(Level)` (`dd_bridge.cpp`) is true
  while `arrivalPending` (the arrival waits for setup), after the new map's first tic (it finishes the handoff), with a
  session, for the primary level, and within the existing 12 s hold limit. The hook in `p_tick.cpp` comes right after
  `DDTreadmill_Tick`: when frozen it skips particles, player think, `WorldTick`, `Level->Tick`, `RunThinkers` and sector
  specials, and does not count level time either. So no actor, player, weapon, projectile or special runs, while network events
  (`G_Ticker`) and Daggerfall's records (`DDTreadmill_Tick`) still apply. The freeze ends where the wait ends
  (`PumpArrival`, on setup done or the gate's timeout). The autosave right after already freezes with `pauseext`.
- **Level time stands still while frozen** (verifier fix, round 2). The first version kept counting `time`,
  `maptime` and `totaltime`, as Doom's own freeze does. The verifier found that this silently skips mods' exact-time
  triggers: DRLAX runs map-start logic on `Level.Time == 2`, `== 3`, `== 5` and `== 70` (familiars, Phase Sisters,
  Nomad, the Cursed Dagger, deployers). Doom's own freeze still calls `WorldTick`; this freeze does not, so those values
  were never seen. My reason for counting was wrong. The freeze starts at maptime 1, so a held maptime is never 0
  (`Start`) and never a multiple of `SCAN_TICS` (8). Other users of maptime that run before the hook: `dd_lights.cpp`
  and `dd_weather.cpp` reapply their state while maptime <= 1, so they reapply on each frozen tic (idempotent, only
  during the wait). `dd_monsters.cpp` claim deadlines simply do not expire during the wait. The harness now checks that
  its `WorldTick` sees `level.time` 0, 1, 2, ... inside the dungeon with no gap.
- **The freeze no longer depends on autosaves** (verifier fix, round 2). `g_level.cpp` now calls
  `DD_BridgeArrivalAutosave(save)` for every stitched change, with `save` = the old autosave condition. With autosaves
  off the arrival still waits frozen (and with the frame held) until setup is done or times out, then makes no save.
- **Loading message** (the owner's loading-screen rule in `work/todo.md`: pause, show a message, resume):
  `DD_BridgeDrawLoading` replaces `D_Display` while the frame is held. Under 1 s after the map loaded it draws
  nothing, so the old frame stays and normal arrivals look as before. After that it draws black with "Loading..." in
  the big font, every loop pass, until the hold ends. (A first version used 300 ms. A normal entry's hold, autosave
  included, ends at about 450-550 ms, so every entry would flash the message for about 0.2 s. With 1 s it does not.) The hold also covers the arrival autosave, so the message stays up
  while that save is written.
- **Stock Doom**: the freeze needs a bridge session and a pending stitched arrival; the loading draw runs only while
  `DD_BridgeHoldFrame` is true, which also needs a session. Neither can happen in a plain WAD.

Game code changed: `p_tick.cpp` (2 lines), `d_main.cpp` (2 lines), `g_level.cpp` (the arrival call), `dd_bridge.cpp` (freeze predicate, freeze log,
loading draw), `dd_setup.cpp` (a one-line test hook). Test only: new `dd_arrival_test.cpp` (`-dfsetuptest <ms|lost>`
adds a fake setup system that answers late or never; `-dffreezetest` logs, to the bridge log, whether any monster,
missile or the player changed during the freeze, including monsters spawned during it, the player's health, and the
largest gap between frames), called from `dd_bridge_test.cpp`. Runner: `tools/arrival_freeze/run_freeze.py`.

### Finding: the remaining stall is the monster spawn tic

The largest frame gap (150-250 ms) is one tic of the setup, in `DDTreadmill_Tick`, that spawns the dungeon's monsters.
It blocked the loop before this goal too (card 04's "one long blocking frame"). It now runs inside the freeze, so the
monsters cannot act after spawning. The window stays responsive in the sense the goal means (no multi-second stall).
But that tic is not split up, and the location record notes measured 1.9 s for a cleared level-30 dungeon. That
belongs to the generic loading-screen work (todo "Loading screen for long operations"), not to this wait.

### Failed approach and a wrong lead

- A first run showed setup done at about 90 ms but the freeze ending at about 290 ms. Temporary logs (removed) showed
  `DD_SetupReady` was not called in between: the loop was blocked in the spawn tic above, not waiting. The first
  version of the test missed this because it did not measure the gap before the comparing frame. Fixed.

## Known gaps

- Performance: while the frame is held and no message is drawn yet, the main loop does not draw or wait, so it spins
  (about 24,000 passes in a 2.5 s slow run, against about 1,000 per second while drawing). Card 04's hold already did
  this. It now lasts up to 1 s of a long wait. Not changed here.
- Player input during the freeze is dropped (the player's tic does not run), as in a pause.
- A non-stitched map load (plain `+map`, a New Game start) still uses `DAutosaver` and the held autosave. It has no held
  frame and no freeze. That is not part of this card.
- "Loading..." is plain English text in the big font, centered on black. The look is a play-test item.

## Round 3 (verifier: Use and townspeople acted during the freeze)

- **Use is dropped during the freeze.** `TickTownDoors` (runs in `DDTreadmill_Tick`, before the freeze hook) still read
  `BT_USE`, `dd_tm_use` and the stored door press, so a press could take an item, talk, or leave by the exit unseen.
  It now consumes them (keeping `useHeld` current, so a held key does not fire on resume) and returns while
  `DD_BridgeArrivalFrozen()` is true. My round-1 note "player input during the freeze is dropped" was false for Use.
  It is true now.
- **Townspeople are held.** `DD_TownsfolkTick` (placement and movement toward Daggerfall's rows) is skipped while
  frozen. They are placed or moved on the first tic after the wait. Checked only by reading the code: no town-arrival
  freeze run was made.
- `DD_BridgeArrivalFrozen()` is a pure query (no log, no count). `DD_BridgeArrivalFreeze` uses it. The comment that
  said level time counts was fixed.
- New mode `run_freeze.py use`: on the new map's first tic (before the freeze) the harness turns the player to face out
  of the entrance, as tools/lockpick's trip does to leave. Then `-dffreezeuse` presses `dd_tm_use` on every frozen
  frame. **Negative control:** with the Use guard removed it failed: the player left the dungeon during the freeze
  (`playsim frozen 7 tics ... until another map change`, three arrivals). With the guard: `use PASS`, 12707 presses,
  one arrival, `changed=0`, `first_time 0 time_gaps 0`. A first try turned the player from the test frame, between
  tics; player prediction undid it (`changed DoomRLMarine`), so the turn moved into the harness.
- Re-run with the guard: normal, slow, lost and nosave all `PASS`. `run_paired.py take` 12/0. `check`: stock exit 0 with
  0 script errors; DRLA exit 0 with the 3 known script errors.

# Synchronized saving

## Status

The handshake, bundle, and failure handling are proven on the real UZDoom exe against a scripted Daggerfall peer.
**No save has been made with real Daggerfall Unity in a game.** This session was denied `D:\dev\DoomDaggerfall\GameResources` and `D:\dev\DoomDaggerfall-build`, so it had no IWAD or Daggerfall data. I did not work around that.

## Plan and decisions

- A request from frozen Doom is the barrier. The event ring is ordered, so three messages replace the five proposed in `20261122-233946.md`.
- Only a save from the menu or console on a Daggerfall map enters the handshake. The gate is the map's world context, so no `--flow` flag is needed. E1M1 over the bridge keeps normal saves.
- Quick keys and quit are untouched, per the owner.
- Daggerfall writes with its real save code through `SaveLoadManager.SaveToFolder`, with no screenshot and no use of normal save slots.

## Save format

One UZDoom `.zds` zip containing:

- Doom's normal entries (`info.json`, `globals.json`, `savepic.png`, map snapshots).
- `doomerfall/daggerfall/...`: every file of the real Daggerfall save.
- `doomerfall/manifest.json`: format 1, transaction, HP, max HP, last applied HP event, Doom's HP, Daggerfall and Doom positions, yaw, world context, map pixel, map name, and file list.

## Handshake

1. Doom checks that Daggerfall is live and in play, creates `<save>.dfstage`, and puts that path in bulk slot 4.
2. Doom sets `pauseext`, publishes its final position, and sends `SAVE_REQUEST` (transaction, last HP event sent).
3. Daggerfall has applied all earlier events because the ring is ordered. It refuses if it cannot save, otherwise pauses, applies Doom's position, waits for the world to settle, and writes to staging.
4. Daggerfall sends `SAVE_PREPARED` (status, HP, last HP event applied, file count, bytes, position).
5. Doom undoes client prediction, requires that every HP event was applied, sets its HP to Daggerfall's, and writes `<save>.tmp` with both halves.
6. Doom verifies the zip, flushes it, and atomically replaces the save. This is the commit point.
7. Doom sends `SAVE_DONE`, removes staging, and both games resume.

## Failure handling

Any failure before step 6 leaves the old file untouched. Doom prints the reason, tells Daggerfall to resume, and removes its temp files. Doom gives up after 10 seconds or a stale heartbeat. Daggerfall resumes by itself 15 seconds after answering if Doom never reports back. After a crash, leftovers stay until the next save to that name removes them.

## What was proven

`python bridge/test/save_handshake_test.py <uzdoom.exe> <doomerfall_bridge.dll> <empty folder>`: **45 of 45 checks passed** on the real UZDoom build, with a generated test IWAD and a scripted Daggerfall peer.

- The bundle is a valid zip with both halves, and nested files are byte exact.
- 20 HP events in flight at the request were all applied. Manifest, Doom, and the level snapshot all hold HP 80.
- These each left the previous save byte-identical: refusal, Daggerfall write failure, silent Daggerfall, file count mismatch, HP mismatch, zip failure, commit failure, and a process crash before commit.
- UZDoom's stock loader restores the bundle's Doom half with HP 80.
- A regular map over the bridge, and a run with no bridge, both make normal saves through the menu's save function.

Real Daggerfall Unity: the build succeeded (`CliBuild result: Succeeded`). With no game data, the built exe received a real save request over the bridge and answered with a refusal, "not in play" (`review/synchronized-saving/tools/dfu_smoke.py`).

## Not proven

- A real Daggerfall save written to staging, its position sync, and its pause and resume.
- A bundle from a real Daggerfall map, with thumbnail rendering on that map.
- `DOOM.WAD` E1M1, stock and with the DRLA set.
- That a normal Daggerfall Unity launch is unchanged. The new code only runs under `-dfbridge`, but `SaveGame` was edited, so a normal in-game save should be checked.

## Known gaps

- Daggerfall accepts a save only after the test start (`-dfsynctest`), because `InGame` is only set there. The real start flow must set it.
- Doom autosaves and quicksaves on a Daggerfall map are still Doom-only, so they have no matching Daggerfall half.
- Daggerfall's save code logs and continues if automap or mod data fails, so those parts could be missing from a bundle.
- Loading restores only Doom's half. Loading is out of scope.

## Failed approaches

- `zlib.h` is not available to the engine. It uses miniz, which has the same API.
- Console scripts cannot time a save from the command line, because `wait` does not delay during startup. The control saves use a test-only ZScript handler that calls the menu's `DoSave`.
- The first load check proved nothing, because `+map` could override the load. It now saves again after loading and checks HP.

# Transport menu from Doom (20261127-113137)

Goal: a key in a paired run opens Daggerfall's transport menu (foot, horse, cart, ship) in Doom, listing what the player
owns as Daggerfall Unity does, with the choice kept by Daggerfall. Report what riding would need on the Doom side.

## Plan

1. Follow the spellbook/character sheet key (commit f1b68be5): a new menu id `DFB_UI_TRANSPORT` (13) in the bridge
   schema, a `netevent df_transport` Doom control (Customize Controls, "Open Transport"), bound to **T** on a fresh
   install (Daggerfall's own Transport key; in Doom T was only chat, `messagemode`).
2. Daggerfall pushes its own `DaggerfallTransportWindow` (unchanged), so the rows, greyed-out art and ownership checks
   are Daggerfall's.
3. Daggerfall's open checks (`DaggerfallUI`, `dfuiOpenTransportWindow`: not inside, on the ground) look at its hidden
   player, which waits outside the door Doom used (as `dd_bridge.cpp` already notes for fast travel). So Doom sends
   where its player is (`DFB_WORLD_*` plus `DFB_TRANSPORT_AIRBORNE`), and `DoomerfallUi` applies the same two rules:
   indoors shows Daggerfall's own localized line (`cannotChangeTransportationIndoors`) on Doom's HUD; in the air or
   swimming it opens nothing, silently, as Daggerfall does.
4. Test hook `DoomerfallTransportTest.cs` (`-dftransporttest <file> [none]`, its own file, no game class calls it) and
   harness `tools/transport/transport.py`.

## Ship (judgment call, please confirm)

Daggerfall's Ship row is not a mode: it teleports Daggerfall's world to the ship's map pixel (2,2 or 5,5, a corner of the
map) with `StreamingWorld.TeleportToCoordinates`, and back to the saved spot on the second use. That is not a fast
travel, so Doom would not follow and the two engines would desync. Doom would also need a map for the ship pixel, which
the overworld converter has probably never produced. So in a bridge session the Ship row shows "You cannot board your
ship yet." and does nothing (`DoomerfallUi.HoldsShip`, a one-line hook in each of the window's two Ship handlers, the
same pattern as `HoldsSpellChoice`). The row is still listed exactly as Daggerfall lists it (lit when a ship is owned).

## What riding would need in Doom (not built, reported as the goal asks)

Choosing Horse or Cart sets `TransportManager.TransportMode`, which Daggerfall saves (`SerializablePlayer`,
`transportMode`). In Daggerfall Unity that mode then:

- changes speed: `PlayerSpeedChanger` uses `dfRideBase` (horse) or `dfCartBase` (cart) instead of walking speed, and
  riding a horse with no cart allows faster running;
- changes jumping/climbing: `AcrobatMotor` blocks jumping on a cart and raises jump height on a horse; climbing is off
  while riding (`PlayerMotor.IsRiding`);
- draws the horse or cart sprite at the bottom of the view and plays riding sounds (`TransportManager.OnGUI` and
  `Update`); in a bridge session Daggerfall's 3D view and its HUD are hidden, so nothing shows;
- is dropped to Foot by Daggerfall on entering a building or dungeon.

None of that reaches Doom. Doom would need: the mode in Daggerfall's published state (a field or flag), a speed and
jump rule applied to Doom's player (who decides the numbers is a design question: Daggerfall's ride speeds vs. Doom's
run speed), a horse/cart weapon-layer sprite or HUD overlay, and a rule for fighting while mounted (Daggerfall lets you
attack from horseback; Doom weapons are drawn where the horse sprite would go).

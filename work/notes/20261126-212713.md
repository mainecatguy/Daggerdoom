# Daggerfall remembers taken Doom pickups (run 20261126-212713)

Goal: `work/goal.md` (taken seeded Doom pickups stay gone through leave/return, save/load, and a rebuild without the Doom
snapshot). Decision: `gamedesign/decisions/20261126-ammo-pickups-baron-taken-guards-owner.md`.

## What already exists (read before planning)

The location record (cards 1-6, `work/backlog/location-record.md`) already has the mechanism:

- `dd_treadmill.cpp` `AssignMapItemIds`: every loose item at map start gets a stable id, `MAP_ITEM_TAG | hash(map
  name) | index in thinker order`. The converter places the pickups (`PickupExport.cs` markers,
  `DoomerfallPickups.zs`), so the order is fixed.
- The tiered ammo swap (`DoomerfallAmmo.zs` `Convert`) replaces a placed clip/shell a tic later; the treadmill hands the
  replacement the map item's id (`dd_treadmill.cpp` ~600), so it is neither a take nor a drop.
- A taken id becomes a tombstone (`MarkGone`, kind `KGone`), reported to Daggerfall on leaving and before each save
  (`dd_locations.cpp`), and kept on disk as one bit per map item (`DoomerfallPlaceCodec.cs`, "gone pickups").
- On entry the record is applied before play (`DD_LocationsEntered`); a gone row removes the map item.

So the goal is mostly to prove it in a paired run, and fix what the run shows.

## Findings

Test folder: `review/taken-pickups` (fresh `install.py` from this branch; DFU built from this branch, `CliBuild result:
Succeeded`). Logs: `review/taken-pickups/test-taken`. Every run: DRLA set, Privateer's Hold at area level 1, monsters
removed by the harness, 3 pickups taken by `Inventory.Touch` (2 `RLStimpack` after real damage, 1 tiered shell
`DFAmmo_Shell_5`), 3 left (`DFAmmo_Shell_0`, `RLStimpack`, a jackpot `DFAmmo_Clip_4`).

### Baseline on the engine as it was (before any change here)

- Leave and return: **pass**.
- Load the save made inside: **pass** right after the load (Doom's snapshot).
- Then leave and come back: **FAIL, all taken pickups came back** (`4 back`). Cause: the save keeps no world table
  (`DDTOWN resumed MAP01 records=0`), and after resuming a save made in a space Doom never asked Daggerfall for that
  place's record. Leaving then reported the place from live actors and an empty table: `49 facts (48 items, 1 gone)`,
  replacing Daggerfall's record, which had 6 gone. The "snapshot stands" branch in `DDTreadmill_ApplyPlace` existed
  but never ran (the location record notes say the same: "It has never fired").
- The first loadout run also failed, but that was my harness: the loadin run's own map change autosaves rotated into
  `auto02.zds`, so loadout loaded an inside save. The runner now copies the take run's saves to `inside.zds` and
  `town.zds`.

### Changes (`UZDoom/src/playsim/dd_treadmill.cpp`, only active in a bridged session on a Daggerfall map)

1. **Resume asks for the record.** In the resume path for a space, Doom now calls `DD_LocationsEntered` and marks
   `resumedSnapshot`; `DDTreadmill_ApplyPlace` then takes the existing "snapshot stands; the record only refills the
   cache" branch (before, only when one of the record's monsters or corpses was live, so a place where only pickups
   changed fell through to a rebuild, or, in practice, was never asked for at all). The setup gate is not active after
   a load, so this adds no freeze.
2. **After a load, map items get their spot and starting amount back** (`ExpectLoaded`), so a take after the load still
   becomes a tombstone with its place's position.
3. **Reverted after verification (out of scope, changes what saves hold).** The change described below was removed;
   the record-size leak is reported to the owner instead (Suspected oversights). Final results are under "Results after
   the revert". What the reverted change did: **untaken tiered ammo no longer stored as changed.** `IsUnchanged` compared a map item's amount with its class
   default; a tiered pickup (`DoomerfallAmmoPickup`, `Inventory.Amount 1`) holds 10 or 4 rounds, so every untaken one
   became a full row on every departure (engineering rule 8's leak, for dungeons). It now compares with the amount the
   item started with (recorded at id assignment and when the tiered heir takes the id). Record of the test dungeon on
   leaving: 49 item rows / 4288 bytes before, 21 / 2240 after. The 21 left are one jackpot's 20 scattered pickups and
   one other loose item, which are real loose items.

### Results after the changes (`run_taken.py all`, then `loadin` again with its final harness)

- take: 3 taken pass; after leaving and coming back the 3 taken are gone, the 3 untaken there once each (74 loose
  pickups = 77 - 3).
- loadin: `the save's snapshot stands ... 5 facts refill the cache, nothing rebuilt`; taken gone, untaken there; a
  placed shell taken after the load (`7 gone` on leaving, was 6); after leaving and coming back all 4 taken gone, the
  2 untaken there.
- loadout (town save, new launch, then walk in): `rebuilt from Daggerfall's record (Doom's cache had 0 rows, the record
  26): removed 5, restored 21, gone 5`; taken gone, untaken there, 74 loose pickups.
- `run_taken.py check`: DOOM.WAD E1M1 stock exit 0, 0 script errors, 0 DDLOC/DDTM lines; with the DRLA set exit 0, the
  3 known DRLA script errors, 0 DDLOC/DDTM lines.

### Results after the revert (final engine: changes 1 and 2 only)

`run_taken.py all`: take PTRESULT passed=5 failed=0, loadin passed=5 failed=0 (`the save's snapshot stands ... 33 facts
refill the cache, nothing rebuilt`; the shell taken after the load gives `7 gone`), loadout passed=2 failed=0
(`rebuilt from Daggerfall's record ... removed 33, restored 49, gone 5`). The record is back to 49 item rows / 4288 bytes
on leaving. `run_taken.py check`: stock exit 0, 0 script errors; DRLA exit 0, the 3 known DRLA script errors; no
DDLOC/DDTM lines in either.

### Notes

- Taken pickups reach Daggerfall on leaving and before each save (the place's record), not the moment they are taken.
  That is enough for every case in the goal, because Daggerfall's copy only matters at a save or a place change.
- Leaving town reports 6-7 gone facts in exterior chunk `O437,1363` though nothing is taken there and the town has
  no seeded pickups. Most likely loose inventory things in the town map at start (given ids) that remove themselves.
  Harmless (a few bits), not investigated.
- Paired runs used the DRLA set only (as `play.bat`); a paired run without DRLA was not done. The stock pickups take the
  same id path (the converter's markers spawn `Stimpack`/`Clip`/`Shell`, and the tier swap runs in both sets).
- Only Privateer's Hold (dungeon) was tested. Towns use the same id and tombstone path but have no converter pickups.

## Failed approaches

- Lowering health with `A_SetHealth` so a stimpack is wanted: Daggerfall owns HP, so the touch was refused. Real damage
  (`DamageMobj`) and a second's wait for the HP sync works.
- Checking a tiered ammo take in the same tic: the pickup goes once Daggerfall answers `dfa_take`; the check now waits
  a second.

## Suspected oversights

- Record-size leak (architecture engineering rule 8, for dungeons): every untaken tiered ammo pickup is written to the
  place record as a full item row on every departure, because `IsUnchanged` (`dd_treadmill.cpp`) compares its amount
  (10 or 4 rounds) with the class default `Inventory.Amount 1`. Test dungeon: 49 item rows / 4288 bytes, about 21 / 2240
  without the leak. A fix was tried here and reverted as out of scope. A fix also changes how an untaken tiered pickup
  comes back (re-rolled by `DoomerfallAmmo.zs` with the handler's current areaLevel, not read from the record), so it
  needs its own check that tier and rounds are kept.

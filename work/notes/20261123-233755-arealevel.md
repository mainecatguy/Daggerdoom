# Area levels computed in Daggerfall (run 20261123-233755)

Goal: Daggerfall computes every location's area level and the wilderness terrain level at runtime, from
the approved proposal (`work/notes/20261123-225515-area-level-proposal.md`, `tools/area_level/`), and the
enemy drops read it instead of a fixed level 1. `-dfarealevel N` stays as a test override.

## Plan

1. Port `area_level.py` to C# in its own file, `Doomerfall/DoomerfallAreaLevels.cs`. Same tables,
   seeds, hash, and floating point order, so levels match bit for bit.
2. Rank stability: read classic `MAPS.BSA` and `POLITIC.PAK` straight from Arena2 with fresh `BsaFile`
   and `PakFile` objects, not through `MapsFile`, so world data mods that add locations or repaint
   regions cannot move classic ranks. Only the classic count in each names record is read (what DFU's
   `ReadLocationCount` reads). A location a mod adds gets a level by placing its score among the sorted
   classic scores of its size class (`PlaceAmongClassic`).
3. Cost: build once on a worker thread, started from the bridge's `Update` as soon as DFU knows its data
   path. The first lookup joins the thread if it is not done. Measure both.
4. Wire in: `DoomerfallDrops.AreaLevel(location)` returns the override if given, else the location's
   dungeon level (or terrain level if it has no dungeon). `DoomerfallMonsters.BuildPlacements` passes the
   current dungeon and keeps the level for `Roll`, which runs right after for the same map.
5. Verify with a test hook (`-dfarealeveldump <dir>`, in `DoomerfallAreaLevelsTest.cs`, no line in any main
   class: it self-starts from `RuntimeInitializeOnLoadMethod`) and `tools/area_level/compare_runtime.py`,
   which compares every location and every land pixel with the script. Then a real paired drops run.

## Decisions (ordinary engineering calls)

- Lookups: `ForLocation` (dungeon and terrain), `ForMapPixel` (wilderness), `ForCurrentPlace` (dungeon
  level inside a dungeon, otherwise terrain of the player's map pixel). Only drops use them today.
- Water and off-map pixels count as terrain 1, as the script does (Mantellan Crux at pixel (1, 1)). The
  proposal says Crux "should get an override" but gives no value, so its dungeon level stays the formula's.
- If the table cannot be built (missing file), drops fall back to level 1 and the monsters log line says why.

## Findings

### Runtime levels match the script exactly

`python tools/area_level/runtime_check.py stage` then `... dump` (Daggerfall alone, minimized, with
`-dfarealeveldump`, then `compare_runtime.py`):

```
locations: 15251 in script, 15251 at runtime, 0 only at runtime, 0 differ
terrain pixels: 319766 land, 0 differ, 19 unranked on both sides (runtime reports 1)
area levels: 15251 locations ranked in 95 ms on a worker, main thread waited 96 ms
fallback on 4231 classic dungeons: 4231 same, 0 differ
```

Every classic location's dungeon and terrain level, and every land pixel, is identical to `area_level.py`.
The 19 "unranked" pixels (around (654..659, 20..22)) have a politic value past the last region. The script
treats them as water and so does the runtime ranking; the runtime reports an unranked pixel as level 1,
the same default the script gives a location on one. The fallback for mod-added places, run on every
classic dungeon except the override, puts each one exactly on its own rank, so mod-added places get
levels consistent with the classic ones.

The same dump runs the drops' `EnemyPicker` at level 1 and at the computed level. For example Castle

19; Tristore Laboratory gets Ancient Liches at 18.

### Cost

- Ranking every location and all 319,766 land pixels: 95 ms, on a worker thread.
- Main thread: 0.7 to 1.8 ms to start the thread. The dump test asks for a level immediately, so it waited
  the full 96 ms; in a real session the thread starts at the first bridge frame and the first lookup is the
  first dungeon entry, much later (see the paired run below).
- Lookups after that are one dictionary read. Travel is unaffected.
- Memory: 500 KB of terrain bytes, a 15,251-entry dictionary, and 4,231 sorted doubles.

`runtime_check.py build`, `stage`, then `paired NAME [--area N] [--kill]`. These use this worktree's
bridge, launcher, UZDoom, and `doomerfall.pk3`, plus the Doom items demo's data (read only).

In a real session the ranking is done long before the first dungeon entry: the main thread waited 0 ms.
Drops roll through the new path. Privateer's Hold is level 1 by the proposal's override, which is also the
old fixed value, so the drop in this run is the same kind as before; the dump above shows the same
`AreaLevel` call returning 19, 25, 28, and so on for other dungeons. The kill harness then timed out
waiting to take the drop (step after `MDDROP`); that step is the older pickup route and is outside this
task. Each run's Player.log has one `NullReferenceException` in `DaggerfallUI.SetupSingleton` at startup,
before any Doomerfall code runs; it is not from this change.

### Failed approaches and snags

- First dump found nothing: the private settings had no Daggerfall path (paired runs pass it through
  `-dfsynctest`). `stage` now writes the path into the private copy's settings, and the test waits for it.
- First paired run: `bridge DLL does not match this build`. The Doom items review build predates the
  townspeople merge. `runtime_check.py build` now builds the bridge, launcher, and UZDoom from this worktree.

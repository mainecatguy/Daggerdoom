# Exact "which gun fired this" engine hook (2026-11-27, run 212559)

Goal: things a shot spawns took the weapon tag of the nearest tagged thing within 128 units, so mixed-gun fights could
credit the wrong gun. Add a small engine hook that passes the firing weapon to everything a shot spawns.

## Did the Explosives work already add a hook?

No. `DoomerfallExplosives.zs` reads the shared shot tag (`DoomerfallShots.zs`), which used only the nearest-parent rule
(`ChildReach = 128`). No engine code tracked spawn parents. So this run adds the hook and extends `DoomerfallShots.zs`
(which Explosives, Shotguns, Automatics, Energy and skill XP already read), rather than anything Explosives-specific.

## Plan

1. Engine: when an actor is spawned, record which actor spawned it.
2. Mod: `DoomerfallShots.Classify` uses that exact parent first; the nearest rule stays only as a fallback.
3. Test: two guns firing into one pack, arranged so the nearest rule would give the wrong gun.
4. Regression: existing `tools/shottag` and `tools/explosives` tests; stock and DRLA E1M1.

## Design (engine, `UZDoom/src/dd_shotsource.cpp`)

- The "parent" of a spawn is the actor whose state action / PostBeginPlay / death is running. The engine already
  tracks that as `DD_ActingActor` (`dd_lootrng.h`, set in `FState::CallAction`). For spawns outside an action (a ZScript
  `Tick` override that spawns fragments or trails, a missile exploding while it moves), the actor whose `Tick` is running
  is the parent: a new one-line `DDTickScope` in `DThinker::CallTick`. Ticks never nest, so an acting actor, when set,
  is always the innermost.
- The new actor stores the parent's *spawn serial* (`ddSpawnedBy`), not a pointer. A pointer would need GC marking and
  goes null once the parent is destroyed, but a rocket's fragments spawn in its death frame and get their spawn event
  a tic later, after the rocket may be gone. Serials are handed out lazily (only to actors that spawn something) from a
  counter that does not repeat in a run. Not saved: the mod reads the field only in the tic an actor is born.
- Recorded only in a bridge session (`DD_BridgeHasSession()`), so stock Doom never writes the fields.
- ZScript: `Actor.DD_SpawnedBy()` and `Actor.DD_SpawnSerial()` (both clearscope, read-only).
- Hooks in stock files, each one marked `[Doomerfall]` line: `actor.h` (two fields), `p_mobj.cpp` (one call in
  `ConstructActor` + include), `dthinker.cpp` (one scope line + include), `CMakeLists.txt`, `actor.zs` (two natives).

## Design (mod, `DoomerfallShots.zs`)

`Classify` first asks `DD_SpawnedBy()`:
- spawned by the player while the gun fires, and a projectile: the held gun's shot (`by fired`);
- spawned by a tagged shot (alive, or destroyed this tic: the detached tag keeps `fromSerial`): copy its tag (`by child`);
- otherwise (a helper actor, a dying monster, a script): the old nearest rule decides (`by near`), unchanged.
The tag log line now ends `by fired|child|near` so tests can tell which path was used.

## Findings / known gaps

- First harness run looked like a hook bug (GunSrcBlastA tagged gun B). It was the harness: `GunSrcFragB` inherited
  `Spawn: ... Goto Death`, and a Goto binds to the defining class's label, so B's fragment spawned A's blast. The tag
  (gun B, by child) was right. Fixed by giving GunSrcFragB its own Spawn state.
- Fallback still exists: when the spawner is not the player and not a tagged shot (e.g. a gun's non-projectile helper
  actor that itself spawns a projectile, or a dying monster's death spawn whose target is the player), the old nearest
  rule decides, as before. No such case showed up in the DRLA pair (0 of 161 tags used it); other DRLA guns may differ.
- `ddSpawnedBy` is not saved. A child spawned in the exact tic a save is made, but not yet given its spawn event, falls
  back to the nearest rule after loading. Rare, and the result is never worse than before.
- A fired projectile spawned by the player is now tagged without the old "within 64 units of the player" test, because
  the engine says the player's own action made it.
- No demo folder: nothing a person can see or play changed (only which gun gets credit inside perk code).

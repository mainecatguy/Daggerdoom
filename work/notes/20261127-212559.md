# Exact "which gun fired this" engine hook (2026-11-27, run 212559)

Goal: things a shot spawns took the weapon tag of the nearest tagged thing within 128 units, so mixed-gun fights could
credit the wrong gun. Add a small engine hook that passes the firing weapon to everything a shot spawns.

## Did the Explosives work already add a hook?

No. `DoomerfallExplosives.zs` reads the shared shot tag (`DoomerfallShots.zs`), which used only the nearest-parent rule
(`ChildReach = 128`). No engine code tracked spawn parents. So this run adds the hook and extends `DoomerfallShots.zs`
(which Explosives, Shotguns, Automatics, Energy and skill XP already read), rather than anything Explosives-specific.

## Plan

1. Engine: when an actor is spawned, record which actor spawned it.
2. Mod: `DoomerfallShots.Classify` uses that exact parent first; the nearest rule stays only as a fallback.
3. Test: two guns firing into one pack, arranged so the nearest rule would give the wrong gun.
4. Regression: existing `tools/shottag` and `tools/explosives` tests; stock and DRLA E1M1.

## Design (engine, `UZDoom/src/dd_shotsource.cpp`)

- The "parent" of a spawn is the actor whose state action / PostBeginPlay / death is running. The engine already
  tracks that as `DD_ActingActor` (`dd_lootrng.h`, set in `FState::CallAction`). For spawns outside an action (a ZScript
  `Tick` override that spawns fragments or trails, a missile exploding while it moves), the actor whose `Tick` is running
  is the parent: a new one-line `DDTickScope` in `DThinker::CallTick`. Ticks never nest, so an acting actor, when set,
  is always the innermost.
- The new actor stores the parent's *spawn serial* (`ddSpawnedBy`), not a pointer. A pointer would need GC marking and
  goes null once the parent is destroyed, but a rocket's fragments spawn in its death frame and get their spawn event
  a tic later, after the rocket may be gone. Serials are handed out lazily (to actors that spawn something, or when the
  mod asks for one with `DD_SpawnSerial()`) from a counter that does not repeat in a run. Not saved: the mod reads the field only in the tic an actor is born.
- Recorded only in a bridge session (`DD_BridgeHasSession()`), so stock Doom never writes the fields.
- ZScript: `Actor.DD_SpawnedBy()` (clearscope) and `Actor.DD_SpawnSerial()` (play; hands out a serial on first ask).
- Hooks in stock files, each one marked `[Doomerfall]` line: `actor.h` (two fields), `p_mobj.cpp` (one call in
  `ConstructActor` + include), `dthinker.cpp` (one scope line + include), `CMakeLists.txt`, `actor.zs` (two natives).

## Design (mod, `DoomerfallShots.zs`), after the verifier's first rejection

`Classify` order:
1. **Spawned by a tagged shot or a carrier** (looked up by spawn serial in 256 buckets; ZScript 3.3 has no `Map`; live
   tags and tags detached from shots destroyed this tic): copy its tag (`by child` / `by carried`), **whatever the new
   actor's `target` is**. This covers an actor a blast spawns without `SXF_TRANSFERPOINTERS` (its target is the blast).
   The shooter comes from the parent tag. A puff spawned this way stays a carrier.
2. **Spawned by the player's own action** (the player found by serial, since a puff has no target unless
   PUFFGETSOWNER): while the gun fires, a projectile is the held gun's shot (`fired`, gen 0); a puff or any other
   actor is a **carrier** of the held gun. A helper carrier is gen -1, so what it fires is gen 0 with fireTic now,
   the same as a shot fired directly. With the gun not firing: untagged.
3. **Anything else** (spawned by a monster, a barrel, a script, or no known spawner) whose target is the player: the
   old nearest rule (`near`), unchanged.

A **carrier** is a `DoomerfallShotTag` with `carrier = true`. `Find`, `Tag` and `Exploding` ignore it, and the
nearest rule never uses it as a parent, so damage through a puff or helper is credited exactly as before (a puff:
the held gun). It only passes the gun on to what the puff or helper spawns. Items, monsters and players are never
tagged.

**Behaviour change, on purpose (verifier item 4):** something the player's own action spawns is never a nearby
shot's child any more. Before, a non-projectile helper spawned by the player near a tagged shot copied that shot's
tag, and a player-spawned projectile with the gun ready copied a nearby tag. That guess *is* the mixed-gun bug: in the
DRLA test, `RLRocketLauncherRecoil` (spawned by the player firing the rocket launcher) got the cluster launcher's
tag through it. Now, with the gun firing, those helpers carry the held gun (not credited for their own damage, which
is how an untagged helper was treated before; their spawns get the held gun). With the gun not firing they are no
gun's: untagged.

The tag log line ends `by fired|child|carried|near` (plus ` carrier`), so tests can tell which path was used.

    engine's spawn chain back to the first ancestor the player's own action spawned, which gives the gun held at that

  - **Case C+D (intermediaries):** gun C's bullet puff (carrier) spawns the fragment family (4 real tags, gen 1-4);

  - Real DRLA pair RLClusterBombLauncher + RLRocketLauncher: every chained spawn carries its own gun, including

## Findings / known gaps

- Doom's damage *source* is unchanged: an actor spawned by a puff or helper without SXF_TRANSFERPOINTERS names the
  puff or helper as its source, not the player. Its tag is right, but perk hooks that start from
  `e.DamageSource == player` will not see those hits. Changing who Doom names as the damage source would change combat
  behaviour, so it was left alone. In the stock families, every blast and fragment the player's bombs spawn still has
  the player as its source.
- A puff and a player-spawned helper get a real `DoomerfallShotTag` (carrier) item, so in bridge sessions there is one
  extra inventory actor per puff while firing. Hitscan-heavy guns (DRLA miniguns, shotgun pellets) make many puffs.
  This is a possible performance cost for the reviewer to weigh. The shotguns and automatics tests ran clean.
- `ddSpawnedBy` is not saved. A child spawned in the exact tic of a save, before its spawn event, falls back to the
  old rules after loading. Rare, and never worse than before.
- An actor spawned by an untagged non-player (a monster, a barrel) or by nobody the engine knows still uses the old
  nearest rule if its target is the player, as before. Nothing exact exists to carry there.
- First-pass harness bugs (fixed): a subclass's inherited `Goto Death` binds to the parent's label. A `Rocket`-based
  bomb spawns the shared `RocketSmokeTrail`. A puff has no target unless PUFFGETSOWNER, so the mod now finds the
  spawning player by serial. ZScript 3.3 has no `Map`, hence the buckets.
- No demo folder: nothing a person can see or play changed (only which gun gets credit inside perk code).

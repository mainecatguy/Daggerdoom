# Dungeon support: "not supported yet" in every dungeon but Privateer's Hold (run 20261126-235852)

## What broke, and since when

Nothing broke: dungeons other than Privateer's Hold were never supported in the play build.

- The message is `This dungeon is not available yet.` (`UZDoom/src/playsim/dd_treadmill.cpp`, `TickTownDoors`). It
  appears when a town's dungeon door names a dungeon map id that has no loaded `DDDUNGN` lump.
- `DDDUNGN` lumps come only from packages built ahead of time. `scripts/play/install.py` builds exactly one dungeon
  (`DUNGEON = "Privateer's Hold"`) and loads `privateershold.wad`, `_mesh.pk3`, `_doors.pk3`.
- Towns and building interiors convert at runtime through the town cache (`dd_towncache.cpp`, converter `--group`),
  but that path never had a dungeon case.
- The message came in with `3abf92dc` ("Add door transitions to generated interiors and dungeons"). From that commit
  on, every dungeon door except Privateer's Hold showed it. The owner's guess was right: dungeon generation left every
  other dungeon unsupported, crypts included, and every dungeon type equally.

Also, two dungeon packages could never be loaded together: each `_doors.pk3` carried `action_objects.zs` (duplicate
classes) and used map name `MAP01`.

## Plan

Make dungeons convert at runtime into the same disk cache as towns and interiors:

1. Shared package (`--runtime-assets`, `ddruntime.pk3`) gains everything that must exist at engine startup for any
   dungeon: dungeon billboard textures, animated mesh texture frames used by dungeons, the door and action scripts and
   handlers, and every door and moving action model in every dungeon, as classes named by model (not by slot).
2. Converter `--group <30000000 + location id>` converts one dungeon into a `.ddt` cache file: the map (named like an
   interior, `DDS` + base 36, so the engine's runtime map hooks already accept it), its mesh, and its door, action,
   flat, light, and exit lumps. Door and action visuals are named by model, so they match the shared package.
3. Engine: a dungeon door with no prebuilt dungeon requests the cache group, shows "Opening...", and enters when it is
   ready. Door and action scripts read their lumps from the current runtime entry first.
4. Prebuilt Privateer's Hold keeps working as before.

## What was built

- Converter (`tools/dungeon_converter/RuntimeDungeon.cs`): `--group <30000000 + location id>` converts one dungeon
  into `T<group>.ddt` (lumps `MAPWAD` with `DFPOINTS` inside, `DFMESH`, `DDDUNGN`, `DFDOORS`, `DFACTION`, `DFDFLATS`,
  `DFDLIGHT`; cache names hold 8 characters). It runs the existing map step and mesh step as child processes with
  `--map-name DDSxxxxx --catalog-names`, because the converter keeps state in statics. `--list-dungeon-types` lists
  every dungeon with its type.
- `--runtime-assets` now also writes the dungeon catalog into `ddruntime.pk3`: 130 door models, 146 moving action
  models (classes `DFDoorVisual_<model>`, `DFActionVisual_<model>`, named by model id, flip, and the archives the texture
  table swapped in), 336 dungeon billboards (126 action billboard classes `DFActionFlat_aNNNrNN`), 4 animated model
  textures, `action_objects.zs`, the door and action event handlers, and a `DDDUNGN` map template with
  `UsePlayerStartZ`. Measured over all 4,232 dungeons, in 32 s for the whole package.
- `--runtime-dungeon` packages (Privateer's Hold in the play build) no longer carry `action_objects.zs` or the handler
  `MAPINFO`, since `ddruntime.pk3` has them; otherwise the two would collide.
- Engine (`dd_treadmill.cpp`): with the town cache on, a dungeon door with no prebuilt dungeon requests its cache group,
  prints "Opening..." and enters when ready, like a building door; dungeon doors within 768 units are converted ahead
  of time; New Game and plain load into such a dungeon wait for it. The message stays only for runs without the town
  cache. A prebuilt dungeon with the same map id still wins, so Privateer's Hold is unchanged.
- Scripts: `door_objects.zs` and `action_objects.zs` read their lumps through `DFDungeonData`, which takes them from
  the runtime dungeon's cache file (new natives `DD_InRuntimeDungeon`, `DD_RuntimeDungeonLump`) and otherwise from the
  packages as before. Door and action visuals accept a class name token (`_m55003f_121`) in place of the slot number.

## Findings / log

- Runtime conversion of one dungeon of each of the 19 types (`runtime_dungeon_check.py --per-type 1`, smallest of each
  type): all produce a cache file with the map and an exit; 7 to 11 s each, 20 s for Mantellan Crux. Mantellan Crux
  (HarpyNest, main quest) has no exit door, as in Daggerfall, where it is reached by teleport; it converts but the check
  flags it for having no exit. 18/19 pass, the 19th is that expected case.
- First try packed `DFACTIONS` and `DFDLIGHTS` under their 9-character names, which overran the cache file's 8-byte
  name field and corrupted the file. Fixed by truncating to 8 characters on both sides.
- Conversion time (7 to 11 s) is the wait at a dungeon door that was not prefetched. Prefetching starts within 768
  units of the door; one converter runs at a time, so a nearby interior can delay it.

- A first paired run of a runtime crypt failed: the engine writes the converter's own output to `work\convert.log`,
  and the dungeon step log used the same name (IOException). Renamed to `steps.log`.

## Known gaps

- The first visit to a dungeon that was not prefetched waits 7 to 11 s at "Opening..."; the game stays responsive.
- The mesh step still writes its texture PNGs into the work folder, which runtime dungeons do not use; about a second
  of each conversion could be saved.
- `install.py` needs no change: it already packages the converter and cache folder, and `--runtime-assets` now holds
  the catalog. Running it rebuilds `ddruntime.pk3` (now about 63 s with the catalog, was about 32 s).
- History keys are unchanged (`DungeonSlot`, place `D<map id>`), so a later prebuilt or runtime conversion of the same
  dungeon keeps its record. The space id of a runtime dungeon is its cache group, not `17000000 + load order`.

# Running skill from running in Doom (20261127-175327)

Goal: the player gains Running uses while running in Doom, at 1.5x Daggerfall Unity's rate; none standing or walking.

## Plan

1. Doom detects running by Daggerfall's rule and reports running time over the bridge (new event kind).
2. Daggerfall turns running time into Running uses with its own rate x1.5 and calls its own `TallySkill`.
3. Test component `-dfrunningtest` logs every Running tally (and with `prime`, shows the skill rising); a paired test
   (`tools/running/running.py`) runs stand / walk / run / run-key-without-moving phases and measures the rate.
4. Manual entry, demo, E1M1 checks.

## Daggerfall's rule, read from the code

- `PlayerEntity.FixedUpdate`: on each classic update, `if (playerMotor.IsRunning && !playerMotor.IsRiding)` count; every
  4th counted classic update is one `TallySkill(Running, 1)`.
- `PlayerSpeedChanger.ApplyInputSpeedAdjustment`: `isRunning = CanRun() && runningMode` while grounded; in the air the
  flag keeps its value. `runningMode` is the run key (held, or toggled by the autorun/Toggle Run options).
- Note: in Daggerfall Unity itself `isRunning` does **not** require moving — holding Run while standing still tallies.
  The owner's card says "running key held and moving", which also matches the done criteria (none while standing), so
  Doom requires movement. Reported as a mapping choice, not a change to Daggerfall.
- Classic update timing (`GameManager.FixedUpdate`): the timer adds `Time.deltaTime` each FixedUpdate and resets to 0 at
  `>= 0.0625`. With the project's fixed step 0.02 s (`ProjectSettings/TimeManager.asset`) that is 4 steps = **0.08 s**,
  not 0.0625. So Daggerfall Unity tallies one Running use per 0.32 s (3.125/s). x1.5 = one per 0.2133 s (4.69/s), i.e.
  one use per 112/15 = 7.467 Doom tics. `DoomerfallRunning.DaggerfallSecondsPerUse` computes this from
  `Time.fixedDeltaTime`, so it follows the project setting.

## Mapping to Doom (UZDoom/src/dd_running.cpp)

Running in Doom = all of:
- `BT_RUN` in the player's executed command. Doom sets it when the Run key is held, inverted by Always Run (`cl_run`) —
  the same as Daggerfall's run key plus its autorun/toggle-run options.
- a movement key pressed (`forwardmove` or `sidemove` non-zero), and
- the body actually travelling (horizontal speed >= 1 map unit per tic; walking is several times that). Running into a
  wall does not count.
- the player alive, in a level, on a generated Daggerfall map (`world_context != DFB_WORLD_NONE`), with a bridge session.
- Riding: checked on the Daggerfall side (`PlayerMotor.IsRiding`), as Daggerfall does.
- Airborne: counts if the keys are held and the body moves (Daggerfall keeps the running flag through a jump).

Doom sends `DFB_KIND_RUN_TIME` (169, payload `dfb_run_time { tics }`) each 35 running tics and when running stops.
Daggerfall (`DoomerfallRunning.cs`) accumulates fractional uses and calls `PlayerEntity.TallySkill(Running, n)`, so
advancement, skill caps and the reflexes scaling stay Daggerfall's. The rate rule lives on the Daggerfall side (Daggerfall
owns rules); Doom only reports time.

Player.log has one `NullReferenceException` in `DaggerfallUI.SetupSingleton` at startup. It is pre-existing (the same

Demo: `D:\dev\DoomDaggerfall-loop\review\running\play.bat` (runs with `-dfrunningtest ... prime`, so about 9 seconds of
running shows a rise; uses are written to `play\running.log`, nothing on screen).

## Known gaps

- Daggerfall Unity itself tallies Running while the run key is held even when standing still; we require movement, as
  the card asks. Swimming is not distinguished (Doom has no Daggerfall swimming yet).
- Choosing Horse or Cart in the transport menu stops Running uses (Daggerfall's rule), even though Doom still moves you
  on foot. If riding later changes Doom movement, this stays right.
- The skill's effect on speed is untouched (no perk or speed formula, per the card).

# New start 3: save when a new game starts (20261124-111724)

Builds on card 2 (`work/notes/20261124-105730.md`): New Game puts both games at Daggerfall's Enter marker in
Privateer's Hold.

## Plan
1. Find the synchronized save path and the end of the New Game flow. Done.
2. After New Game, once Daggerfall's opening messages are done, make one normal bundled save through that path,
   under a file name that cannot be one of the player's saves. Done.
3. Prove it with a paired New Game through the launcher (`--minimized`): the save is written, the player dies, the death
   screen's Load Last Save loads it, and both games are back at the start point with the same HP. Done.
4. Regression: the old save/load cycle, death with the player's own save, and a second character in one session. Done.

## Findings
- Synchronized saves: `SaveQueue` / `SaveStart` / `SaveRun` in `UZDoom/src/dd_bridge.cpp`. Doom freezes, asks Daggerfall
  for its save (`DFB_KIND_SAVE_REQUEST`), and bundles it into the `.zds` through `G_DoSaveGame`. The menu, autosaves
  and quicksaves all go through it, so the new save does too. No new format.
- New Game ends at `HandleNewGameGo` (Daggerfall's `KIND_NEWGAME_GO`, sent after `FinishNewCharacterStart` starts the
  clock and the `_TUTOR__` and `_BRISIEN` quests). That is also where the campaign id for the new character is made.
- Daggerfall's opening message: `_TUTOR__` opens a `DaggerfallMessageBox` about 0.6 s after Go. Daggerfall waits
  0.25 s and then asks Doom to show it (`DFB_KIND_UI_ASK`, repeated every 1 s if Doom cannot open it). Doom shows it as
  a menu, which pauses Doom.
- Death screen Load Last Save (`dd_death_loadlast`) loads `NewestBundle`: the newest `.zds` that passes the bundle checks
  and belongs to the current campaign. So the new game save is the target until the player saves again.
- Doom's load menu lists every `.zds` in the save folder (`FSavegameManager::ReadSaveStrings`), and `G_DoSaveGame`
  adds new saves to the open list, as for autosaves.

## What changed (UZDoom/src/dd_bridge.cpp only)
- `PumpNewGameSave`, started by `HandleNewGameGo`. It waits until both games have been quiet for 2 s: map loaded,
  `SaveReady()` (no Daggerfall window open, no door handoff, Daggerfall in play), no save or autosave pending, no Doom
  menu, not paused. Then it queues one save through `SaveQueue` (as an autosave, so quicksave never picks this slot).
- **File:** `<savedir>/<campaign id>-newgame.zds`, for example `0003e4112f0a63fc-newgame.zds`. **Description in the
  load menu:** `New game <date and time>`. The campaign id is new for every New Game, so the name never matches a menu
  save (`saveNN`), an autosave (`<campaign>-autoNN`) or a quicksave. If the file already exists, it is left alone and no
  save is made.
- If the save fails (Daggerfall refuses, Doom can't write the file), it tries again after another quiet 2 s, up to
  3 times. It is dropped if the player dies first, a load starts, the game goes back to the title, or 10 minutes pass
  without a quiet moment. Each case is logged as `new game save: ...` in the bridge log.
- Test only: `-dfloadtest newgame:<unused>` waits for the new game save, moves the player 48 units, kills them through
  Daggerfall's HP, picks Load Last Save on the death screen, and passes only if the new game save was the file loaded and
  position (dungeon space) and HP in both games match the save. The other load test modes now wait for the new game
  save to finish before making their own, so the two do not collide.

## Failed approaches / notes
- First version recorded the save position with `DDTreadmill_PlayerWorld`, which reads 0,0 inside a dungeon, so the
  position check passed trivially. It now uses `DDTreadmill_PlayerSpace` (dungeon coordinates) and moves the player
  before the death, so the check means something.
- The 2 s quiet time is an engineering choice: longer than Daggerfall's 0.25 s ask and 1 s re-ask, short enough that a
  player can hardly die first. A player who dies within about 3 s of arriving has no start save (logged as dropped).

# Paired New Game driver and message boxes (20261127-183307)

Goal: Q&A item 66. Find out whether the paired New Game test driver still stalls at Daggerfall's message boxes. If it
does, find out whether players are affected (keyboard yes/no in Daggerfall popups shown in Doom), and fix that, then the
driver.

## Result: it no longer happens, so this run reports and stops

**The unchanged driver got through every New Game message box in all 13 runs that reached character creation. Keyboard
yes/no works in those popups.** Nothing is changed in the repository except this note.

An earlier version of this run also changed `tools/new_game/run_new_game.py` and added a test tool. Both are reverted,
because the goal says to report and stop. They are now suggestions for the owner (below).

Build used: `review\batch9-stage`, copied to `D:\dev\DoomDaggerfall-loop\review\newgame-keys` so other lanes' staging
was not touched (integration at 399b9c24, the Daggerfall and UZDoom builds staged at 18:26 today). All runs used the
DRLA set unless marked stock, and every run went through `quiet_run.py` with `--inside-quiet`.

**Evidence that the stall no longer happens:** 13 runs reached character creation and logged their boxes (A1, B2, C5,

After those runs I made 5 more launches (driver x3, popup check x2) with a driver change that is now reverted. All 5
passed, but they are not counted above.

## Keyboard yes/no for players

The popup check (D2, F) answered each box with one key, posted to Doom's window the way a player's keys arrive:

- "Is this your race?" Yes/No: **N** alone went back to the race list.
- The same box again: **Y** alone went on to gender.
- The class confirmation Yes/No: **Y** alone went on to the bio.
- The reputation box after the bio (no buttons): **Enter** alone went on to the name screen. Y does nothing there,
  the same as in Daggerfall Unity, because that box has no Yes button.

Escape does nothing on boxes that have buttons. That is Daggerfall Unity's own rule (`AddButton` sets
`AllowCancel = false`), already recorded by `tools/new_game/run_escape.py`. That accounts for the Escape half of the
earlier "travel box ignores N and Escape" report. N on the travel box uses the same `DaggerfallMessageBox` Yes/No
button hotkeys and the same `DoomerfallInput` route that worked above (`DaggerfallTravelMapWindow.cs:1747-1752`). I did
not drive the travel box itself.

The check script is not committed. A copy is in this run's scratchpad and was removed from the repository.

## Why it stalled before (best guess, not proven)

All the earlier stalls were between about 04:30 and 06:15 on 2026-11-27. In that window many lanes were building and
testing at once, and an older Daggerfall build stalled the same way. It passed at about 04:00, and it passes now. Even
with all 16 cores busy, the boxes kept closing. Two things may explain the old reports:

- **The 50 s limit is tight.** A New Game alone takes about 36-40 s. With other lanes running it took 46 s or more, and
  under full load it ran out of time (E, F). A timed-out run prints the last window it saw, so it can name a box
  that had already closed late.
- **Clicks worked when keys did not.** The old reports said this. Nothing tonight showed it. The cause is unknown.

## Suggestions for the owner (not done)

- Raise `run_new_game.py`'s default `TIMEOUT` from 50 s. Runs on a busy machine need more than 50 s. The two-character
  modes (`again`, `restart`, 85 s) should then stay above the new one-character limit.
- Have the driver stop with a clear "message box ignored Y and Enter" result after about 5 s on one box, instead of
  waiting for the time limit. Then a real return of the key problem could be told apart from a slow machine.
- Keep a single-key popup check (N, Y, and Enter on the info box) as a committed tool, if wanted.

## Other findings

- **The driver's stock mode times out on a current staged folder.** The driver always loads `doomerfall-drla.pk3`
  when the folder has it, and that file needs DRLA, so Doom stops before writing a log (B, 2 of 2). This is unrelated
  to message boxes.
- **No output under full load.** During E, one driver run and two popup runs printed nothing. The driver run's log
  shows every box closed. This is probably the stress processes and quiet_run competing for the machine, because the
  same command passed as soon as the stress ended.

No game, engine, mod, or tool changes, so the E1M1 check, builds, and demo do not apply.

# Autosave waits until the level is initialized (run 20261126-142733)

Goal: the dungeon-entry autosave (`PumpArrival`, `UZDoom/src/dd_bridge.cpp`) was taken after the new map's first tic,
before Daggerfall's door facts armed the locks, so loading it left every door unlocked. Build a general "wait until
level setup is done" with a timeout, find other systems with the same problem, keep stock autosaves working.

## Verdict on the approach

The owner's idea (systems report when they are ready, with a timeout) is the right call, and I built it. Alternatives I
considered and rejected:

- Re-ask Daggerfall for the door facts after every load. Wrong for doors: Doom owns the live lock, so a save must hold
  it (a lever-relocked door, a magic lock), and re-arming on load would overwrite Doom's state.
- Delay the arrival autosave by a fixed time. Either too short (Daggerfall loading a dungeon) or a needless hitch.

## What I built

`UZDoom/src/dd_setup.cpp` (new, ~90 lines), the level setup gate. Bridge sessions only; nothing runs without `-dfbridge`.

- `DD_SetupLevelLoaded(fromSave)`: called from `G_DoLoadLevel` right after the `WorldLoaded` handlers (one line in
  `g_level.cpp`, through `DD_BridgeLevelLoaded`). It clears the gate and queues the network event `dd_setup_settled`.
  Network events run in order, so when that event runs, every system that asked Daggerfall from `WorldLoaded` (the door
  handler sends `dfdoor_facts` there) has already registered. A map restored from a save starts with the gate open.
- `DD_SetupWait(name)` / `DD_SetupDone(name)`: a system registers when it asks and reports when its answer is applied.
- `DD_SetupReady(now)`: settled and nobody waiting, or 5 s since the map loaded (then it logs who it gave up on and
  saves the map as it is: a missing answer can never block saving).

Users of the gate (`dd_bridge.cpp`):

- `PumpArrival`: after the handoff's first tic, waits for `DD_SetupReady`. The screen keeps the frame from before the
  change while it waits (existing `DD_BridgeHoldFrame`, capped at 12 s; the gate caps the wait at 5 s).
- `DD_BridgeAutosaveHold` and the held-autosave loop in `PumpSave`: a non-stitched autosave (stock `DAutosaver` path)
  on a Daggerfall map is held until the gate is ready too.

Doors (`dd_doors.cpp`, `DoomerfallDoors.cs`, `bridge/doomerfall_bridge.h`):

- Forwarding `dfdoor_facts` registers `doors`.
- Daggerfall's `DFB_DOOR_ARM` now carries the number of `DFB_DOOR_FACT` events that follow in `state` (header comment
  updated, bindings regenerated; no new constant). Doom queues `dfdoor_ready` to the mod after the arm and its last
  fact; when that event runs, the mod has applied them (same queue, in order), and `DD_SetupDone("doors")` is called.
  Without the count Doom could not tell "no more facts" from "facts still in flight".

## Other systems that finish a map after Daggerfall answers

Searched every `WorldLoaded` that sends a network event (only `door_objects.zs` does) and every bridge system that asks
Daggerfall on a context change (`DD_*Frame` in `dd_items/monsters/npcs/townsfolk/guards.cpp`).

| System | Asks Daggerfall | Problem for a save made before the answer? | Covered |
|---|---|---|---|
| Dungeon doors (`dd_doors.cpp`) | on a fresh dungeon map | Yes: a load never asks again, because Doom owns the live lock | Gated |
| World items / treasure (`dd_items.cpp`) | on every context change | No: `DD_ItemsResync` asks again after every load (`HandleLoadResume`) | Listed |
| Dungeon monster list (`dd_monsters.cpp`) | entering a dungeon | No: `DD_MonstersResync`; "SpawnEncounters never doubles one that is present" | Listed |
| Interior NPCs (`dd_npcs.cpp`) | entering an interior | No: `DD_NpcsResync` | Listed |
| Townsfolk (`dd_townsfolk.cpp`) | entering an exterior | No: `DD_TownsfolkResync` | Listed |
| Guards (`dd_guards.cpp`) | no: spawned on Daggerfall's crime event | Not a setup step | n/a |

These four could join the gate with two calls each if a reason appears (for example, if one stops re-asking on load).
I left them out because they already heal on load and waiting on them would make the held frame longer.

### Timing

The dungeon arrival autosave now lands ~220-240 ms after the map loads instead of ~6-20 ms. That is not the gate
waiting: the doors are ready 9-50 ms after loading, and a temporary log (removed) showed the main loop does not run
again for ~200 ms after that (one long blocking frame, likely the dungeon's first spawns). Before, the save came before
that frame; now it comes after it. The held frame covers both, so the player sees one hitch, as before.

### Failed approaches

- `stock_autosave.py` first used `+wait 70;changemap E1M2`: the level never changed on the private desktop (with or
  without `wi_autoadvance`). A small ZScript handler calling `level.ChangeLevel(..., CHANGELEVEL_NOINTERMISSION)` works.
- The entry check first ran on the starting town map before the load test loaded the save; it now runs only inside.

## Known gaps

- The timeout path (Daggerfall never answers) was not run live. By code: after 5 s `DD_SetupReady` returns true and logs
  `setup: gave up waiting ...`, the arrival autosave is taken (or dropped by the existing checks), and a held autosave
  runs. `DD_DoorsFrame` dropping queued answers on a space change also ends in this timeout.
- Manual saves (menu, quicksave) are not gated. During the arrival the screen is held, so a save in that window is
  unlikely; gating them is two lines in `DD_BridgeSaveBegin` if wanted.
- While the arrival autosave waits, Doom keeps ticking behind the held frame (as it did for the handoff wait). Normally
  tens of ms; at worst the 5 s timeout.

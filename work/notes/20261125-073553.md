## 1. Lockpick item (`daggerfall-unity-master/Assets/Scripts/Doomerfall/DoomerfallLockpick.cs`)

- `DoomerfallLockpickItem`: template 9300, "Lockpick", 25 gold, 0.1 kg, stackable. It carries its own name, weight and
  value, because Daggerfall rebuilds its template list after the bridge registers custom templates (the same
  workaround as `DoomerfallAmmoItem`). It saves under its class name.
- Icon: the owner's `mods/doomerfall/src/sprites/LPCKA0.png` is copied byte for byte to
  `Assets/Resources/Doomerfall/LPCKA0.png.bytes`. It is decoded at runtime with point filtering and stays readable,
  because Daggerfall's UI may read icon pixels. Nothing resamples the pixels. The copy is the owner's own art, not game
  data, so committing it is fine. If the art changes, both files must be updated.
- Registered only in a bridge session (`DoomerfallBridge.cs`, next to `DoomerfallAmmo.Register`). Every hook does
  nothing in a plain Daggerfall Unity game.
- Sources. The rules are the owner's; the numbers are my choice within them:
  - New character: 3 picks. A class with Lockpicking among its primary or major skills (the burglar types) gets 8.
    This uses `StartGameBehaviour.OnStartGame`, which fires after `AssignStartingEquipment`. It is skipped during a
    load and when the character already has picks. A classic-save import also fires `OnStartGame`, so an imported
    character with no picks gets the starting count.
  - General store 70% and pawn shop 80% per restock, scaled by shop quality as Doom ammo is (0.5 + quality/20, at most
    95%). Each stock is a stack of 5-15 (`DaggerfallLoot.StockShopShelf`, one line after the ammo hook).
  - Treasure and human enemies: at the end of `LootTables.GenerateRandomLoot`, an 8% chance of 1-3 picks for any
    loot table that carries gold. Human and treasure tables carry gold; animal tables (B, I) do not. The roll comes
    after all of Daggerfall's own rolls, so a seeded roll keeps the same earlier items. Rolls made later from the same
    seed do shift, but a fixed seed still gives the same results every time.
  - Thieves Guild: no sales (owner, 2026-11-25). The guild has no vendor and none will be added.
- `DoomerfallLockpick.Count` and `BreakOne` are ready for the door code.

## 2. Minigame (`mods/doomerfall/src/zscript/DoomerfallLockpick.zs`)

- Network event `dflp_start` (args: chance, token) starts an attempt. `dflp_cancel` cancels it. The result goes back as
  the network event `dflp_result:<token>:<hit|miss|cancel>`, the same way `dfa_take` reaches the engine. The engine
  does not listen for it yet.
- Drawing: a thin grey ring outline, empty inside, with one thick solid white arc. A gold chevron outside the ring
  points in and turns clockwise. The ring's radius is screen height / 14, at least 24 pixels. Drawn with
  `Screen.DrawThickLine` in `RenderOverlay`. The chevron is interpolated within the tic.
- Input: a `Thinker` at `STAT_USER` ticks before players, reads Fire and Use, and removes them from the player's
  command while an attempt runs. So the gun never fires and Use never reaches a door. Only new presses count, so a
  button already held when the attempt starts is ignored.
- Cancel rules (the owner's): taking damage (health drops or the pain counter rises), moving more than 64 units from
  the start point, Use pressed again, or death. A cancel costs nothing, and the engine forwards it as `cancel`.
- Difficulty curve (my choice, for play-testing). It uses Daggerfall's own chance, which is already clamped to 5-95:
  t = (chance − 5) / 90, the white arc is 14 + 56t degrees, and the chevron turns at 230 − 105t degrees per second.

  | Daggerfall chance | arc | speed | time over the arc |
  |---|---|---|---|
  | 5% (hopeless) | 14° | 230°/s | 61 ms, about 2 tics |
  | 50% | 42° | 178°/s | 237 ms |
  | 95% | 70° | 125°/s | 560 ms |

  At 5% the chevron sits on the arc for at least two tic positions, so a hit is always possible but needs precise
  timing.
- The arc's centre is random, 90-270° away from the chevron's start, so a hit is never free on the first tic.
- Test: `python tools/lockpick/run_minigame.py --out <dir> [--drla]` runs E1M1 through `quiet_run` with
  `tools/lockpick/harness`. The harness presses buttons from its own thinker and checks: a hit, a miss, a damage
  cancel, a move cancel, a Use cancel, and a hit at 5%. Each case also checks that the Clip count did not change, so
  the gun did not fire.
  - Stock: `LPTEST done 6/6`, `RESULT stock PASS` (Clip 50→50 in every case).
  - DRLA set: `LPTEST done 6/6`, `RESULT drla PASS` (60→60). Its only script errors are DRLA's own, the ones earlier
    notes record (translation, menudef).
  - The demo's UZDoom copy with DRLA: 6/6, but that run started with a gun that does not use Clip (0→0). This is the
    random DRLAX starting gun reported earlier, so that run did not check firing.
- E1M1 behaves as before. The handler only acts on `dflp_start`, which nothing sends outside the test or the demo
  keys. Both E1M1 runs above load the mod with the new handler.

## 2b. Second session: door data and Daggerfall's lock authority

- **Converter** (`b8de497d`). Each ordinary dungeon door's `DFDOORS` line now ends with `startingLock loadId`, and
  each `DFACTIONS` `A` line ends with `loadId`. The lock uses the same table as `RDBLayout`. The LoadID is
  `block.Position + obj.Position`, exactly as `RDBLayout` computes it for the `DaggerfallActionDoor`.
  `door_objects.zs` (`DFDoor.startingLock`, `loadId`) and `action_objects.zs` (`DFAction.loadId`) read the new
  fields when present. Older maps give 0, so cached maps keep working.
  - Checked by converting Privateer's Hold with `--export-mesh`, using a converter built to
    `D:\dev\DoomDaggerfall-build\conv-lockpick`. It has 58 doors, every line has 14 fields, and all 58 LoadIDs are
    unique. **One door starts locked (lock value 2, LoadID 29539363)**, which makes it a good target for the paired
    demo. Its 6 action records got LoadIDs as well (for example 29550096).
  - UZDoom (the `uzdoom\Release` build) loaded the reconverted wad and the mesh and door pk3s as MAP01 with no
    script errors.
  - Stale caches: towns and dungeons already in a player's cache keep the old lines until they are reconverted. They
    then read as lock 0 and LoadID 0, so the door code must treat LoadID 0 as "unknown, ask nothing". This is the
    known missing converter version check in the cache.
- **`DoomerfallLocks.cs`** (`87771cbd` plus the label helper). It finds the live `DaggerfallActionDoor` by LoadID in
  Daggerfall's hidden area (it indexes `FindObjectsOfType` and builds the index again on a miss). It also gives:
  - `StateOf`: unlocked, locked, or magic (lock value 20 or more).
  - `Chance`: Daggerfall's own interior formula.
  - `Label`: Daggerfall's own words, "Locked." (`lockedExteriorDoor`) and "This is a magically held lock..."
    (`magicLock`). A plain unlocked door is "Door".
  - `ApplyAttempt`: one Lockpicking tally per attempt. A hit sets `CurrentLockValue = 0`, a miss calls `BreakOne`,
    and `FailedSkillLevel` is not set, per the owner's retry rule.

  The DFU build passes. Nothing calls this class yet; the bridge messages are the next step.
- Other Daggerfall wording for later messages: "The lock clicks open." (`lockpickingSuccess`), "It does not unlock."
  (`lockpickingFailure`), and the difficulty lines `lockpickChance1-3` and the `lockpickChance` list, which
  `PlayerActivate.LookAtInteriorLock` uses.

## 2c. Third session: Doom-side lock gate on dungeon doors

- `door_objects.zs`: `DFDoor.lockState` is set only by Daggerfall, through the network event
  `dfdoor_lock:<loadId>:<state>[:open]`, where state is 0 (not locked), 1 (locked) or 2 (magically held). A closed
  door with a non-zero state does not move on Use. It sends `dfdoor_use:<loadId>:<state>` so the engine can forward
  the Use to Daggerfall, which picks the label and decides whether the minigame starts. `dfdoor_lock:<id>:0:open`
  (after a hit) opens it. Without these events every door behaves exactly as before. Both fields are saved with the
  door, since actors and handlers are serialized.
- Monsters: converted doors open only through the player's Use trace (`DFDoorBlocker.Used`). Monsters never open them,
  locked or not, so "monsters do not open locked doors" already holds for dungeon doors.
- Test: `tools/lockpick/doorgate` (load it after a converted dungeon's pk3s, `+dd_lockdoor <LoadID>`). On Privateer's
  Hold (wad from `conv-lockpick/out`, pk3s from `out5`, DOOM2.WAD) with the locked door 29539363 it printed
  `DGTEST done 5/5`. The door is found with starting lock 2. Use reaches it, it stays shut, and it reports
  `dfdoor_use:29539363:1`. Daggerfall's `:0:open` then opens it.
- Still missing for the dungeon path: engine C++ that relays `dfdoor_use`, `dflp_result` and `dfdoor_lock` between
  the mod and the bridge (new bridge kinds), plus the Daggerfall dispatcher that calls `DoomerfallLocks` and sends the
  locked-door list when a dungeon loads.

## 3. Doors: findings and plan for the next run

### Identity (checked in the code)

- Dungeon action doors: Daggerfall Unity gives each door `LoadID = blockData.Position + obj.Position`
  (`RDBLayout.cs:1193`, also used for saves by `SerializableActionDoor`). The converter already has the block and
  `FilePosition` for every action record (`ActionExport.cs:416`). It can compute the same LoadID from the block's file
  position in BLOCKS.BSA and export it as a new last field of the `A` line (after the trapdoor flag, field 33).
  Daggerfall then finds the live `DaggerfallActionDoor` by LoadID in the hidden dungeon. Its `CurrentLockValue`
  (0 = unlocked, at least 20 = magically held, `DaggerfallActionDoor.cs:71,91`) is the authority, and its unlocked state
  already persists through Daggerfall's save (`SerializableActionDoor.cs:75,97,116`).
- Interior doors are the same `DaggerfallActionDoor` component (built by `RMBLayout`). Their LoadID comes from the
  interior's layout and still needs checking.
- Exterior building doors: Daggerfall reads the building's lock from `buildingLockValue` in `PlayerActivate.cs:546`
  (exterior formula `skill − 5 × lock`). The building door already reaches Daggerfall by index for the look label
  (`DFB_INFO_BUILDING`, `dd_look.cpp:111`), so that request can grow a lock answer.

### Contract (proposed; it changes the bridge layout hash once)

1. Doom, on Use of a door: `DFB_KIND_DOOR_USE {kind (exterior/interior/dungeon), id (LoadID or building index),
   steal flag}`. Doom waits; the door does not move.
2. Daggerfall answers `DFB_KIND_DOOR_STATE {id, state: open | locked | magic, chance, picks}`, where chance is Daggerfall's
   own `CalculateInteriorLockpickingChance` / `CalculateExteriorLockpickingChance`. "open" lets Doom move the door.
   "locked" with picks > 0 starts `dflp_start chance token`. "locked" with no picks, and "magic", show Daggerfall's text.
3. Doom, on the minigame result: `DFB_KIND_LOCKPICK {id, hit|miss|cancel}`. Daggerfall then runs its own bookkeeping:
   `TallySkill(Lockpicking, 1)` per attempt, `BreakOne` on a miss, and `CurrentLockValue = 0` on a hit (for exteriors,
   the same last-attempt and guild tally code as `PlayerActivate`). It answers with a new `DOOR_STATE`. Cancels report
   nothing.
4. Lock state for the look label and monsters: when a dungeon or interior loads, Daggerfall sends the list of doors that
   are locked now (id, magic flag), and sends one update whenever that changes (pick, action types 16 and 17, the Open
   spell later). Doom uses that list for the label ("locked" or "magically held") and to keep monsters from opening those
   doors. It never decides that a door is unlocked by itself.
5. Action types 16 and 17 (`action_objects.zs:293`) should become requests that Daggerfall runs on the same door
   (`DaggerfallAction.cs:622,637`), followed by the update in step 4.

### Daggerfall's text

The `lockpickingSuccess` and `lockpickingFailure` keys, and the locked-door text `PlayerActivate.LookAtInteriorLock`
uses (it describes the lock's difficulty and says when a door is magically held), are what the label and messages
should reuse. I have not extracted the exact strings yet.

### A rule that differs from Daggerfall (the owner's decision wins)

Daggerfall refuses another attempt at the same skill level after a failure (`FailedSkillLevel`,
`DaggerfallActionDoor.cs:157`). The owner's rule is "may try again at once if they have picks left", so the door code
must not apply `FailedSkillLevel` when the minigame decides.

# Position sync

Branch `agent/engine-20261122-235129`. The hidden Daggerfall player now follows the Doom player through the exterior world over the bridge, and Daggerfall keeps the same area loaded.

## Transform

UZDoom publishes Daggerfall world units, so the 75% scale lives in one place (`ToWorld` in `dd_treadmill.cpp`).

| Value | Formula |
|---|---|
| World X | `(originTileX * 192 + 12288 + doomX) / 0.75` |
| World Z (north) | `(originTileY * 192 + 12288 + doomY) / 0.75` |
| Height | `(doomZ + 35240) / 0.75`. Published, but Daggerfall stands on its own terrain |
| Map pixel | `x = floor(worldX / 32768)`, `y = 499 - floor(worldZ / 32768)` |
| Unity yaw | `90 - doomAngle` |
| Unity scene delta | `world delta / 40` (`SceneMapRatio`) |

In a town map the origin is the town's world origin instead of the window's.

## What was built

- **Bridge (protocol 2).** The UZDoom state carries world position, yaw, context, map pixel, and an area sequence. A new `DFB_KIND_AREA` event is sent at once when the context or map pixel changes.
- **Context.** `NONE`, `EXTERIOR`, `INTERIOR`, `DUNGEON`. Only `EXTERIOR` is produced today. Daggerfall holds still on `INTERIOR` and `DUNGEON`. That switch in `DoomerfallPositionSync.Tick` is the place for the transition task.
- **Daggerfall (`DoomerfallPositionSync.cs`).** Applies position once per second and immediately on an area event. A jump of more than 2 map pixels uses Daggerfall's teleport. Shorter moves let normal streaming run.
- **Hidden player.** While Doom is on the exterior, Daggerfall's character controller, motor, mouse look, activation, and weapons are off, and enemy AI uses Daggerfall's existing `DisableAI`. All of it is restored when Doom leaves the Daggerfall world. There is no god mode, so poison and similar effects still run.
- **Random encounters** are held off with `PreventEnemySpawns` while synced, because Daggerfall would otherwise create enemies on its own. This also stops low-reputation guard spawns. Encounters are a shared contract for later.
- **`--nodraw`** on the launcher passes `-dfnodraw`. The main camera stays on with nothing to draw, so the 2D interface can keep rendering, and other cameras are turned off. Without the flag Daggerfall draws normally.
- **Test start.** `-dfsynctest <Daggerfall path>` enters the world directly and refuses to run outside a portable install.

## Measurements

Scripted route through the real launcher: wait for Daggerfall, stand 5 s, run east, run north, crossing 2 map pixel borders at 2,800 Daggerfall units/s, then leave to MAP01. Run with `tools/position_sync/run_sync.py`. **Both games were minimized and Daggerfall's vsync was off, so treat frame times as relative.**

| Measure | Drawing on | `--nodraw` |
|---|---:|---:|
| Daggerfall frame, median | 0.72 ms | 0.24 ms |
| Frames over 16 ms | 1 of about 24,700 | 1 of about 56,600 |
| Worst frame | 55.9 ms | 52.4 ms |
| New map pixel loaded after Doom entered it | 59.5 and 54.2 ms | 53.1 and 46.0 ms |
| Time in the wrong map pixel | 0.00 s of 21.5 s | 0.00 s of 21.5 s |
| Position error right after applying | at most 1.41 units | at most 1.41 units |
| Largest drift before an update | 2,875 units | 2,835 units |
| Managed memory | 273 to 283 MB | 255 to 282 MB |
| 3D camera test image | 66.9% non-black | 0.0% non-black |

- The drift is one second of running at test speed, as expected from a 1 Hz update.
- The first world load took 5.6 s in the first run and about 2.9 s in the two after it, **including a later run with drawing on**. That difference is a warm disk cache and not a drawing saving.
- The streaming cost that matters is the single worst frame, about 50 to 55 ms either way, so turning drawing off does not remove it. I did not isolate which frame it was or what it was doing.

## Not verified

- **The owner's registry key was not compared before and after,** because reading it needs approval. Isolation rests on the portable install and the patched product name (0 occurrences of the real name, 2 of the private one).
- **The negative control never landed an attack** (health stayed 100), so it proves the AI switch stops movement. Stopping attacks rests on `EnemyAttack` checking the same flag.
- **Town handoffs and `dd_tm_warp` were not run with the sync.** The teleport path was only exercised by Daggerfall's first jump to Doom's location.
- Yaw is applied, but its accuracy was not measured.
- `play.bat` itself was not launched, because it opens visible windows. The same launcher path ran minimized.
- Real focused performance was not measured.

## Failed approaches and corrections

- The first frame times were all 8.5 ms in both modes. The portable settings had vsync on, so they showed the display rate and not the cost.
- The percentile window keeps only the last 1,024 frames, which is under a second when uncapped and can miss a streaming hitch. Worst-frame and slow-frame counters now cover every frame.
- The test enemy appeared to move 42.9 units. A diagnostic showed its local position changed by exactly its parent's offset while its world position stayed put, so the check now uses world position.
- The first runner never saw the route finish, because `+logfile` was given a full file name and wrote to a different file.

## Housekeeping

Every Unity build rewrites `addressables_content_state.bin`. It is deliberately left out of these commits and still shows as modified.

## Human play-test list

1. Run `D:\dev\DoomDaggerfall-loop\review\position-sync\play.bat`. Walk across the terrain and confirm the Daggerfall window follows you to the same place, about once per second.
2. Compare both windows at a few spots, including near a town, for matching area and LODs.
3. Run `play.bat nodraw`. Daggerfall's 3D world should be black while its interface still draws.
4. Walk into a town and back out, which the automated route did not do.
5. Confirm your normal Daggerfall Unity still opens with your usual settings and saves.
6. With both windows focused, watch for a hitch when crossing a map cell.

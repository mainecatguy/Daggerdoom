# Doom view behind small Daggerfall menus (run 20261127-091125)

Goal: opening a small Daggerfall window (merchant Talk/Sell/Exit and others) shows the Doom view around it instead of
black; full-screen menus unchanged.

## Cause

- Daggerfall already renders its windows into a render target cleared to transparent (`UserInterfaceRenderTarget`
  clears to `Color.clear`, `DaggerfallUI.OnGUI`), and the readback to Doom keeps BGRA with alpha.
- Doom was the one painting black: `DD_BridgeDrawUi` (`UZDoom/src/dd_bridge.cpp`) ran `Dim(..., 1.f, ...)` over the
  whole screen before drawing the Daggerfall frame. Doom keeps rendering the (paused) level every frame underneath,
  so the view is simply hidden.

## Plan

1. Drop the opaque fill while a menu is open (the "Entering Daggerfall..." screen keeps it). Doom's paused view then
   shows wherever the Daggerfall frame is transparent: a live render of the frozen frame, not a stored image.
2. Alpha fix: Unity's UI shaders blend with a single `Blend SrcAlpha OneMinusSrcAlpha` (checked
   `Assets/Shaders/DaggerfallSDFFont.shader`, `DaggerfallPixelFont.shader`, `DaggerfallUIBlendShader.shader`), so the
   render target's alpha is `a*a + dst*(1-a)`, not coverage. Over an opaque panel it never drops below 0.75; drawn
   straight in Doom, anti-aliased text edges would let ~25% of the Doom view bleed through full-screen menus. Doom now
   converts each frame while copying it (`DDUiTexture::SetFrame`): alpha >= 190 becomes opaque (already composited);
   below that the pixel lay over the clear, so coverage = sqrt(alpha) and colour is un-premultiplied. Fully opaque and
   fully clear pixels are copied unchanged (fast path). Result: the same look as Daggerfall Unity drawing over its
   own 3D view, including the dim that popups with a parent window draw.
3. Test: `DoomerfallMenuBackdropTest` (`-dfmenubackdroptest <folder>`, own file, no hook) pushes merchant popup,
   message boxes (plain and dimmed), pause options, spellbook, automap and travel map over the inventory, saves each
   Daggerfall render with alpha and logs alpha counts. `tools/menu_text/menu_text.py --backdrop` runs it paired;
   Doom's `-dfuitest` screenshots each window.

4. Found in the first good run (run5) and fixed:
   - Doom drew its pause graphic (red "PAUSE", top centre) because `pauseext` is set while a Daggerfall menu is open;
     it was hidden under the black before. `D_Display` now skips it while `DD_BridgeUiActive()` (one condition in
     `d_main.cpp`, false without a bridge session).
   - A popup whose parent is Daggerfall's HUD draws the HUD first (`DaggerfallPopupWindow.Draw`), so Daggerfall's
     vitals bars and HUD text appear over Doom's view and HUD. They were drawn over black before too. A first try
     hid the whole Daggerfall HUD during menus; the verifier rejected it (it also hid fades, escort faces, spell
     icons). **Reverted**: the HUD draws as before. Question below.
5. Verifier round 1 (rejected run6): full-screen menus must stay unchanged, including their black side bars.
   - Doom now keeps the black backdrop when the frame covers Daggerfall's 320x200 panel: while copying, it counts
     clear pixels inside the centred panel rect (2 px inset); at most 1% clear means a full-screen window
     (`DDUiTexture::coversPanel`). New Game and Load Game always keep the black backdrop.
   - With only the HUD up (fast travel settling, fades through the HUD panel) Daggerfall clears its render to black
     (`DoomerfallUi` sets the target's `ClearColor`; `DaggerfallUI.OnGUI` now clears with `ClearColor`, which
     defaults to clear, so standalone Daggerfall Unity is unchanged). Those frames are opaque, so they look as before.

## Failed / wasted steps

- Copying only `Assembly-CSharp.dll` into the demo: a new `[RuntimeInitializeOnLoadMethod]` class is registered in
  `globalgamemanagers`, so the test never started (runs 3, 4). Copy the whole `Builds/Windows64`.
- The `menu-text` demo's bridge DLL, launcher and `uzdoom.pk3` were older than this branch (bridge schema mismatch,
  missing ZScript natives); the demo now has all of them rebuilt from this branch.
- `uzdoom.exe -norun` exits 57 after "f 2" on the private desktop, for the previous demo's exe too, so it is not this
  change; a real E1M1 launch was used instead.

## Known gaps

- Frame copy cost: the alpha fix walks every pixel while copying (fast path for opaque and clear pixels, two table
  lookups otherwise). Doom logs `texture copy` latency when a menu closes; the test ends with the menu open, so no
  number was captured. Play-test item below.
- The Doom view is the paused live render, not a stored frame: anything Doom draws while paused (console messages,
  Daggerfall text held for later) shows around the menu.

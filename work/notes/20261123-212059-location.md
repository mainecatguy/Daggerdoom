# Recheck Daggerfall's reported location after New Game (20261123-212059)

## Result

Reproduced, but it is not a desync. Daggerfall's info box ("You are in %cn", text record 22) names the location
that owns the player's whole map pixel, not the town's walls. Daggerfall Unity does this too:
`MacroHelper.CityName` returns the location name whenever `PlayerGPS.HasCurrentLocation` is true, and that flag is
set per map pixel in `PlayerGPS.UpdateWorldInfo`. A map pixel is 32768 Daggerfall units (about 800 m) wide, and
Privateers Hold is a tiny location in the middle of its pixel. Open wilderness around it still reports
"You are in Privateer's Hold." No game code was changed. The project rule is to work as Daggerfall does.

## Plan and approach

1. Read the status text path, `PlayerGPS`, position sync, New Game, and door transitions.
2. Add a temporary probe (`tools/reported_location/probe.patch`) that logs Daggerfall's real expanded status text,
   Doom's reported pixel, Daggerfall's GPS pixel, and whether either pixel has a location. It is used only for a
   test build and is not in the game code. To repeat: apply the patch, build Daggerfall, run `stage.py`, then
   `run_location.py 3 <label>` and `extract_evidence.py <label> <file>`.
3. Drive a real New Game route (`tools/reported_location/run_location.py`, `harness.zs`, `stage.py`): real
   character creation with clicks, real cinematics, real difficulty pick, then Doom's own dungeon start, the real
   exit door, a walk east out of the town map onto the overworld, a walk across the pixel border, and a real fast
   travel through the travel map's location list. The run used the full DRLA, DRLA Monsters, and DRLAX set, as
   `play.bat` does.

## Failed approaches and test-harness lessons

- The UZDoom build in `DoomDaggerfall-build/uzdoom-launcher` does not match this checkout (no bridge log). The
  monster-deaths bridge DLL is protocol 4 and this checkout needs 5. `stage.py` uses private builds in
  `uzdoom-location`, `bridge-location`, and `launcher-location`.
- `+logfile route` writes `log-route.txt`. A name with a dot gets mangled.
- `EventHandler.SendNetworkEvent("df_fast_travel")` does not open the menu, because the bridge hooks only the
  `netevent` console command. Keys posted to a minimized window do not reach game bindings. The route uses
  `-dfuitest 1` with `dd_ui_test_hold` instead.
- The first harness moved the player to the dungeon exit's coordinates for one tick after arriving in the town map,
  which threw Doom onto the overworld. Fixed. It was the harness, not the game.
- The DRLA set always logs a harmless `Script error` in a translation, so the runner's fatal check is narrower.
- The first evidence write-up cited `test-run/df.log`, which a later clean run overwrote. Runs now take a label and
  keep their logs, and the evidence lines are committed. The verifier caught this.
- Character creation with the full mod set takes 30-55 s, so the runner allows 150 s for the whole route. That is
  longer than the usual 30 s guideline, but fatal errors still stop it at once. One run also lost a list double click,
  so the runner now retries the click.

## Play-test list

- Start a New Game, leave the dungeon, walk well away from the entrance, and open the info (status) button. It should
  still say Privateer's Hold until you have gone roughly 400 m from the middle of its map pixel. Then it should say
  the region name ("Daggerfall"). Compare with stock Daggerfall Unity if in doubt.
- Fast travel to a town and check the info button once Doom has arrived.

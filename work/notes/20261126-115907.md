# Lanes hang when a run ends: keep build helpers (run 20261126-115907)

Continues `work/notes/20261126-114648.md` (cause, first patch). Owner's new instruction: build helpers meant to stay
open (MSBuild nodes, Unity's license client and the like) must not be closed; everything else a round leaves is.

## Plan
1. Replace the job's "terminate everything" with a selective close that spares a list of build helpers.
2. Share it between run.ps1 (per child) and queue.ps1 (per run, backstop), so both clean up the same way.
3. Make the fake lane prove helpers survive and games do not.

## What changed
- `tools/lane_hang/harness-fix.patch` now adds `scripts/overnight/lane_job.ps1` (job helper, keep list) and uses it
  in `run.ps1`'s `Invoke-Logged` and around `run.ps1` in `queue.ps1`. The job no longer has kill-on-close, so the kept
  helpers outlive the job handle. Details and the keep list: `tools/lane_hang/README.md`.
- The fake lane now also starts a fake `MSBuild.exe` (built by the test with `Add-Type -OutputAssembly`) each round,
  and FAILs if any of them were closed.
- Still a patch: `scripts/overnight/` cannot be edited by agents. Apply with `git apply tools/lane_hang/harness-fix.patch`.

## Verifier fix: timeout path
The verifier found that a timed-out child was still killed with `taskkill /T`, which kills build helpers in its tree.
Now, when a job exists, only the child is ended (`$p.Kill()`) and `Stop-LaneJob` closes the rest selectively;
`taskkill /T` stays only as the no-job fallback. New `tools/lane_hang/run_timeout_test.py` calls the patched
`Invoke-Logged` with a child that never exits:
| Patch | Return | Game left | Helper alive | Result |
|---|---|---|---|---|
| previous (taskkill /T) | -1 | 0 | 0 of 1 | FAIL |
| new | -1 | 0 | 1 of 1 | PASS |
The fake lane still PASSes with the new patch (5.1 s, 0 games, 2 of 2 helpers).

Test detail: when the test driver's output was a pipe, the fake helper died as the driver exited, even though the
cleanup had left it running (it was listed alive right after `Invoke-Logged`). With file output, which matches what
patched `queue.ps1` does for `run.ps1`, it survives. I did not dig into why; with the unpatched pipe setup a real
MSBuild node could die the same way when `run.ps1` exits, which the patch's file output avoids.

## Failed approaches
- First try set `JOB_OBJECT_LIMIT_BREAKAWAY_OK` through the basic limit structure; Windows rejects that flag there
  (it needs the extended structure), so no job was made and games survived. Fixed; the fake lane caught it.

## Known gaps
- Not checked with a real Claude session: a cheap haiku session inside a job (scratch script) needed a permission
  approval nobody could give overnight. If Claude Code's shell tool starts background tasks with "break away from job",
  those escape the cleanup (they still cannot stall the lane, thanks to the queue.ps1 file change). The first real lane
  after applying the patch is the live check: its run log should show `Closed what ... left running` lines.
- A kept helper is kept wherever it came from; a leftover `MSBuild.exe` that is a stuck build, not an idle node, also
  stays. Processes started outside the tree (Task Scheduler, WMI) are not touched.
- The keep list is by name. Anything not on it is closed at the end of each round, check, verifier and review.

# Synchronized loading and the death screen

## Status

Loading a bundled save now restores both games from the same `.zds`. Doom's load command and death on a Daggerfall map both go through this path. Run the tests with `python tools/synchronized_load/run_load.py`. Results are appended to `review/synchronized-loading/test/results.txt`.

## Plan

1. Add a load transaction to the bridge, with checks before anything is destroyed.
2. Replace both games' automatic death behavior on Daggerfall maps with one death screen.
3. Prove save, change, load, death, bad saves, and stock behavior with the real games.

## Load sequence

1. `G_LoadGame` hands a bundle to the bridge. A regular save on a regular map loads normally.
2. Between tics, Doom checks every zip entry's CRC, the manifest, the file list, the map, the engine version, and the required WADs. It then stages Daggerfall's files and freezes.
3. Daggerfall parses its half and compares HP, max HP, and position with the manifest. Up to here, a refusal leaves both running games untouched.
4. Daggerfall restores, waits for its world to settle, pauses, publishes HP, and answers.
5. Doom restores its half and confirms.
6. Daggerfall unpauses and sends resume. Doom unfreezes on that message.

A load freezes both games for about 2.1 seconds in the City of Daggerfall.

## Death flow

- Daggerfall still decides death. Its automatic restart is off in a bridge session only.
- Doom shows its death view for 2.5 seconds, then a menu: Load Last Save, Load Game, Main Menu. Escape cannot dismiss it, because it reopens.
- **Load Last Save** picks the newest save that passes every check, and logs any it skips.
- **Main Menu** goes to Doom's title with Daggerfall paused. Load Game works there. New Game is refused with "Load a save to continue", because the real new game flow does not exist yet. This keeps the two games from desyncing.

## Bad saves

Each of these was refused with the game still running, the file unchanged, no staging files left, and Daggerfall's restore never started: flipped byte in Daggerfall's half, flipped byte in Doom's half, truncated file, missing Daggerfall file, Doom-only save, manifest HP mismatch, manifest map mismatch, newer bundle format.

If a restore fails after it has begun, both games are held at the death menu until another save loads. This path is written but was **not** exercised by a test.

## Proven with the real games

- Save, change HP and position, load: HP and position return in both games, and they keep running.
- Death, 5 seconds past Daggerfall's old restart time, Load Last Save.
- Death, Main Menu, refused new game, Load Game from the title.
- Load Last Save passes over a damaged newer save.
- `DOOM.WAD` E1M1, stock and with the DRLA set, with no bridge: save, load, death, and Doom's automatic reload.
- The owner's Daggerfall registry key hash was unchanged.
- The death menu draws correctly in a real screenshot (`review/synchronized-loading/test/menu`).
- The final build passed all 18 checks in `run_load.py`, and the existing scripted save handshake test passed 45 of 45.

## Not proven, and known gaps

- Normal Daggerfall death with no bridge was not played. The restart is gated on the bridge session flag. A plain launch was only smoke-tested.
- The menus were driven by their console commands. A human has not clicked them.
- Loading from a building or dungeon was not tested. Only the city was.
- `-loadgame` at startup in a bridge session is routed to the load path but untested.
- Killing either game mid-load was not tested.
- Indoors, Daggerfall's half still records the door outside, as noted in the save work.

## Failed approaches

- The first version crashed Doom just after resuming a load made from inside a level. Doom's between-tic player prediction outlived the level. Undoing prediction before the load fixed it. Loading from the title never hit this.

## What Escape did, step by step (before this change)

| Step | Doom | Daggerfall | Result before |
|---|---|---|---|
| Doom's menu → New Game, waiting for Daggerfall (`NgWaitDf`) | Escape opens Doom's main menu | – | Doom's menu over the starting flow |
| Creation screens (`NgCreating`, Daggerfall window shown) | The bridge's window hook forwards every key to Daggerfall; raw keyboard key-downs are off in GUI capture | Daggerfall's wizard handles it | Correct (see table below) |
| Between the last cinematic and the difficulty prompt (`NgCreating`, window closed, Daggerfall still placing the character, up to 20 s) | Escape opens Doom's main menu | – | Doom's menu, then the difficulty prompt replaces it |
| Difficulty prompt (`NgDifficulty`) | Escape closes the prompt; the next frame reopens it | – | **No way out**: Escape just brings the prompt back forever; you must pick a difficulty |
| "Entering Daggerfall..." (`NgLoading`..`NgWaitGo`) | Escape opens Doom's main menu, which pauses Doom | – | **Can break the start**: the 60 s start deadline keeps running while the menu pauses Doom, and `NgFail` drops the character |

Daggerfall's own wizard, per screen (`DaggerfallStartNewGameWizard.cs`, measured in the run below):

| Screen | Escape |
|---|---|
| Race | closes creation; Doom is at its title, New Game works again |
| "Is this your race?" Yes/No box | ignored (Daggerfall Unity: boxes with buttons set `AllowCancel = false`) |
| Gender (Male/Female buttons) | ignored, same reason |
| Class method (generate / list) | goes to the class list (Daggerfall's own quirk: cancelling means "from a list") |
| Class list | back to Race |
| Biography method | back to Class list |
| Reputation message (after "generate") | closes, goes on to Name |
| Name | back to Biography method |
| Face | back to Name |
| Bonus stats | back to Face |
| Bonus skills | back to Bonus stats |
| Summary | back to Bonus skills |
| Cinematics | skips each |

So the creation screens themselves already did the Daggerfall thing. The breakage was in Doom, around them.

## Changes

`UZDoom/src/dd_bridge.cpp`, `UZDoom/src/menu/doommenu.cpp` (inactive without `-dfflow` and a bridge session):

- **Doom's main menu stays shut during the whole New Game / plain load flow** (`DD_BridgeBlocksMainMenu`, hooked in
  `M_SetSpecialMenu` for `MainMenu`). Daggerfall's screens, the difficulty prompt and the trip to the start each answer
  Escape themselves. A blocked attempt logs `new game: kept Doom's main menu closed, new game step N`.
- **Escape at the difficulty prompt asks "Abandon this character and return to the title?"** (plain load: "Return to
  the title without loading this save?"). **No is highlighted.** Yes sends `NEWGAME_ARRIVED 0`, so Daggerfall drops
  the held character (the existing `NgFail` path), and Doom goes idle at its title, where New Game starts over. No or
  Escape brings the prompt back.
- **An Escape within 1 s of the prompt opening just reopens the prompt.** That is a late Escape meant for the last
  cinematic. Seen in every test run: the driver's cinematic-skip Escape lands on the prompt.
- Test only: `-dfnewgametest escape` chooses New Game at every return to the title and never picks the difficulty
  (two expressions in the existing test lines).

Why a question and not an immediate back-out: by the difficulty prompt, the character is made and the cinematics have
played. The first test run showed the danger. A cinematic-skip Escape opened the question, and the driver's Enter
chose the then-default Yes and dropped the character. Hence No is the default and the 1 s grace. Daggerfall has no
difficulty prompt to copy, so this is my engineering call. A plain "Escape = back to title" is a one-line change if
the owner prefers it.

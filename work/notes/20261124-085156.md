# Ammo can be picked up in Daggerfall's inventory (20261124-085156)

## Goal

Owner (2026-11-24): "we need the ability to pick up ammo in the inventory at all in Daggerfall." The ammo stacks from
`DoomerfallAmmo.cs` (notes `20261124-075147.md`) could not be picked up in Daggerfall's inventory. The cause was not traced.

## Plan

1. Find how ammo moves in Daggerfall's real inventory window. The first ammo test changed stacks directly
   (`DoomerfallAmmo.Change`) and never went through the window.
2. Reproduce it in the paired harness by driving the window's own click handlers: drop from the inventory, which
   makes a ground pile when the window closes, then open that pile as a loot window and take the ammo back.
3. Fix what breaks, then rerun the take, load, and E1M1 checks.

## Cause

Found by reproducing it in the paired harness (`tools/ammo/ammo.py take`, first run, before the fix):

- **Splitting an ammo stack made a non-ammo item.** `ItemCollection.SplitStack` builds the split part with
  `ItemBuilder.CreateItem(group, TemplateIndex)`. Ammo templates are gone by play time, and only the bullets template
  is registered to the ammo class. So 5 shells split from a stack came out as a plain `DaggerfallUnityItem`
  "Shotgun shells" (log: `split 5 shells gave DaggerfallUnityItem 'Shotgun shells' x5, type -1`). Once taken back, it
  did not count as ammo, and Doom lost those 5 shells for good (Daggerfall's counts ended "DIFFERENT from the counts
  before the drop": Shell 15 instead of 20). Daggerfall splits a stack whenever the "how many?" popup is used, which
  happens on a Ctrl-click and on any pickup the weight limit cuts short. So taking part of a pile, or a pile while
  heavily loaded, did not give the player ammo. A split bullet stack would also break if the templates were gone.
- **Equip-mode clicks said the ammo was broken.** In the plain inventory window (the one Doom's Inventory key
  opens), the default action is Equip. Taking a dropped item back in that mode moves it and then calls `EquipItem`,
  which shows Daggerfall's "broken" message for ammo, because ammo has a condition of 0. The ammo did move, but the
  player was told otherwise. Clicking one's own ammo stack in Equip mode showed the same message.

A whole stack taken in the loot window's Remove mode already worked.

## Fix

- `DaggerfallUnityItem.CreateStackPart()` (new, virtual, `[Doomerfall]`). It returns what `SplitStack` used to build.
  `ItemCollection.SplitStack` now calls it, a one-line change. `DoomerfallAmmoItem` overrides it to return an ammo
  item of the same type with its own weight and price.
- `DoomerfallHotkeys.BlockEquip` quietly refuses to equip ammo, so there is no "broken" message.
- Test only: `DoomerfallAmmo.Settled`, which is true when both sides agree with no delta in flight. The
  `-dfammotest` hook now also drives the real `DaggerfallInventoryWindow` through its own click handlers, using
  reflection. It drops the whole bullet stack and 5 split shells, closes the window, opens the pile that closing made
  as a loot window, takes bullets in Remove mode and shells in Equip mode, and compares the counts. The harness
  (`tools/ammo/harness.zs`) watches Doom's counts for each step. The review folder is now
  `D:\dev\DoomDaggerfall-loop\review\ammo-pickup`, which leaves the first run's folder alone.

## Verification

Builds: `python tools/ammo/build_native.py` (bridge, launcher, and UZDoom from this branch, exit 0). Daggerfall
Unity CliBuild (`CliBuild result: Succeeded`) before and after the fix.

- `ammo.py take` after the fix: `split 5 shells gave DoomerfallAmmoItem 'Shotgun shells' x5, type 1`. Doom applied
  `Clip -93`, `Shell -5`, `Clip +93`, `Shell +5`. Daggerfall then logged `window pickup settled, same as the counts
  before the drop`, and no message box covered the window after the Equip-mode take. After that, 2 boxes were picked
  up by touch, 5 rounds were spent, and an autosave was made. Final: Doom Clip 88 Shell 20, Daggerfall the same (MATCH).
- `ammo.py load`: Daggerfall restored `Clip 88; Shell 20` from the bundle. The hook and the window test ran again
  and both sides ended at Clip 81 Shell 40 (MATCH).
- `ammo.py check`: stock DOOM.WAD E1M1 exit 0 with 0 script errors. DRLA E1M1 exit 0 with the usual 3 DRLA script
  errors and none fatal. `-norun` exit 1337.

Not covered by scripts: real mouse clicks in the window while Doom shows it. The test calls the window's click
handlers directly, with Doom running rather than paused behind the menu.

## Findings outside this fix

- **Piles dropped outdoors cannot be reached from Doom.** `DoomerfallPositionSync.ItemSpace` returns only indoor
  spaces, so `DoomerfallItems` never lists exterior piles. This was already noted in `20261123-182155.md`. Ammo (or
  anything else) dropped in a town is safe in Daggerfall but cannot be picked up again. A New Game starts in a town,
  so this may be what the owner ran into. It is a feature of its own (exterior piles in Doom's outdoor coordinates)
  and is not done here. Asked as a question.
- `ItemCollection.CopyAll` and `CloneAll` use the non-virtual `DaggerfallUnityItem.Clone()`, which turns any custom
  item class (ammo, Doom items) into a plain item. Nothing in the inventory, loot, or trade paths uses them for the
  player's items, so this is left alone. A quest that clones a Doom item would hit it.

## Play-test list

1. Open the inventory with Doom's Inventory key. Click Remove, then click part of the bullet stack with Ctrl held and
   drop 10. Doom's bullet count drops by 10.
2. In the same window, click the dropped bullets in the right-hand list while in Equip mode. They come back with no
   "broken" message, and Doom's count is back.
3. Indoors (a dungeon or tavern), drop ammo, close the inventory, look at the pile, and press Use. Take it all, then
   drop again and take only part with Ctrl. Doom's count matches each time.
4. Load up near the weight limit and take a big ammo pile: Daggerfall offers part of it, and the part taken shows in
   Doom's HUD.
5. Outdoors, dropped ammo leaves no pile in Doom (known gap, see above).

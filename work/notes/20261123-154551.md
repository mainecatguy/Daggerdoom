# Scale Daggerfall sprites to the 75% world

## Result

Only one sprite path was the wrong size: `DaggerfallItem`. It drew at 100%, and the gallery shrank anything over 112 pixels to fit. It now uses Daggerfall Unity's billboard size at 75%. Dungeon, action, and town billboards were already correct, so their code and generated data did not change.

Images were not touched. All 396 item image files have the same CRC in the old and new packages.

## Every sprite path, compared with Daggerfall Unity

"Expected" is `MeshReader.GetBillboardMesh`'s size times 0.75, read from the `TEXTURE.xxx` headers independently of the converter by `tools/dungeon_converter/sprite_scale_check.py`. A ratio of 1 is exact.

| Path | Where | Sprites measured | Before (shown / expected) | After |
|---|---|---|---|---|
| Ordinary dungeon flats | `FlatExport.cs`, `DFDFLATS` | 129 Privateer's Hold, 426 Scourg Barrow | 0.9999 to 1.0001 | unchanged |
| Action flats | `DoorExport.cs` | 1 Privateer's Hold, 5 Scourg Barrow | 1.0000 | unchanged |
| Town billboards, standalone package | `CityExport.cs`, `DFFLATS` | 6,629 Daggerfall, 5,225 Sentinel | 0.9999 to 1.0001 | unchanged |
| Town billboards, live game cache | `.ddt` files, spawned by `dd_treadmill.cpp` | 7,751 in 3 cached locations | 0.9999 to 1.0000 | unchanged |
| `DaggerfallItem` | `ItemGallery.cs`, `DaggerfallItem.zs` | 432 entries | 0.884 to 4.533 | 0.9999 to 1.0001 |

The item "before" range is wide because items ignored Daggerfall's per-record scale and the gallery capped large images.

The 0.75 was not applied twice anywhere. The treadmill passes the scale from the lump through unchanged. Generated `DDTxxxxx` maps copy the `DDTOWN` template, so they have `pixelratio = 1.0`.

## Engine proof

`tools/dungeon_converter/sprite_scale_probe.py` puts a 64x64 image at scale 0.75 beside a real 48-unit pillar at the same depth in UZDoom. Pillar, floor-anchored sprite, and centered sprite each measured 75 x 75 pixels with the same bottom row (363). This proves displayed size and both anchor types.

## Regressions

- Item gallery: 460 shown, 0 broken.
- Stock `DOOM.WAD` E1M1: entered, no errors.
- E1M1 with the DRLA set: entered. It logs the same 766 error lines with and without the item package, so the package adds none.
- Privateer's Hold: 129 billboards. Scourg Barrow: 426. City of Daggerfall: 6,629. All loaded and exited cleanly. Doors, actions, and water code were not changed, and no dedicated door, action, or water regression was rerun.
- UZDoom source was not changed.

## Decisions and limits

- **Inventory art has no Daggerfall world size.** Most item sprites are paper-doll or inventory images that Daggerfall Unity never draws as billboards. I used the same formula, so one pixel is one Daggerfall unit before the 75%. Those items can still look large, such as a pauldron nearly as tall as the player. See the owner question in the final report.
- **Removed the gallery's 112-unit cap.** It would have made large items the wrong size. The largest image is 169 pixels, or 127 units, so it still fits the 128-unit grid.
- **Eye height may affect perceived size.** The default Doom body has a 41-unit eye. Daggerfall's eye at 75% is 51.3 units. A lower camera can make everything look bigger. This is a hypothesis and I did not change it.

## Failed approaches

- The first engine probe failed because the pillar's side faces were also red, and its linedefs were wound backward. That was a harness bug, fixed by coloring only the front face and correcting the winding.

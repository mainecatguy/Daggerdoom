# QA bot: a Daggerfall character that Claude can control (design, 20261124-120622)

Research card plus the smallest prototype. Run log, commands and play-test list: `work/notes/20261124-120622.md`.
Proposed cards: `work/notes/20261124-120622-qabot-cards/` (copies of `work/queue/qabot/proposed/`).

QA use only. Everything here is inert unless UZDoom is started with `-ddqa <folder>`, and the QA runs proper are
overnight-only (2AM to 7AM).

## 1. Summary

- **Channel (built, prototype):** a file channel, not a socket. `qa.py` appends `<id> <command> [args]` lines to
  `<folder>/inbox.txt`; UZDoom (`UZDoom/src/dd_qa.cpp`) reads new lines between frames, runs each one *inside the
  next game tic*, and appends one JSON line per answer or event to `<folder>/outbox.jsonl`. Both files together are
  the replay log. No bridge layout change, no firewall, nothing listening on a port.
- **Honest movement (built):** `move_to` steers through the player's own input. `dd_qa.cpp`'s `DD_QaInput` is called
  from `G_BuildTiccmd` and adds forward/turn exactly as keys and a mouse would. Doom's own physics, step height,
  friction and collision move the player. Teleport exists only as a separate, labelled `setup` command.
- **Pathfinding (built, offline):** the dungeon converter already writes a walk graph for every dungeon
  (`<slug>.points.txt`: a 24-unit lattice of standing spots with floor/ceiling, plus directed links for steps, one-way
  drops and door crossings). `tools/qa/nav.py` runs A* on it. Median 9 ms per plan in Privateer's Hold, 53 ms in
  Scourg Barrow. This beats sector-based A* (section 6).
- **Daggerfall windows (design only):** a Daggerfall-side QA file reader, not new bridge kinds. Daggerfall walks the
  top window's components and writes text, list items and clickable rectangles to `<folder>/df_window.json`; answers
  go through the same `DoomerfallInput` path Doom's real mouse and keys use (section 4).

## 3. Protocol

### Where commands run

| Command | Runs in | Kind | Status |
|---|---|---|---|
| `pos` | UZDoom tic | read | built |
| `actors [radius] [limit] [kind]` | UZDoom tic | read | built (actors only; doors/exits are a card) |
| `move_to x y [tolerance] [seconds]` | UZDoom tic + `G_BuildTiccmd` | honest, job | built |
| `stop` | UZDoom tic | control | built |
| `use` | `G_BuildTiccmd` (one `BT_USE`) | honest | built |
| `god [on/off]` | UZDoom tic | setup | built |
| `teleport x y [z/nan] [angle]` | UZDoom tic | setup | built |
| `kill <ref or df id>` | UZDoom tic, `P_DamageMobj` with the player as source | setup | built |
| `con <console command>` | UZDoom console (`screenshot`, `dd_tm_use 1`, ...) | setup | built |
| `goto x y z` | `qa.py` + nav.py, then `move_to` per waypoint | honest, high level | built (one call) |
| `window` / `choose <n or label>` / `type <text>` | Daggerfall QA reader | read / honest | card 2 |
| `inventory`, `quests`, `journal`, `stats` | Daggerfall QA reader | read | card 2 |
| `levitate on/off` | needs a real Doomerfall levitation feature first (see risks) | honest | blocked |
| `attack <ref>` / `clear_room` | UZDoom tic + input (aim, `BT_ATTACK`) | honest, job | card 3 |
| `explore_until <condition>` | qa.py over nav.py frontier | honest, high level | card 3 |
| `path_to exit` | qa.py: exits from the converter's door list | honest, high level | card 3 |

### Wire format

Inbox line: `<id> <command> [args]`, ids chosen by `qa.py` (`c1`, `c2`, ...). Outbox: one JSON object per line.

- Reply: `{"id":"c7","tic":4120,"ok":true,...}`.
- Job end: `{"id":"c8","done":true,"result":"arrived|stuck|timeout|died|stopped|replaced","honest":true,...}`.
- Event: `{"event":"hello|level|left_level|paused|resumed|bad_line","tic":...}`. Planned: `damage`, `window`,
  `quest_message`, `died`, `stuck` (stuck already ends a job).

Commands are buffered between tics and run at the start of the next tic (`DDTreadmill_Tick`), so nothing changes the
world from outside a tic. This matters: the oversight list already has one class of bug from spawning in
`DD_BridgeFrame` while client prediction is active.

When Doom is paused (any menu, including a Daggerfall window shown in Doom), tics stop, so commands queue and
`qa.py` reports `no reply` plus the last `paused` event. The bot then reads the window instead.

### Why a file and not a socket

The card suggested a localhost endpoint. Files are simpler here and lose nothing that matters at QA speed:

- latency: polled every 25 ms between frames; replies arrive in one or two tics;
- the inbox and outbox *are* the replay log (question 9) with no extra code;
- no Winsock code in the engine, no firewall prompt on the owner's machine, no port clash between lanes;
- `qa.py` is a fresh process per tool call, so a socket would need reconnects anyway.

A socket can replace the file later without changing the command set.

## 4. Daggerfall windows

Facts:
- Daggerfall windows are not translated into Doom menus. Daggerfall draws its real UI into a render texture and
  publishes it on the bridge's shared surface; Doom forwards mouse and keys (`DoomerfallUi.cs`, `DoomerfallInput`).
  So Doom knows nothing about the window's text.
- Many Daggerfall buttons are hit rectangles over background art with no label (talk window, character sheet,
  inventory tabs). Text components (`TextLabel`, `MultiFormatTextLabel`, `ListBox`, `TextBox`, `Button.Label`) carry
  the rest.

Design (card 2):
1. **Read.** A Daggerfall-side `DoomerfallQa.cs`, active only with Daggerfall's own `-ddqa <folder>` flag (a one-line
   hook in `DoomerfallBridge`), writes `<folder>/df_window.json` whenever the top window changes or on request:
   window class, every text component's text and rectangle in native 320x200 coordinates, list items with indexes,
   buttons with rectangles and names, and the text box if any.
2. **Adapters** for the windows that matter: message boxes (text + `MessageBoxButtons`), quest popups and yes/no
   questions, talk (topics list), shops/trade, inventory, loot, travel map, rest, and the text-input box (riddles,
   names). Each adapter turns the window into `{"text": "...", "choices": [{"n":1,"label":"Yes"}, ...]}`.
3. **Answer** through `DoomerfallInput` with a click at the choice's rectangle or typed characters. That is the same
   path Doom's real mouse and keys take, so it is honest. A fallback is the existing pixel click through Doom's
   window (`run_new_game.py`).
4. **Fallback for unknown windows:** `qa.py shot` (console `screenshot`) gives Claude the picture, plus the raw
   component dump.

Files instead of bridge kinds 210-219: the QA folder is already shared by both sides, the window dump is long text
that a fixed bridge payload would have to chunk, and any change to `bridge/doomerfall_bridge.h` changes the layout
hash and breaks every other lane's test folder until rebuilt. The reserved kinds stay free for a later in-band
version.

## 5. Honest versus setup movement

- Honest: `move_to`, `goto`, `use`, and later `attack`. The player is moved only by input that a human could give;
  turning is applied as a view-angle delta exactly like the mouse. Each job reply says `"honest":true`.
- Setup: `teleport`, `god`, `kill`, `con`. Every setup reply says `"setup":true`.
- A completability claim is computed from the outbox: the route counts only if every movement between its start and
  end came from honest jobs. `qa.py` should print a run summary listing setup commands used (card 1).
- Levitation must be an honest *ability*, not noclip. **Doomerfall has no levitation today**: no code in UZDoom or
  the Daggerfall bridge maps Daggerfall's Levitate effect to Doom flight (grep for "levitat" in `UZDoom/src`: none).
  Until it exists, levitation links in the plan are reported as "needs levitation" and the bot cannot walk them
  honestly. That is a question for the owner (section 10).

## 6. Pathfinding comparison

Measured with `tools/qa/nav.py` on the converter's own graphs
(`review/encounter-placer/wad/privateershold.points.txt`, `review/pickups/scan/scourgbarrow/scourgbarrow.points.txt`),
40 random reachable pairs each.

| | Privateer's Hold | Scourg Barrow |
|---|---:|---:|
| Graph nodes / directed links | 13,968 / 49,775 | 56,705 / 199,780 |
| Load | 25 ms | 515 ms |
| Reachable from the entrance by walking | 9,674 | 42,040 |
| Levitation links added (up to a ledge one step away, under this node's ceiling, with body room) | 1,123 (28 ms) | 10,353 (351 ms) |
| Reachable with levitation | 9,750 (+76) | 44,648 (+2,608) |
| A* per plan, median / max (walking graph) | 5.8 / 22.3 ms | 26.6 / 80.1 ms |
| Smoothing median / max (strict version, after the in-game fix) | 18 / 43 ms | 40 / 135 ms |
| Median route length / waypoints after smoothing | 3,480 units / 111 | 10,488 units / 302 |

Waypoints are internal to `goto` (one `move_to` each), not tool calls, so their number costs time, not tokens.
The first, looser smoothing (39 waypoints median) cut a wall corner in play; see section 11. The strict version keeps
almost every node; a better string-puller (funnel over the lattice) is a card 1 or 3 job.

Options compared:

1. **A* over the converter walk graph (chosen).** Already exists for every converted dungeon; it is the graph the
   converter's connectivity and leak audits check (`Program.cs` `WriteStats`, `AuditEdges`), so its links already
   respect step height, one-way drops, closed doors (door flag on nodes and links) and the wall audit. Fast enough
   offline in Python. Stacked floors are separate nodes, so 3D floors and bridges work.
2. **A* over Doom sectors and their two-sided lines.** Converted maps are built from a 12-unit grid and then fitted
   chains: Privateer's Hold has tens of thousands of lines and many control sectors for 3D floors. Sector polygons are
   irregular, so "can I cross this line" needs the same step/drop/ceiling tests per line plus 3D-floor handling, and
   paths through big sectors need a second funnel pass. More work for a worse graph.
3. **Runtime grid sampling in UZDoom** (probe `P_CheckPosition`/`P_TryMove` dry runs on a lattice). The most honest
   source (the engine's own collision, current door state), but slow to build per visit and duplicates the converter.
   Good as a *local* fallback: when `move_to` reports `stuck`, probe around the player and re-plan.
4. **Navmesh libraries (Recast).** Would need the map's triangles exported and a new dependency. Not worth it while
   the converter graph exists.

Gaps in the chosen option, each small: the graph is per converter version (a stale points file will mismatch a newer
map; the session should take the points file produced with the same WAD); towns and building interiors have no points
file yet (the city exporter has a separate raster); doors need a `use` before crossing a door link; lifts and moving
action platforms are not links. The levitation links above are a first cut.

## 7. Seeing the world

- `actors` (built): kind (`mook`, `monster`, `npc`, `guard`, `item`), class, `df` record id, position, health,
  distance and line of sight (`P_CheckSight`), nearest first, with a radius, limit and kind filter.
- Doors, action objects and exits (card 3): from the town cache's `DDDOORS`, the converter's door list, and lines with
  specials near the player.
- Screenshot: `qa.py con screenshot` writes into the session's `qa/shots` (UZDoom `screenshot_dir`). Claude can read
  the PNG. Costs about 1,000 to 1,600 input tokens per image, so use it for confusion, not routine.

## 8. Cost

Each call is a tool call: about 100 to 200 tokens to write plus the reply. Replies here are 150 tokens (`pos`) to
about 2,500 tokens (`actors` with 40 rows). Every reply stays in the conversation and is re-read on each later turn
(cached, but still billed at the cache-read rate), so call count matters more than reply size.

Rough estimate for Privateer's Hold, start to exit, about 40 rooms and 40 to 60 mook packs at the current planner:

| Style | Calls | Context added |
|---|---:|---:|
| Low level (pos, actors, move_to + wait per waypoint, kill per monster) | 600 to 1,000 | 300k to 600k tokens |
| With `goto` (one call per destination) and `actors` once per room | 150 to 250 | 80k to 150k |
| High level (`path_to exit`, `explore_until <item/npc/exit>`, `clear_room`, events summarised per call) | 20 to 60 | 15k to 40k |

So the high-level commands are not optional for a full dungeon: Mantellan Crux is many times larger than Privateer's
Hold. Proposals:
- `goto x y z` (built), `path_to exit|<df id>|<marker>`, `explore_until <condition> [budget]` (frontier search over
  unvisited graph nodes, stops on a condition such as "quest item visible", "window opened", "health < 30%").
- `clear_room [radius]`: honest fighting (aim + fire) until no hostile in sight; or, as setup, `kill` all in radius.
- Every reply carries a compact `events` digest since the last call (damage taken, kills, windows), so the bot never
  polls for them.
- `actors` defaults to a summary (counts by kind + the 10 nearest), with full rows on request.

## 9. Replay

The inbox is the command log and the outbox the answer log, both append-only, with tic numbers. A replay runner (card
1) feeds the inbox back line by line, waiting for each job to finish before the next command, and compares job
results (arrived/stuck, final positions within a tolerance) and window texts. Not frame-exact, because Daggerfall runs
in parallel, so replays check outcomes, not tics.

## 10. Risks and open points

- **No levitation in Doomerfall** (section 5). Completability of places that need it cannot be claimed honestly yet.
- **Windows pause Doom.** Every Daggerfall window stops tics; the bot must notice (`paused` event) and answer the
  window. Until card 2, only the window class name is known (`ui: top window is X`).
- **Graph and map versions.** The walk graph must come from the same conversion as the WAD being played. The prototype
  used the `encounter-placer` points file with the `newstart3` WAD; they differ in hash (encounter changes), not in
  geometry as far as the prototype shows.
- **Token cost** (section 8): without high-level commands a full dungeon run is too expensive.
- **Daggerfall's own HP and death**: `god` sets Doom's god flag only. Daggerfall owns HP and death, so a QA god mode
  that holds across both engines needs a Daggerfall-side flag too (card 2).
- **Live monsters block honest movement.** Doom monsters are solid. In the prototype a Former Sergeant stood in a
  corridor; with god mode on it could not hurt the player but still blocked the route. Honest completion therefore
  needs `attack`/`clear_room` (card 3), or a `kill` that is counted as setup.
- **Steering is a simple pursuit controller.** It turns part way each built command, because commands are built
  ahead of the tic that applies them. It does not strafe around corners or jump. Narrow ledges and moving platforms
  will need a better local controller.

# Run notes: 20261121-214123

Goal: research how to put the Daggerfall world inside UZDoom. The report is `work/notes/world-conversion-proposals.md`.

## Plan as executed

1. Read targeted UZDoom and Daggerfall Unity code for limits and world structure.
2. Measure real Daggerfall data with `work/spikes/measure_df.py` (prints aggregates only).
3. Generate synthetic UDMF terrain with `work/spikes/gen_maps.py` and run the built UZDoom through `work/spikes/run_probe.py`.
4. Write proposals from the evidence.

## Key findings

- UDMF is limited to ±32768. A vertex at exactly +32768 crashed the engine, while a 65,472-unit span worked.
- Fully connected maps of 21,632+ sectors crashed at load. `zoneboundary=true` lines fixed it up to 131,072 sectors with no engine change.
- `level.ChangeLevel("file:<path>")` loaded a WAD written after engine start, on the stock engine.
- Registry hop: 2,000 actors restored in about 2.9 ms, zero player position error over 8 swaps.
- Swap time: about 160 ms at 8k sectors, 600 ms at 33k, 1.5 s at 74k, 3.3 s at 131k.

## Failed approaches and deviations

- Generated files went to the session scratchpad, because the harness blocked writes to `D:\dev\DoomDaggerfall-loop\scratch`. Nothing generated is in the repo.
- Reading the Windows crash log needed approval, so I did not. The crash was isolated by varying test maps, so the stack-overflow cause is inferred.
- `++forward` did not move the player. A probe player class that sets `cmd.forwardmove` measured speed instead.
- First registry test restored 0 actors because ZScript is case-insensitive and a local `n` shadowed constant `N`. Fixed and rerun.
- The `DDSPEED` values on sloped maps are not valid top speeds. Only the flat-map value is used.
- One 128-cell swap took 5,976 ms and did not recur. Cause unknown.

# Fast travel arrival

Branch `agent/engine_r3-20261123-144443`. Demo: `D:\dev\DoomDaggerfall-loop\review\fast-travel-arrival\play.bat`. Press K for the map, pick a place, press Begin. Esc or K cancels.

## Result

Choosing a destination in Daggerfall's real travel map now travels. Daggerfall charges, advances time, and picks the arrival point with its own code. Doom then loads that location's map, or the overworld, at the same point.

## How it works

1. The old intercept in `DaggerfallTravelPopUp` is gone, so Daggerfall's normal `performFastTravel` runs.
2. `DoomerfallUi` listens to Daggerfall's post-travel event and keeps Doom paused until Daggerfall's placement settles.
3. Daggerfall sends the exact world position and facing in a new event, `DFB_KIND_TRAVEL`. It is additive, so the protocol version stays 4.
4. Position sync holds until Doom reports the same map pixel, so Doom's old position cannot pull Daggerfall back. A save during that hold is refused. After 30 seconds it logs an error and follows Doom.
5. `DDTreadmill_RequestTravel` lands in the location's map if the point is inside its entry band, otherwise in the overworld.
6. Doom refuses to open the map indoors. Daggerfall's own indoor check cannot see this, because its hidden player waits outside the door.

A separate two-trip run went overworld to Agakawan (5000 to 4990 gold), then **from inside Agakawan's town map** to Baasan Grange (4990 to 4980). Both games ended at world 27508736, 1947238, pixel 839,440. Those map changes took 552 and 203 ms.

- **Accuracy:** 0 world units of difference on all three, compared after Doom's published position was applied back to Daggerfall. Published positions are truncated to whole units by that path.
- **Cancel:** Esc on the first menu in every run left pixel, gold, and game time unchanged.
- **Load, first visit:** the converter took 4.7 to 5.3 s, and Doom is frozen during it with no message. The map change then took 194 to 509 ms.
- **Load, cached town:** 508 ms for the map change.
- **No bridge:** `DOOM.WAD` E1M1 runs clean. With the DRLA set it reports the same 3 script errors and 763 unknown-class lines as the build before this work.
- **Plain Daggerfall:** the private copy logged no bridge activity and no exceptions. It was stopped by the 12-second test limit (exit 124).
- **Registry:** a SHA-256 fingerprint of all 13 values in the owner's Daggerfall Unity key was unchanged after the test runs (`registry_check.py`).
- **Bridge:** `bridge_stress` passes on protocol 4.

## Not proven

- **Facing in Doom was not measured.** Daggerfall's yaw is logged and sent, and Doom assigns it, but nothing read it back. Check by eye.
- **True empty wilderness cannot be chosen.** Daggerfall's map selects named locations, so a remote farm was the open-country test. The overworld branch was exercised only by an earlier run where the town file was unreadable, and that run also reached the right pixel.
- The indoor refusal and a save right after arrival were not run.
- Doom's monsters do not block travel, because Daggerfall's "enemies nearby" check cannot see them. This is an open question for the owner.
- Trips used the blank test character, not a real one.
- The window-to-map mouse mapping is still only tested with surface coordinates.

## Failed approaches

- The blank test character has no skill-use table, so `RaiseSkills` threw partway through travel, after charging and moving but before the post-travel event. Fixed in the test start only.
- The converter copied from the runtime-towns demo writes a cache format this Doom rejects as unreadable, so travel fell back to the overworld. The demo now builds the current converter and `ddruntime.pk3` privately, without touching `tools/dungeon_converter`.
- The first driver assumed 7-pixel list rows. They are 6, which is why one run went to Baghjiwan. It counted as a valid village trip.

# Daggerfall's top-of-screen messages in Doom (run 20261127-055226)

## What was there already

- Doom could already draw Daggerfall HUD rows with Daggerfall Unity's motion (`mods/doomerfall/src/zscript/Doomerfall.zs`,
  a port of `PopupText.cs`), but only for the few lines sent on purpose: Info answers, door/lockpick text, and the
  level-up line (`DFB_KIND_HUD_TEXT`).
- Every other Daggerfall HUD message (`DaggerfallUI.AddHUDText`, `PopupMessage`, `SetMidScreenText`) went to Daggerfall
  Unity's own HUD only, which the player never sees in a paired run. That includes Doomerfall's own lines such as
  "Nothing is assigned to that hotkey." and "Loading ...", which the ammo and hotkey code shows with `AddHUDText`.
- Rows were drawn in Doom's SmallFont at whole-number scale, starting at the very top (where the compass will go), and
  every row was held 1 s, whatever hold time Daggerfall gave it.

## What changed

1. **Every Daggerfall HUD message goes to Doom.** `DoomerfallHudMessages.cs` installs a standing handler on the
   existing `DaggerfallUI.DoomerfallHudText` hook, and the hook now also carries the hold time. Info and NPC Use still
   capture the hook for their own answers and now hand it back afterwards instead of clearing it, so nothing is sent
   twice. The token form of `AddHUDText` (used by action records) now reaches the hook too, one call per line.
2. **Hold time crosses the bridge.** `DFB_KIND_HUD_TEXT` puts the hold time in ms in `dfb_info_text.request`, which was
   always 0 for that kind before (0 still means Daggerfall's default). No layout change, only the header comment.
   Generated bindings were regenerated. `dd_info.cpp` passes the time to the mod, and lines held back while a Daggerfall
   menu is open keep their style and time.
3. **Daggerfall's font.** The converter's `--runtime-assets` step (which already builds `ddruntime.pk3` from the player's
   ARENA2 at install) now also writes `FONT0003.FNT`, the font Daggerfall Unity uses for these messages, as a UZDoom
   folder font `fonts/dffont3` (`tools/dungeon_converter/FontExport.cs`). It is read as Daggerfall Unity reads it: glyphs
   from ASCII 33, proportional widths, space = fixed width - 1, one pixel between glyphs. It is game data, so it is
   generated, never committed. When it is missing (standard WADs, or an older `ddruntime.pk3`), Doom uses SmallFont.
4. **Scale.** Rows use Daggerfall Unity's own native-panel scale, 320x200 scaled to fit (`min(w/320, h/200)`), not a
   whole-number scale. At 1280x800 both are 4. At 1920x1080 it is 5.4, as in Daggerfall Unity.
5. **Hold times.** Each row is held as long as Daggerfall says ("You are entering" 2 s, dungeon flavour text 3 s,
   the Language pacify line 5 s, mid-screen text 1.5 s by default), with PopupText's catch-up and scroll rules.

## Where the messages go, and why

The owner plans a compass at the top centre of Doomerfall's screen, which is exactly where Daggerfall Unity starts its
rows (y = 4 on its 320x200 panel). The rows need to stay at the top centre to look and move as they do in Daggerfall
Unity, so the compass gets a band of its own and the rows keep everything else:

- A band 26 native pixels high (Daggerfall's compass box is 69x17, and DRLA's top key bar ends near 26) is kept clear at the top centre
  (`HudCompassBand` in `Doomerfall.zs`).
- Rows start 4 pixels below the band (y = 30 instead of 4) with Daggerfall Unity's spacing, hold, and scroll.
- A row scrolling away is cut off at the band's bottom edge (a clip rectangle), just as Daggerfall Unity's rows are cut
  off by the top of the screen. So a row never draws over the compass, and the motion looks the same.
- Mid-screen text stays at Daggerfall Unity's row 146. Doom's own pickup messages stay at the top left.

When the compass card is built, `HudCompassBand` should match the compass's real height. It is one constant.

Other options considered: messages under the crosshair or at the bottom (they would no longer look like Daggerfall's),
or the compass below the messages (the compass would move down whenever there is a message, or always sit low). Both
change the owner's layout more than a 26-pixel offset does.

  every 0.25 s for 5 s) and `pairs.gif`. Daggerfall's window draws only black in a paired run, so the test draws
  Daggerfall Unity's interface into a render texture of Doom's screen size and saves that. Same rows, same centring and
  spacing, same mid-screen row 146, same hold times. In both, the mid line is gone by 1.5 s and the first row has
  scrolled away by 3.75 s (pair-015). Doom's rows sit 26 native pixels lower, below the compass band.
- **Visible difference:** Daggerfall Unity draws these with its SDF font (smooth, the default `SDFFontRendering=True`).
  Doom draws the same classic FONT0003 pixel glyphs that Daggerfall Unity uses with SDF off. An SDF font in Doom
  would need a font format UZDoom does not read. Same colours and shadow.
- **Fixed during runs:** the first Doom frames drew the rows almost black. Doom's colour translation maps a one-colour
  font to its darkest shade, so the Daggerfall font is now drawn untranslated and tinted (SmallFont keeps CR_WHITE).
- **Band raised to 26** (from 20): with DRLA's full HUD, 20 put the first row against DRLA's key bar (which ends near
  y = 26 native at 1252x721). 26 still leaves room for Daggerfall's 69x17 compass box. The HUD rework may change this.
  It is one constant, `HudCompassBand`.
- `assemble` now builds the launcher and bridge DLL from this checkout and copies the portable Daggerfall Unity files.
- A stray converter build went to `D:\dev\DoomDaggerfall-loop\lane-items\DoomDaggerfall-build` (a relative `-o` path).
  It is outside this session's allowed folders, so it could not be removed.

# Bridge core

Branch `agent/engine-20261122-220421`. A message and a shared state value now travel both ways between the real UZDoom and the real Daggerfall Unity, started by the launcher.

## What was built

| Piece | Where |
|---|---|
| Transport (C ABI, one source) | `bridge/doomerfall_bridge.{h,cpp}` |
| UZDoom side, static link | `UZDoom/src/dd_bridge.cpp`, two calls in `d_main.cpp`, a small block in `src/CMakeLists.txt` |
| Daggerfall side, P/Invoke | `daggerfall-unity-master/Assets/Scripts/Doomerfall/DoomerfallBridge.cs` |
| Session creation | `launcher/main.cpp` (`--no-bridge` turns it off) |
| Tests | `bridge/test/`: `bridge_stress.cpp`, `real_games_test.py`, `no_session_check.py`, `assemble_review.py` |

Lanes match contract sections 2, 3, and 4.1: two 4,096-slot rings of 64-byte events with a 16,384-event local outbox, two 256-byte state halves in triple buffers, and eight 64 KiB bulk slots. Attach checks magic, protocol version, and layout hash. OS calls sit in one section of the source. The POSIX half is written but **has never been compiled**.

## Pump location: decided by reading and running

The contract proposed `G_Ticker`, and the goal suggested `P_RunClientSideLogic`. **Neither works in every pause state.** `TryRunTics` returns before both while `pauseext` is set (`d_net.cpp:2226`). The pump is in `D_DoomLoop`, before `TryRunTics`.

Measured over a held pause of about 4 seconds, real games:

| Pause state | Doom tics | Map clock | Bridge frames | Pings answered |
|---|---|---|---|---|
| `pauseext` (background pause) | +0 | +0 | +142 | +76 |
| `pause` command | +141 | +0 | +148 | +78 |
| Main menu open | +141 | +0 | +145 | +74 |

While paused the pump runs at about 35 Hz, because the main loop waits for the next tic.

## Measured latency

Real games, launched minimized, so **frame rates are not representative**. Daggerfall ran at roughly 100 to 115 FPS. Figures are from the DRLA run, per 2-second window, startup windows excluded.

| Path | Median p50 | Worst p99 |
|---|---|---|
| Daggerfall to UZDoom, one way | 2.0 ms | 5.6 ms |
| UZDoom to Daggerfall, one way | 5.1 to 6.6 ms | 9.5 ms |
| Round trip | 7.5 to 8.4 ms | 13.2 ms |
| State value age when read | about 1.5 ms | about 6 ms |

Latency is almost entirely each game's frame interval. The transport alone, with spin-polling stand-ins, has a round trip of 0.2 us p50 and 1.3 us p99.9 (the clock resolves 0.1 us), with a 10 ms worst case from OS scheduling. It carried 28 million events per second.

Other runs showed worse moments: 30 to 50 ms p99 in some windows, and a **546 to 611 ms UZDoom-to-Daggerfall spike early in a session**, in the window right after Daggerfall starts. It fits Daggerfall's startup stall, but the cause was not isolated.

Daggerfall's pump allocated **0 bytes over 2,985 measured frames** by `GC.GetTotalMemory`. Only the two-second log line allocates, and those frames are excluded.

## Proven with the real games

- Hello, text, ping, and pong in both directions, with 0 sequence gaps, stock and with the DRLA set.
- Shared state in both directions (`df_value` and `uz_value` advance on the other side).
- All three pause states above.
- Force-killing either game mid-session: the launcher closes the other in about 0.2 s.
- **No session, UZDoom:** E1M1 stock and with DRLA, compared with the `uzdoom-launcher` baseline. Logs match after filtering out lines with timings, paths, and versions (38 and 2,149 lines, 0 differences). `-norun` exits 1337.
- **No session, Daggerfall:** launched with the bridge DLL removed; the log has 0 bridge or missing-DLL mentions.

## Proven only with stand-in processes

`bridge_stress` passes all 9 tests: bad attach, overflow and hard cap, 5M-event wraparound, 10M-event cross-process stream, state tearing across 12 killed writers, bulk tearing, killed and replaced consumer, repeatedly killed producer, and latency.

A replacement process **reattaching** to a live session was only tested here. The launcher ends both games when one dies, so the real games never do this.

## Known gaps

- **The demo lives in the worktree.** Writing the assembled folder to `review\bridge-core` was blocked by this run's sandbox. `review\bridge-core\play.bat` is a one-line forwarder to `daggerfall-unity-master\Builds\bridge-core\play.bat`, so it breaks if this worktree is removed. To relocate it, change `REVIEW` in `assemble_review.py` and rerun it.
- **`play.bat` itself was not launched,** because it opens visible windows and the owner may be using the machine. The same launcher path ran minimized with the same mods.
- **The owner's Daggerfall registry key was not compared before and after,** because reading it needed approval. Isolation rests on the private copy: its product name is patched to `Doomerfall Local` and it runs in portable mode.
- Every Unity build rewrites `addressables_content_state.bin`. The overnight auto-save commits (`e5d12b5`, `bdcd356`) picked up that change. It has been reverted to its pre-run version in a later commit, so this branch has no net change to it. A future Unity build will modify it again.
- Nothing stops two processes attaching as the same side.
- UZDoom's pump does not run during a blocking level load. This was not measured.
- A bulk reader can be starved by a writer rewriting nonstop (about 90,000 good reads against 250 million busy results in the worst-case test). It never saw torn data.
- Callers in the demo ignore a refused send. The contract's fault handling for a full outbox is not built.
- `-dfbridgetestpause` remains in UZDoom as a test flag. It only acts inside a bridge session.

## Failed approaches

- A first pause test relied on the window being in the background. `pauseext` never turned on, because a window that never had focus never gets the transition. The log showed `pauseext=0`, so that run was discarded and replaced with the explicit test flag.
- The first overflow test failed because the test's own empty check consumed an event. The test was fixed and its count check made exact.

## Human play-test list

1. Run `D:\dev\DoomDaggerfall-loop\review\bridge-core\play.bat`. Both games and two log windows should open. Each log should show the other game's hello and advancing counters.
2. Open Doom's menu and press pause. The log's `maptime` should stop while `answered` keeps rising.
3. Alt-tab away from Doom with `i_pauseinbackground` on, and confirm the same.
4. Quit either game. The other should close.
5. Confirm your normal Daggerfall Unity still opens at its usual window size and settings.
6. Check latency with both games focused and unminimized, which these tests could not do.
